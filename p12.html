A. Realistic Interview Prompt

"Design a Tic-Tac-Toe game for two players. Then generalize it: support an arbitrary board size and an arbitrary number of symbols in a row to win, and support both human and computer-controlled players."

B. Difficulty

Beginner → Intermediate. Trivial if hardcoded to a 3×3 board with 8 fixed win-lines; the entire value of this problem, as an interview signal, is in the generalization the interviewer almost always asks for next.

C. What This Problem Tests

  • Whether the win-check is a generic algorithm over rows/columns/diagonals of any size, or 8 hardcoded coordinate triples
  • Cleanly polymorphic players (human vs. AI) via Strategy, rather than an isAI boolean with branching move logic
  • Recognizing the turn-based game loop itself as a reusable skeleton (Template Method) across an entire family of board games, not something specific to Tic-Tac-Toe
  • Resisting over-engineering — this problem rewards clean simplicity, not pattern-stacking for its own sake

D. Requirements

Functional

  1. Support an N×N board (default 3×3)
  2. Support K-in-a-row win condition (default 3), checked across rows, columns, and both diagonal directions
  3. Support 2+ players, each assigned a distinct symbol
  4. Support both human players (external move input) and computer players (internally decided moves)
  5. Detect a win, a draw (board full, no winner), and reject illegal moves (occupied cell, out-of-turn, out-of-bounds)

Non-Functional

  • Adding a new board size or win-length must require zero changes to the win-checking algorithm's code, only its parameters
  • Adding a new AI difficulty must not require changes to the game loop or board

F. Assumptions

  • Confirmed: N×N board, K-in-a-row win, human and computer players, turn-based.
  • Assumption: default 2 players unless asked for more — the design supports a list of players either way, so this is a configuration detail, not a structural one.
  • Assumption: "computer player" means at least a legal-random-move strategy; a full minimax/alpha-beta implementation is discussed as a swappable MoveStrategy but not required to be exhaustive.

I. Class Relationships

  • Strategy for both AI move selection and win-checking: both are algorithms an interviewer expects generalized or swapped — "make the AI harder" is a new MoveStrategy; "support Connect Four's 4-in-a-row on a taller board" is a parameterized WinningStrategy, not new code.
  • Why win-checking must not be 8 hardcoded coordinate triples: the single most common naive shape for this exact problem is a literal list of the 3×3 board's 8 winning lines. It works for the demo and breaks the instant the board size changes. A generic WinningStrategy scans every row, column, and both diagonal directions through the just-played cell, checking for K consecutive matching symbols — this is the direct generalization interviewers are testing for.
  • Why Template Method for the game loop: "initialize board → loop (get move → validate → place → check win/draw → switch turn) → declare result" is the same skeleton for Tic-Tac-Toe, Connect Four, and Gomoku — only setupBoard() (board dimensions) and the winning strategy actually differ. This is the genuine case for Template Method that Coffee Vending Machine's brewing steps (Problem 8) explicitly were not — there, "the recipe" was just varying data over one fixed algorithm; here, subclasses truly do plug in different structural pieces (board shape, win rule) into a shared control flow.
  • Player as abstract base, not a boolean flag: HumanPlayer vs. AIPlayer as real polymorphic types (rather than one Player class with an isAI flag and an if in getMove()) is what lets a new player type (e.g. a remote/networked player) slot in with zero changes to TurnBasedGame.

M. Design Patterns

PatternProblem It SolvesWhere It AppearsWhen NOT to Use
StrategyAI move selection and win-checking are both algorithms expected to vary/generalizeMoveStrategy, WinningStrategySkip MoveStrategy variety if the round only ever needs "legal random move"
Template MethodThe turn-based loop skeleton is identical across a family of grid games; only specific steps differTurnBasedGame.play()Skip entirely if only one single game will ever exist — then a plain loop in GameController is simpler and this is a real case where Template Method is not needed (contrast with the reasoning in I)

Explicitly avoided: hardcoded win-line enumeration — the most common shortcut for exactly this problem, and precisely what a generic line-scan WinningStrategy replaces.

O. Design Evolution

  • V1: 3×3 board, 8 hardcoded win-line checks, two hardcoded players.
  • V2: replace hardcoded lines with a generic line-scan WinningStrategy the moment board size is generalized — the central lesson of this problem.
  • V3: extract Player as an abstract base once a computer opponent is requested, avoiding an isAI flag.
  • V4: extract MoveStrategy once a second AI difficulty is requested.
  • V5: extract TurnBasedGame as a Template Method only if a second game (Connect Four) is actually requested — not preemptively.

What stays stable: Board's cell-level API. Generalizing size/win-length/game-family are all additive changes behind existing interfaces.

Ownership/validation notes: Board.isValidMove() checks bounds and occupancy before placeMark() ever mutates state; WinningStrategy.checkWinner() is only ever invoked against the cell that was just played, not the whole board, keeping each check O(K) instead of rescanning everything.

Q. Pseudocode — Critical Logic

LineScanWinningStrategy.checkWinner(board, lastMove):
  symbol = board.get(lastMove.row, lastMove.col)
  for each direction in [horizontal, vertical, diagonal, anti-diagonal]:
    count = 1
    count += countMatching(board, lastMove, direction, symbol)
    count += countMatching(board, lastMove, oppositeOf(direction), symbol)
    if count >= K: return true
  return false

TurnBasedGame.play():
  setupBoard()
  while true:
    player = nextPlayer()
    move = player.getMove(board)
    if not board.isValidMove(move): continue   // human retries; AI never produces one
    board.placeMark(move, player.symbol)
    if winningStrategy.checkWinner(board, move): declareResult(WINNER, player); return
    if board.isFull(): declareResult(DRAW); return

void play() {
  setupBoard();
  while (true) {
    Player player = nextPlayer();
    Move move = player.getMove(board);
    if (!board.isValidMove(move)) continue;   // human retries; AI never produces one
    board.placeMark(move, player.getSymbol());
    if (winningStrategy.checkWinner(board, move)) { declareResult(Result.WINNER, player); return; }
    if (board.isFull()) { declareResult(Result.DRAW); return; }
  }
}

R. End-to-End Use Case

startGame() — 3×3 board, K=3, Player X (human), Player O (AI, RandomMoveStrategy)
  │
  ▼
makeMove(X, 0, 0) → valid → board updated → checkWinner (count=1) → no win → switch turn
  │
  ▼
AIPlayer.getMove() → RandomMoveStrategy picks (1,1) → board updated → checkWinner → no win
  │
  ▼
... turns continue until X completes a diagonal ...
  ▼
checkWinner(board, lastMove) scans diagonal through last move → count=3 → declareResult(WINNER, X)

U. Testing Strategy

  • Happy path: a completed row/column/diagonal of length K is detected as a win regardless of board size.
  • Edge cases: a full board with no K-in-a-row is a draw, not silently unresolved; an out-of-turn or occupied-cell move is rejected without mutating the board.
  • Generalization tests: the same WinningStrategy correctly handles a 5×5 board with K=4 without any code change — only the constructor parameter changes.
  • Polymorphism tests: swapping an AIPlayer's MoveStrategy at runtime changes its behavior without touching TurnBasedGame.

W. Concurrency

This problem is turn-based and single-threaded by nature — only one player acts at a time, and there is no shared-resource race analogous to the ones in Parking Lot or Elevator. The one legitimate concern is a networked/remote human player submitting a move for a turn that is no longer theirs (a stale-turn check), which is a validation concern in TurnBasedGame.play(), not a locking concern.

X. Persistence

Not required for a live single-session game. If game history/replays are requested, each move is naturally an append-only log entry (player, cell, timestamp) — a simple repository behind the existing API, no change to Board or TurnBasedGame.

Z. Failure Scenarios

  • A human player's move arrives out of turn (e.g. a delayed network message): rejected by the turn-order check in TurnBasedGame before it ever reaches Board.
  • An AI's MoveStrategy returns an already-occupied cell (a bug in that strategy): Board.isValidMove() still rejects it — validation is never skipped just because the mover is a computer.

AA. Common Bad Designs

  • 8 hardcoded 3×3 win-line coordinate triples — the single most common shortcut for this problem, and the first thing a "generalize the board size" follow-up breaks.
  • One Player class with an isAI boolean and a branch in getMove() instead of real polymorphism.
  • Building a full TurnBasedGame Template Method hierarchy for a round that only ever asks for Tic-Tac-Toe — this problem is one of the few in this document where under-engineering is the safer default; add the abstraction only once a second game is actually requested (see O, M).

AC. Interviewer Evaluation

Strong signal: writing the win-check as a direction-scan from the start rather than enumerating lines; cleanly polymorphic Player subclasses; correctly judging not to build Template Method until a second game is actually on the table.

Red flag: hardcoded win-lines that silently break the moment board size is generalized; an isAI flag with branching logic; reflexively building a multi-game framework for a problem that only asked for Tic-Tac-Toe.

AD. Interview Simulation

Interviewer: Design Tic-Tac-Toe.
Candidate: A 3×3 grid, two players with distinct symbols, and a win-check. I'd write the win-check as a generic scan — for the cell just played, count consecutive matches in each of the four line directions — rather than listing the eight specific winning lines, since that generalizes for free.
Interviewer: Good. Now generalize it to any board size and any number-in-a-row to win.
Candidate: That's exactly why I avoided hardcoding the lines — the same scan works unchanged, I'd just parameterize K and the board dimension.
Interviewer: Add a computer player.
Candidate: I'd make Player an abstract type with HumanPlayer and AIPlayer subclasses rather than a flag, and give AIPlayer a swappable MoveStrategy so a smarter AI later is a new class, not a rewrite.
Interviewer: Would you build out a whole reusable game-engine framework here?
Candidate: Not unless a second game is actually requested — right now that would be speculative abstraction. I'd keep the loop simple and only extract a Template Method base class if Connect Four or something similar actually comes up.

A. Realistic Interview Prompt

"Design a hotel reservation system. Guests can search for available rooms over a date range, book a room, and cancel a reservation. Room prices vary by room type and season."

B. Difficulty

Intermediate, climbing to Advanced on the concurrency follow-up. The entity model itself is approachable; the real signal is whether the candidate notices that "room available for these dates" is a date-range query, not a boolean flag, and handles two guests racing to book overlapping dates on the same room.

C. What This Problem Tests

  • Modeling availability as a function of a date range, not a single mutable status flag on the room
  • Builder for constructing a reservation request that has many optional parts (dates, room type, guest count, add-ons, special requests)
  • Strategy for pricing that varies by room type, season, and demand
  • Observer for booking-confirmation/cancellation notifications, reusing the Pub-Sub foundation rather than reinventing a notification path
  • The check-then-act race, now shaped as an interval-overlap race rather than a simple boolean flag race

D. Requirements

Functional

  1. Search for rooms available across a given check-in/check-out date range, optionally filtered by room type
  2. Book a room for a date range, producing a reservation with a computed total price
  3. Cancel a reservation, freeing the room's availability for that date range
  4. Price a room based on room type, season, and current demand
  5. Notify the guest (and hotel staff) on booking confirmation and cancellation

Non-Functional

  • Two guests booking overlapping (or identical) date ranges on the same room must not both succeed
  • Adding a new pricing rule (e.g. a weekend surcharge) must not require touching booking or cancellation logic

F. Assumptions

  • Confirmed: date-range search, booking, cancellation, room-type-and-season-aware pricing, booking/cancellation notifications.
  • Assumption: availability is tracked per specific physical room (not an undifferentiated type-level pool), since that is the harder and more commonly asked version.
  • Assumption: no intentional overbooking — a booked date range is a hard exclusion on that room unless stated otherwise.

I. Class Relationships

  • Availability as an interval structure, not a boolean: the single most consequential modeling decision in this problem is that a room's availability is a function of a date range, so RoomInventory holds a sorted collection of booked intervals per room and answers "is this range free" via interval-overlap logic — not a single isAvailable boolean on Room, which cannot represent "free from March 1–5 but booked March 6–10."
  • Builder for reservation requests: a booking has several optional parts — room type preference, number of guests, add-ons (breakfast, late checkout), special requests — that don't all apply to every booking. A telescoping constructor or a giant parameter list is the naive alternative; ReservationRequestBuilder assembles the request step by step and validates it once, at build(), rather than validating partial state throughout.
  • Strategy for pricing: price depends on room type, season, and demand, and hotels change these rules far more often than they change the booking flow itself — isolating this behind PricingStrategy.calculatePrice(...) means a new seasonal rule is a new strategy, not a change to Reservation or Hotel.
  • Observer for booking notifications: confirming or cancelling a reservation triggers notifications to the guest and possibly hotel staff. Rather than building a bespoke notification path, this explicitly reuses the same subject/observer relationship Pub-Sub (Problem 10) established as the foundational pattern for "something happened, tell everyone who's registered interest" — BookingNotifier is a thin, domain-specific subject, and the actual message dispatch reuses the Notification System (Problem 7) rather than reimplementing channel logic.

O. Design Evolution

  • V1: one boolean availability flag per room, one flat price, no notifications.
  • V2: replace the flag with RoomInventory's interval structure the moment "available for these specific dates" becomes a real requirement, not a demo simplification.
  • V3: extract PricingStrategy once a second pricing rule (season) is requested.
  • V4: introduce ReservationRequestBuilder once the request grows past dates and room type.
  • V5: wire BookingNotifier to the existing Pub-Sub/Notification System infrastructure once confirmations are requested.

What stays stable: Hotel's public search/book/cancel API. New pricing rules and request fields are additive.

P. API / Interface Design

interface PricingStrategy {
  Money calculatePrice(Room room, Date checkIn, Date checkOut);
}

class ReservationRequestBuilder {
  ReservationRequestBuilder withDates(Date checkIn, Date checkOut);
  ReservationRequestBuilder withRoomType(RoomType type);
  ReservationRequestBuilder withAddOn(AddOn addOn);
  ReservationRequest build();
}

class Hotel {
  List<Room> searchAvailability(Date checkIn, Date checkOut, RoomType type);
  Reservation bookRoom(Guest guest, ReservationRequest request);
  void cancelReservation(String reservationId);
}

Ownership/validation notes: bookRoom() locates a specific Room whose RoomInventory reports the requested range free, atomically reserves that interval, and only then constructs the Reservation and prices it — availability is never assumed to still hold between the search call and the book call.

Q. Pseudocode — Critical Logic

Hotel.bookRoom(guest, request):
  candidateRoom = pickCandidate(request.roomType)
  lock(candidateRoom.inventory)
  try:
    if not candidateRoom.inventory.isAvailable(request.range): reject
    candidateRoom.inventory.book(request.range)
    price = pricingStrategyFor(candidateRoom).calculatePrice(candidateRoom, request.range)
    reservation = new Reservation(guest, candidateRoom, request.range, price)
    bookingNotifier.notifyConfirmed(reservation)
    return reservation
  finally:
    unlock(candidateRoom.inventory)

RoomInventory.isAvailable(range):
  return bookedIntervals.none(existing => existing.overlaps(range))

U. Testing Strategy

  • Happy path: booking a free date range on a room makes that exact range unavailable for future searches without affecting adjacent, non-overlapping ranges on the same room.
  • Edge cases: a request whose check-out date exactly equals another booking's check-in date (back-to-back stays) is accepted, not rejected as a false overlap.
  • Pricing tests: the same room and duration produce different totals in peak vs. off-season, without changing any code — only the active PricingStrategy.
  • Concurrency tests: two guests simultaneously booking overlapping date ranges on the same room result in exactly one success and one clean rejection.

W. Concurrency

Shared mutable state: each room's booked-interval collection in RoomInventory, particularly for popular rooms/dates.

  • The check-then-act race, in interval form: checking "is this range free" and then booking it are two steps; without a lock around the specific room's inventory, two guests racing for overlapping dates on the same room could both read "free" before either commits. This is the same bug shape already seen in Parking Lot (Problem 1), Splitwise (Problem 4), ATM (Problem 14), and Library (Problem 15) — lock the specific resource, re-verify, then commit.
  • Per-room locking, not per-hotel: only the one contested room's inventory needs locking — bookings on other rooms proceed independently, even for the same dates.
  • Real-world alternative: a database-level exclusion constraint on a range type (e.g. PostgreSQL's EXCLUDE USING gist over a date range column) enforces non-overlap at the storage layer itself, turning the race into a constraint-violation error on the losing transaction instead of requiring an application-level lock.

X. Persistence

Reservations and booked intervals are durable by nature — a booking that disappears on restart is a correctness failure, not a caching inconvenience. Each room's booked intervals are naturally repository-backed, and the exclusion-constraint approach from W is specifically a persistence-layer technique, not an in-memory one.

Z. Failure Scenarios

  • Payment succeeds but the booking commit fails (or vice versa): the two must be transactionally consistent, or the booking flow needs a compensating action (refund on booking failure, or hold-then-confirm rather than charge-then-book) — the same commit-ordering discipline as ATM's debit-before-dispense logic (Problem 14).
  • A cancellation is retried after a network timeout: cancelling an already-cancelled reservation must be idempotent — checking current status before re-releasing the interval, rather than assuming the retry is the first attempt (the same idempotency-under-retries lesson from Pub-Sub, Problem 10).

AA. Common Bad Designs

  • A boolean isAvailable flag on Room instead of an interval structure — the defining mistake for this problem; see I.
  • Checking availability and booking as two separate, unlocked calls from the caller's side — reintroduces the check-then-act race even if RoomInventory itself is well-designed, because the caller does the check-then-act instead of the room.
  • Hardcoding seasonal price multipliers as constants inside Reservation instead of a swappable PricingStrategy — breaks the first time a promotional rate or demand-based rule is requested.
  • A single Hotel class directly implementing search, booking, pricing, and notification — the same god-object shape flagged in nearly every problem in this document.

AC. Interviewer Evaluation

Strong signal: modeling availability as intervals unprompted; isolating pricing behind a Strategy before being asked for a second pricing rule; catching the overlapping-booking race and proposing either a lock or an exclusion constraint without being walked into it.

Red flag: a boolean availability flag; checking-then-booking as two unlocked steps; hardcoded seasonal price constants; a god-object Hotel class.

AD. Interview Simulation

Interviewer: Design a hotel reservation system.
Candidate: The key modeling decision is that a room's availability isn't a single flag — it's a set of booked date intervals. I'd give each Room a RoomInventory that answers "is this range free" via overlap checks against its booked intervals, not a boolean that can't represent partial-date availability.
Interviewer: How would you handle a booking request with optional extras like breakfast or late checkout?
Candidate: I'd use a Builder for the reservation request — ReservationRequestBuilder — since the request has several optional parts that don't all apply to every booking. It validates once at build() instead of forcing every caller through a huge constructor or leaving partial state to be validated ad hoc.
Interviewer: Two guests try to book the same room for overlapping dates at the same instant.
Candidate: Same fix as the last-copy race in the Library problem or the balance race in the ATM problem — lock that room's inventory, re-verify the range is still free, then commit. In production I'd actually push this to the database with an exclusion constraint on a date-range column, so the non-overlap invariant is enforced at the storage layer instead of relying purely on application-level locking.
Interviewer: How does pricing work if it varies by season?
Candidate: Behind a PricingStrategy interface, keyed by room type and the date range's season — a new promotional rule or demand-based rule becomes a new strategy, not a change to the booking flow itself.

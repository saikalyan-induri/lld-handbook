A. Realistic Interview Prompt

"Design a notification system that can send a message to a user through multiple channels — email, SMS, push. It should respect user preferences, avoid spamming any one user, and retry failed deliveries."

B. Difficulty

Intermediate for the core multi-channel dispatch; Advanced once rate limiting, retry-with-backoff, and idempotent at-least-once delivery enter — at which point this problem directly reuses machinery from Problem 3 (Rate Limiter) and shares its concurrency lessons with Problem 4 (Splitwise) and Problem 5 (Ride-Sharing).

C. What This Problem Tests

  • Strategy for per-channel dispatch — the same shape as matching/fare/split strategies elsewhere in this document
  • Recognizing a genuine Chain-of-Responsibility pipeline (preference check → rate-limit check → send), unlike Logging's thinner CoR fit
  • Deliberately rejecting Bridge in favor of simple parameterization — a considered "fancier pattern, correctly avoided" call
  • Reusing an existing abstraction (RateLimitAlgorithm from Problem 3) instead of reinventing one
  • Idempotent, retryable delivery under an at-least-once guarantee

D. Requirements

Functional

  1. Send a notification to a user through one or more channels (email, SMS, push, in-app)
  2. Respect per-user, per-channel, per-category opt-in/opt-out preferences
  3. Render notification content from a template plus parameters
  4. Rate-limit notifications per user per channel (e.g. max 5 SMS/day)
  5. Retry failed deliveries with backoff, up to a bounded number of attempts

Non-Functional

  • Adding a new channel must not require changes to the core dispatch logic
  • A burst of trigger events must not overwhelm downstream channel providers
  • A retried delivery must not result in a user receiving the same notification twice
  • An opted-out user must never receive a notification on that channel/category, full stop

F. Assumptions

  • Confirmed: multi-channel dispatch; per-user preferences; rate limiting; retries.
  • Assumption: notifications are triggered by internal system events (Observer-style), not only direct synchronous calls — matching how the Ride-Sharing problem's notification stub was left open-ended.
  • Assumption: delivery is at-least-once; every Notification carries an idempotency key so a retried send is safely deduplicated by the channel provider or a local dedupe cache.
  • Assumption: rate limiting reuses the RateLimitAlgorithm interface from Problem 3 verbatim, keyed by (userId, channel) — no reason to design a second rate-limiting abstraction from scratch.
  • Assumption: exhausted retries land in a dead-letter queue for later inspection rather than vanishing silently.

I. Class Relationships

  • Dependency: NotificationService → NotificationChannel, UserPreference, RateLimiter, RetryScheduler (all interfaces/collaborators, injected).
  • Strategy: NotificationChannel implementations (Email/SMS/Push/InApp) are mutually exclusive alternative delivery mediums — a clean Strategy fit, identical in shape to FareStrategy/MatchingStrategy in Ride-Sharing.
  • Why Bridge was considered and rejected: category (Transactional/Promotional/Security-alert) and channel (Email/SMS/Push) look like two independent dimensions that Bridge is designed to decouple. But in practice, category only ever changes content and default channel selection (via the template + a config lookup), not delivery behavior — there's no method on NotificationChannel that a category needs to override differently. Introducing Bridge here would add a second class hierarchy to solve a problem that a template lookup plus a parameter already solves. This mirrors Splitwise's Payment-not-subclass and Ride-Sharing's Singleton rejection — a deliberately not-applied pattern.
  • Composition: a Notification is rendered from exactly one NotificationTemplate at send time; the rendered content has no independent lifecycle.

O. Design Evolution

  • V1: one channel (email), direct synchronous call, no preferences.
  • V2: add NotificationChannel interface; support SMS and push alongside email.
  • V3: add UserPreference checks before every send.
  • V4: integrate the reused RateLimiter from Problem 3, keyed per (user, channel).
  • V5: add RetryScheduler with exponential backoff and a DeadLetterQueue for exhausted attempts.
  • V6: event-driven triggering via Observer, idempotency keys for at-least-once delivery, async dispatch queue for burst absorption.

What stays stable: NotificationService.notify()'s signature. New channels, new preference granularity, and new retry policies are all additive.

P. API / Interface Design

interface NotificationChannel {
  DeliveryResult send(RenderedContent content, String recipientAddress);
}

class NotificationService {
  void notify(String userId, Category category, String templateId,
              Map<String,Object> params, List<ChannelType> channels, String idempotencyKey);
}

Ownership/validation notes: notify() runs preference → rate-limit checks per requested channel before rendering or sending anything on that channel — an opted-out or rate-limited channel is skipped cheaply, never rendered. The idempotencyKey is mandatory, not optional, given the at-least-once assumption in F.

Q. Pseudocode — Critical Logic

notify(userId, category, templateId, params, channels, idemKey):
  if dedupeCache.seen(idemKey): return                 // idempotent replay guard
  for channel in channels:
    if not userPreference.isAllowed(userId, channel, category): continue
    if not rateLimiter.tryAcquire(key=(userId, channel)): continue
    content = template.render(templateId, channel, params)
    result = channelImpl(channel).send(content, resolveAddress(userId, channel))
    if result.failed:
      retryScheduler.scheduleRetry(notification, attempt=1)
  dedupeCache.record(idemKey)

RetryScheduler.onRetryDue(notification, attempt):
  result = channelImpl(notification.channel).send(...)
  if result.failed:
    if attempt >= MAX_ATTEMPTS:
      deadLetterQueue.record(notification, result.error)
    else:
      scheduleRetry(notification, attempt + 1, delay=backoff(attempt))

U. Testing Strategy

  • Happy path: allowed, unthrottled channel delivers successfully and is recorded as such.
  • Preference short-circuit: an opted-out channel is never rendered or sent — assert the channel implementation's send() was never called.
  • Rate-limit short-circuit: exceeding the per-channel quota skips the send without consuming a retry attempt.
  • Idempotency: calling notify() twice with the same idempotency key results in exactly one delivery attempt sequence, not two.
  • Retry/backoff: a failing channel is retried at the correct intervals and lands in the dead-letter queue after the configured max attempts, not before and not indefinitely.

W. Concurrency

Shared mutable state: the rate limiter's per-key counters (already addressed in Problem 3), the dedupe cache, and the retry scheduler's pending-retry queue.

  • Burst absorption: a flood of trigger events (e.g. a mass promotional campaign) shouldn't call channel providers synchronously inline — an async dispatch queue between "decided to send" and "actually sent" smooths bursts, mirroring Logging's async-appender lesson in a different domain.
  • Idempotent retries under concurrency: if a retry and a fresh duplicate trigger race for the same idempotency key, the dedupe cache must be checked and recorded atomically (check-then-set is the same race shape flagged in Parking Lot and Ride-Sharing) — an atomic putIfAbsent-style operation, not a separate read then write.
  • Per-channel isolation: one slow or failing channel's retries must not consume worker capacity needed by healthy channels — a separate retry queue or thread pool per channel type avoids one outage degrading everything.

X. Persistence

Two different durability needs worth separating: (1) delivery records — an audit trail of what was sent, when, and its final status, useful for support/compliance, naturally append-only; (2) pending retry state — must survive a process restart (a retry scheduled for 5 minutes from now shouldn't vanish if the service redeploys), which argues for a durable queue (e.g. a database table or a message broker) rather than a purely in-memory timer. Treating pending retries as safely in-memory is the single most common shortcut worth flagging as a real gap.

Z. Failure Scenarios

  • Channel provider returns an ambiguous result (timeout — did it send or not?): must be treated as "unknown," retried under the idempotency guarantee, not assumed successful or failed.
  • Retry storm after a provider outage recovers: a large backlog of queued retries firing all at once can re-overwhelm the just-recovered provider — jittered backoff (not just exponential) mitigates this.
  • Dedupe cache eviction before a legitimate slow retry lands: if the TTL is too short relative to the real retry window, a legitimate retry could be treated as new (or vice versa) — the TTL must be sized against the actual max retry duration.

AA. Common Bad Designs

  • God-object NotificationService with preference, rate-limit, rendering, and sending all inlined — the same trap as everywhere else in this set.
  • Bridge pattern for category × channel — a "textbook-looking" but ultimately unjustified pattern here; see I for why it doesn't survive contact with what actually varies.
  • Reinventing rate limiting from scratch instead of reusing Problem 3's abstraction — duplicated logic that will drift out of sync over time.
  • No idempotency key, relying on "retries are rare enough" — silently violates the non-functional requirement the moment retries actually happen.
  • Synchronous, blocking channel calls directly inside the event handler — a burst of trigger events becomes a burst of blocked threads.

AC. Interviewer Evaluation

  • Weak candidate: hardcodes one channel, no preference or rate-limit checks at all.
  • Average candidate: has a Channel Strategy and preference checks, but no idempotency story and no retry policy.
  • Strong candidate: full pipeline (preference → rate-limit → send → retry) with a clean Strategy for channels and an explicit idempotency key.
  • Exceptional candidate: all of the above, plus explicitly reuses the Problem 3 rate limiter rather than reinventing it, correctly rejects Bridge for category/channel, and connects burst-handling directly to a Pub-Sub-style async queue without being asked.

AD. Interview Simulation

Interviewer: Design a notification system supporting email, SMS, and push.
Candidate: I'll make delivery medium a Strategy — a NotificationChannel interface with one implementation per medium. Quick question: should this also enforce user preferences and rate limits, or is that out of scope?
Interviewer: Both are in scope.
Candidate: Then the send pipeline is preference-check, then rate-limit-check, then render-and-send — each stage can short-circuit the rest. For rate limiting specifically, I'd reuse the same token-bucket abstraction I'd use for an API rate limiter, just keyed by user and channel instead of by client.
Interviewer: A delivery attempt times out — did it send or not?
Candidate: That's treated as unknown, and retried — which means every notification needs an idempotency key so a provider that actually did send it the first time doesn't double-deliver on retry.
Interviewer: Isn't category (promotional vs. transactional) and channel (email vs. SMS) exactly the kind of two-dimensional variation Bridge is meant for?
Candidate: It looks that way, but category only changes which template and default channels get used — it doesn't change how any channel actually sends. Since there's no method that needs to vary by category on the channel side, Bridge would add a second hierarchy to solve something a template lookup already solves more simply.
Interviewer: How would this handle a flash-sale-sized burst of notifications?
Candidate: I wouldn't call channel providers synchronously from the event handler — I'd push onto an async queue and let a worker pool drain it, which is really just this document's Pub-Sub design applied directly to this problem's dispatch step.

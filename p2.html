A. Realistic Interview Prompt

"Design an in-memory cache with a fixed capacity that supports get and put in O(1) time. When the cache is full, evict the least-recently-used entry."

B. Difficulty

Intermediate as a pure data-structure exercise (many candidates have memorized DLL+HashMap). It becomes a genuine LLD problem — not just a DSA problem — the moment the interviewer asks for thread-safety, pluggable eviction policies, or scale, which is why it's included here despite its simple core.

C. What This Problem Tests

  • Choosing the right data structure combination for O(1) access + O(1) reordering
  • Encapsulation — hiding the linked-list/map wiring behind a clean two-method API
  • Recognizing when Strategy/pluggability is (and isn't) the right abstraction
  • Concurrency reasoning — specifically the "read that mutates" trap
  • API design discipline (CQS: does get need a non-mutating peek sibling?)

D. Requirements

Functional

  1. Fixed capacity, set at construction
  2. get(key) returns the value or a miss signal; counts as a "use" (updates recency)
  3. put(key, value) inserts or updates; counts as a "use"
  4. When inserting past capacity, evict the least-recently-used entry first

Non-Functional

  • O(1) time for both get and put
  • Thread-safe under concurrent access (confirm with interviewer — see E)
  • Extensible to other eviction policies without a full rewrite, if asked

F. Assumptions

  • Confirmed: fixed capacity, O(1) get/put, LRU eviction on overflow.
  • Assumption: both get and put on an existing key update recency.
  • Assumption: single-threaded core design first (V1–V3), thread-safety added explicitly (V4+) — this mirrors how the problem is actually escalated in interviews.
  • Assumption: capacity is entry-count based, not weight-based, unless asked.
  • Assumption: no TTL, no distributed scope, no persistence in the base design.

I. Class Relationships

  • Composition: LRUCache owns its Node list and its map — neither outlives the cache.
  • Shared reference (not ownership duplication): the map's values and the linked list's nodes are the same objects — the map gives O(1) lookup, the list gives O(1) reordering. This dual-structure trick is the core insight of the whole problem.
  • Realization (optional): LRUCache implements Cache<K,V> only if a second implementation (e.g. LFU) is actually needed — see M for why this interface is easy to get wrong.

O. Design Evolution

  • V1: HashMap + DLL, fixed capacity, no eviction yet — just storage.
  • V2: Add eviction — when put exceeds capacity, remove the tail (LRU) node.
  • V3: get and put on existing keys move the node to the head (recency).
  • V4: Thread-safety — wrap critical sections in a single lock; explicitly reason about why "readers don't need a lock" is wrong here (see W).
  • V5: Reduce contention — shard into N independent sub-caches by hash(key) % N, each with its own lock; global order becomes approximate.
  • V6: Pluggability — extract Cache<K,V> interface if a second policy (LFU) is genuinely required, accepting that it's a whole-class swap, not a strategy field.

What stays stable: the two-method public API (get/put). Internal locking granularity and eviction bookkeeping evolve underneath it without callers noticing.

public Optional<V> get(K key) {
  Node<K, V> node = map.get(key);
  if (node == null) return Optional.empty();   // MISS
  moveToHead(node);
  return Optional.of(node.value);
}

public void put(K key, V value) {
  Node<K, V> node = map.get(key);
  if (node != null) {
    node.value = value;
    moveToHead(node);
    return;
  }
  Node<K, V> newNode = new Node<>(key, value);
  map.put(key, newNode);
  addToHead(newNode);
  if (map.size() > capacity) {
    Node<K, V> lru = tail.prev;
    removeNode(lru);
    map.remove(lru.key);
  }
}
std::optional<V> get(const K& key) {
  auto it = map.find(key);
  if (it == map.end()) return std::nullopt;   // MISS
  moveToHead(it->second);
  return it->second->value;
}

void put(const K& key, const V& value) {
  auto it = map.find(key);
  if (it != map.end()) {
    it->second->value = value;
    moveToHead(it->second);
    return;
  }
  auto newNode = std::make_shared<Node>(key, value);
  map[key] = newNode;
  addToHead(newNode);
  if (map.size() > capacity) {
    auto lru = tail->prev;
    removeNode(lru);
    map.erase(lru->key);
  }
}
get(key) {
  const node = this.map.get(key);
  if (node === undefined) return MISS;
  this.moveToHead(node);
  return node.value;
}

put(key, value) {
  const node = this.map.get(key);
  if (node !== undefined) {
    node.value = value;
    this.moveToHead(node);
    return;
  }
  const newNode = new Node(key, value);
  this.map.set(key, newNode);
  this.addToHead(newNode);
  if (this.map.size > this.capacity) {
    const lru = this.tail.prev;
    this.removeNode(lru);
    this.map.delete(lru.key);
  }
}
get(key: K): V | typeof MISS {
  const node = this.map.get(key);
  if (node === undefined) return MISS;
  this.moveToHead(node);
  return node.value;
}

put(key: K, value: V): void {
  const node = this.map.get(key);
  if (node !== undefined) {
    node.value = value;
    this.moveToHead(node);
    return;
  }

U. Testing Strategy

  • Happy path: put then get returns the same value; recency order updates correctly.
  • Edge cases: capacity = 1; put on an already-full cache with a brand-new key evicts exactly one; repeated get on the same key never evicts it.
  • Invalid input: capacity ≤ 0 at construction should be rejected.
  • Concurrency tests: N threads hammering get/put — assert size never exceeds capacity and no node ever appears twice in the list (structural corruption check), even though exact eviction order under a race is not required to be deterministic.

W. Concurrency

The central insight: get is not a pure read — it mutates the linked list (moveToHead). Treating it as read-only and reaching for a read-write lock (letting concurrent "readers" proceed together) is a classic, subtle bug: two concurrent "reads" can corrupt the list pointers.

  • Simplest correct approach: one exclusive lock (mutex/synchronized) guarding both get and put entirely.
  • Reducing contention: shard into N independent caches by key hash, each with its own lock — same idea used internally by structures like ConcurrentHashMap. Global recency order becomes approximate across shards, which is an accepted trade-off.
  • Why plain atomics aren't enough: updating a DLL node touches multiple pointers (prev/next on up to three nodes) — not a single atomic word, so std::atomic alone can't make this safe without a lock or a much more complex lock-free list.
  • Real-world alternative: production caches (e.g. Caffeine) use approximate recency (CLOCK-like sampling) specifically to avoid taking a lock on every access — worth mentioning as the "senior" answer if pushed on extreme throughput, without over-claiming you'd implement it from scratch in an interview.

X. Persistence

Caches are usually intentionally volatile — the source of truth lives elsewhere (DB), and the cache is just an optimization. If persistence is explicitly requested: introduce a CacheLoader (read-through on miss) and/or CacheWriter (write-through/write-back on put), and be explicit that persisted "cache" state is a performance optimization, not a durability guarantee — losing it on crash should be an acceptable, recoverable event, not a data-loss incident.

Z. Failure Scenarios

  • Process crash: all cached data is lost by design — the system must tolerate a cold cache and repopulate from the source of truth.
  • Partial mutation on crash mid-eviction: only relevant if persisted; in-memory-only designs don't need to reason about this.
  • Listener/write-back failure on eviction: should not block or corrupt the cache itself — failures in a listener must be isolated (e.g., caught and logged, not propagated to break put).

AA. Common Bad Designs

  • ArrayList + linear shift for order — looks intuitive, but shifting elements on every access is O(n), defeating the entire point of the problem.
  • Sorting by a stored "last accessed" timestamp at eviction time — looks clever (avoids a linked list), but makes eviction O(n log n) instead of O(1), and still needs a way to look up entries by key.
  • Read-write lock "optimization" — looks like a throughput win ("reads don't block each other"), but is actually incorrect here because get mutates state (see W).
  • A generic pluggable "EvictionPolicy" interface bolted onto one fixed DLL+Map structure — looks extensible, but LFU/ARC genuinely need different backing structures, so the abstraction leaks or becomes dishonestly slow. Better to swap the whole class via a Cache<K,V> interface.

AC. Interviewer Evaluation

  • Weak candidate: uses an array/list with linear scans; doesn't recognize the O(1) requirement drives the whole design.
  • Average candidate: correct HashMap+DLL design, but doesn't proactively mention thread-safety or ask about it.
  • Strong candidate: correct design, asks about concurrency requirements unprompted, and explains why get is "secretly a write."
  • Exceptional candidate: all of the above, plus recognizes that naive policy-pluggability (LRU→LFU) doesn't fit a field-injection model, and can discuss sharding/approximate-LRU trade-offs at scale without being asked.

AD. Interview Simulation

Interviewer: Design an LRU cache with O(1) get and put.
Candidate: I'll use a hash map for O(1) lookup and a doubly linked list for O(1) reordering — the map's values and the list's nodes will be the same objects.
Interviewer: Walk me through put when the cache is full.
Candidate: Insert the new node at the head, then if size exceeds capacity, remove the tail's previous node — that's the least recently used — and delete it from the map too.
Interviewer: Now make it thread-safe.
Candidate: I'd guard both get and put with a single exclusive lock. It's worth calling out explicitly: get isn't read-only here, it moves the node to the head, so a read-write lock would actually be a bug, not an optimization.
Interviewer: Good catch. Now, high contention — thousands of threads hitting this every millisecond.
Candidate: I'd shard into N independent LRU caches by hashing the key, each with its own lock — similar to how ConcurrentHashMap works internally. The trade-off is the LRU order becomes approximate across the whole cache rather than globally exact.
Interviewer: Now I want LFU as an alternative, switchable at runtime.
Candidate: I wouldn't try to inject an eviction-policy object into this same map+list structure — LFU needs frequency buckets, a genuinely different backing structure. I'd extract a Cache<K,V> interface and write LFUCache as a sibling implementation instead.
Interviewer: Last one — a billion entries, way past one machine's memory.
Candidate: That's outside LLD at that point — it becomes a distributed cache with consistent hashing and replication across nodes. The class design here stays the same per-node; the system around it changes.

AG. Full Implementation

A complete, compilable reference implementation of every class in the diagram above (composition, inheritance, interface realization, and dependency-injected strategies all preserved per section I), with a runnable demo exercising the primary flow — in Java, C++, JavaScript, and TypeScript.

// LRU Cache - full LLD implementation (single-file demo).
// Difficulty badge is plain "Intermediate" (no Concurrency tag), so this stays
// single-threaded and simple - no locks.
import java.util.*;

public class p2 {

    // ---------- Cache (interface) ----------
    // Exists so callers can depend on a contract rather than the concrete LRU
    // implementation - e.g. an LFU variant could implement this same interface later.
    interface Cache<K, V> {
        Optional<V> get(K key);
        void put(K key, V value);
    }

    // ---------- Node ----------
    // Pure intrusive doubly-linked-list element; holds no policy logic of its own.
    static class Node<K, V> {
        K key;
        V value;
        Node<K, V> prev;
        Node<K, V> next;
        Node(K key, V value) { this.key = key; this.value = value; }
    }

    // ---------- LRUCache ----------
    static class LRUCache<K, V> implements Cache<K, V> {
        private final int capacity;
        // Map gives O(1) lookup; the list (via the same Node objects) gives O(1) reordering.
        // This dual-structure trick is the core insight of the whole problem.
        private final Map<K, Node<K, V>> map;
        private final Node<K, V> head; // sentinel; head.next = most-recently-used
        private final Node<K, V> tail; // sentinel; tail.prev = least-recently-used

        LRUCache(int capacity) {
            if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
            this.capacity = capacity;
            this.map = new HashMap<>();
            this.head = new Node<>(null, null);
            this.tail = new Node<>(null, null);
            head.next = tail;
            tail.prev = head;
        }

        public Optional<V> get(K key) {
            Node<K, V> node = map.get(key);
            if (node == null) return Optional.empty();
            moveToHead(node);
            return Optional.of(node.value);
        }

        public void put(K key, V value) {
            Node<K, V> existing = map.get(key);
            if (existing != null) {
                existing.value = value;
                moveToHead(existing);
                return;
            }
            Node<K, V> newNode = new Node<>(key, value);
            map.put(key, newNode);
            addToHead(newNode);
            if (map.size() > capacity) {
                Node<K, V> lru = tail.prev;
                removeNode(lru);
                map.remove(lru.key);
            }
        }

        // ---- internal list helpers ----
        private void addToHead(Node<K, V> node) {
            node.prev = head;
            node.next = head.next;
            head.next.prev = node;
            head.next = node;
        }

        private void removeNode(Node<K, V> node) {
            node.prev.next = node.next;
            node.next.prev = node.prev;
        }

        private void moveToHead(Node<K, V> node) {
            removeNode(node);
            addToHead(node);
        }

        int size() { return map.size(); }
    }

    // ---------- Demo ----------
    public static void main(String[] args) {
        LRUCache<Integer, String> cache = new LRUCache<>(2);
        cache.put(1, "a");
        cache.put(2, "b");
        System.out.println("get(1) = " + cache.get(1)); // Optional[a], 1 is now most recent

        cache.put(3, "c"); // capacity exceeded -> evicts key 2 (least recently used)
        System.out.println("get(2) = " + cache.get(2)); // Optional.empty (evicted)
        System.out.println("get(3) = " + cache.get(3)); // Optional[c]

        cache.put(1, "a-updated"); // update existing key, also refreshes recency
        System.out.println("get(1) = " + cache.get(1)); // Optional[a-updated]

        System.out.println("final size = " + cache.size());
    }

#include <iostream>
#include <unordered_map>
#include <optional>
#include <stdexcept>
#include <string>

// ---------- Node ----------
// Pure intrusive doubly-linked-list element; holds no policy logic of its own.
template <typename K, typename V>
struct Node {
    K key;
    V value;
    Node* prev = nullptr;
    Node* next = nullptr;
    Node() = default;
    Node(K k, V v) : key(std::move(k)), value(std::move(v)) {}
};

// ---------- Cache (interface) ----------
// Exists so callers can depend on a contract rather than the concrete LRU
// implementation - e.g. an LFU variant could implement this same interface later.
template <typename K, typename V>
class Cache {
public:
    virtual ~Cache() = default;
    virtual std::optional<V> get(const K& key) = 0;
    virtual void put(const K& key, const V& value) = 0;
};

// ---------- LRUCache ----------
template <typename K, typename V>
class LRUCache : public Cache<K, V> {
public:
    explicit LRUCache(int capacity) : capacity(capacity) {
        if (capacity <= 0) throw std::invalid_argument("capacity must be > 0");
        head = new Node<K, V>();
        tail = new Node<K, V>();
        head->next = tail;
        tail->prev = head;
    }

    ~LRUCache() override {
        Node<K, V>* cur = head;
        while (cur) {
            Node<K, V>* next = cur->next;
            delete cur;
            cur = next;
        }
    }

    std::optional<V> get(const K& key) override {
        auto it = map.find(key);
        if (it == map.end()) return std::nullopt;
        Node<K, V>* node = it->second;
        moveToHead(node);
        return node->value;
    }

    void put(const K& key, const V& value) override {
        auto it = map.find(key);
        if (it != map.end()) {
            it->second->value = value;
            moveToHead(it->second);
            return;
        }
        Node<K, V>* newNode = new Node<K, V>(key, value);
        map[key] = newNode;
        addToHead(newNode);
        if (static_cast<int>(map.size()) > capacity) {
            Node<K, V>* lru = tail->prev;
            removeNode(lru);
            map.erase(lru->key);
            delete lru;
        }
    }

    size_t size() const { return map.size(); }

private:
    void addToHead(Node<K, V>* node) {
        node->prev = head;
        node->next = head->next;
        head->next->prev = node;
        head->next = node;
    }

    void removeNode(Node<K, V>* node) {
        node->prev->next = node->next;
        node->next->prev = node->prev;
    }

    void moveToHead(Node<K, V>* node) {
        removeNode(node);
        addToHead(node);
    }

    int capacity;
    std::unordered_map<K, Node<K, V>*> map; // O(1) lookup; list (same Node objects) gives O(1) reordering
    Node<K, V>* head; // sentinel; head->next = most-recently-used
    Node<K, V>* tail; // sentinel; tail->prev = least-recently-used
};

// A sentinel "miss" value distinct from any legitimate stored value (including
// undefined/null), so callers can tell "not found" apart from "found, value is null".
const MISS = Symbol("MISS");

// ---------- Cache (interface, documented via JSDoc since JS has no interfaces) ----------
// Exists so callers can depend on a contract rather than the concrete LRU
// implementation - e.g. an LFU variant could implement this same interface later.
/**
 * @interface Cache
 * get(key) -> value or MISS
 * put(key, value) -> void
 */

// ---------- Node ----------
// Pure intrusive doubly-linked-list element; holds no policy logic of its own.
class Node {
  constructor(key, value) {
    this.key = key;
    this.value = value;
    this.prev = null;
    this.next = null;
  }
}

// ---------- LRUCache ----------
class LRUCache {
  constructor(capacity) {
    if (capacity <= 0) throw new Error("capacity must be > 0");
    this.capacity = capacity;
    // Map gives O(1) lookup; the list (via the same Node objects) gives O(1) reordering.
    // This dual-structure trick is the core insight of the whole problem.
    this.map = new Map();
    this.head = new Node(null, null); // sentinel; head.next = most-recently-used
    this.tail = new Node(null, null); // sentinel; tail.prev = least-recently-used
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  get(key) {
    const node = this.map.get(key);
    if (!node) return MISS;
    this._moveToHead(node);
    return node.value;
  }

  put(key, value) {
    const existing = this.map.get(key);
    if (existing) {
      existing.value = value;
      this._moveToHead(existing);
      return;
    }
    const newNode = new Node(key, value);
    this.map.set(key, newNode);
    this._addToHead(newNode);
    if (this.map.size > this.capacity) {
      const lru = this.tail.prev;
      this._removeNode(lru);
      this.map.delete(lru.key);
    }
  }

  size() { return this.map.size; }

  // ---- internal list helpers ----
  _addToHead(node) {
    node.prev = this.head;
    node.next = this.head.next;
    this.head.next.prev = node;
    this.head.next = node;
  }

  _removeNode(node) {
    node.prev.next = node.next;
    node.next.prev = node.prev;
  }

  _moveToHead(node) {
    this._removeNode(node);
    this._addToHead(node);
  }
}

// ---------- Node ----------
// Pure intrusive doubly-linked-list element; holds no policy logic of its own.
class Node<K, V> {
  prev: Node<K, V> | null = null;
  next: Node<K, V> | null = null;
  constructor(public key: K | null, public value: V | null) {}
}

// ---------- LRUCache ----------
class LRUCache<K, V> implements Cache<K, V> {
  private readonly capacity: number;
  // Map gives O(1) lookup; the list (via the same Node objects) gives O(1) reordering.
  // This dual-structure trick is the core insight of the whole problem.
  private readonly map: Map<K, Node<K, V>> = new Map();
  private readonly head: Node<K, V>; // sentinel; head.next = most-recently-used
  private readonly tail: Node<K, V>; // sentinel; tail.prev = least-recently-used

  constructor(capacity: number) {
    if (capacity <= 0) throw new Error("capacity must be > 0");
    this.capacity = capacity;
    this.head = new Node<K, V>(null, null);
    this.tail = new Node<K, V>(null, null);
    this.head.next = this.tail;
    this.tail.prev = this.head;
  }

  get(key: K): V | undefined {
    const node = this.map.get(key);
    if (!node) return undefined;
    this.moveToHead(node);
    return node.value as V;
  }

  put(key: K, value: V): void {
    const existing = this.map.get(key);
    if (existing) {
      existing.value = value;
      this.moveToHead(existing);
      return;
    }
    const newNode = new Node<K, V>(key, value);
    this.map.set(key, newNode);
    this.addToHead(newNode);
    if (this.map.size > this.capacity) {
      const lru = this.tail.prev as Node<K, V>;
      this.removeNode(lru);
      this.map.delete(lru.key as K);
    }
  }

  size(): number { return this.map.size; }

  // ---- internal list helpers ----
  private addToHead(node: Node<K, V>): void {
    node.prev = this.head;
    node.next = this.head.next;
    (this.head.next as Node<K, V>).prev = node;
    this.head.next = node;
  }

  private removeNode(node: Node<K, V>): void {
    (node.prev as Node<K, V>).next = node.next;
    (node.next as Node<K, V>).prev = node.prev;
  }

  private moveToHead(node: Node<K, V>): void {
    this.removeNode(node);
    this.addToHead(node);
  }
}

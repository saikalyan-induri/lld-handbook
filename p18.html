A. Realistic Interview Prompt

"Design a food delivery system like DoorDash or Swiggy. Customers order from a restaurant's menu, the order moves through preparation and delivery, and a delivery partner is assigned to carry it. Customers should see live status updates."

B. Difficulty

Intermediate, climbing to Advanced on the delivery-assignment and status-ordering follow-ups. The order lifecycle itself is a clean, bounded state machine; the real signal is whether the candidate snapshots menu-item price/name at order time instead of pointing at a live, mutable catalog record, and whether delivery-partner assignment is race-free.

C. What This Problem Tests

  • Snapshotting a menu item's name/price into the order at checkout time, instead of a live reference to a catalog entry that can change later — the same "shared template vs. frozen instance" shape as Book/BookItem, Room/RoomInventory, and Seat/ShowSeat, applied to pricing history
  • State machine for the order lifecycle (placed → confirmed → preparing → out-for-delivery → delivered), including legal-transition enforcement
  • Strategy for delivery-partner assignment (nearest-available vs. load-balanced)
  • Observer for pushing status updates to the customer, reusing the Pub-Sub/Notification System foundation rather than a bespoke path
  • The atomic select-then-claim race on assigning a delivery partner, and out-of-order status updates arriving from the field

D. Requirements

Functional

  1. Browse a restaurant's menu and add items to a cart
  2. Place an order, transitioning it through placed → confirmed → preparing → out-for-delivery → delivered
  3. Assign an available delivery partner to an order ready for pickup
  4. Push real-time status updates to the customer as the order progresses
  5. Reflect a historical order's price exactly as charged, even if the menu item's price later changes

Non-Functional

  • An order must never skip or reverse illegal lifecycle transitions (e.g. "delivered" cannot follow "placed" directly)
  • A delivery partner must never be assigned to two active deliveries at once

F. Assumptions

  • Confirmed: menu browsing/cart, ordered lifecycle with real-time status updates, delivery-partner assignment, price-history correctness.
  • Assumption: cancellation is only legal up through the "confirmed" state; once "preparing" begins, cancellation is out of scope for this pass unless asked.
  • Assumption: status updates arrive as discrete events (from the restaurant POS or the delivery partner's app) that the order's State machine must validate, not blindly trust.

I. Class Relationships

  • MenuItem vs. OrderLineItem is the central modeling decision: this is the same "shared, mutable template vs. frozen, per-instance snapshot" shape already seen in Book/BookItem, Room/RoomInventory, and Seat/ShowSeat — but the mutable thing here is price, not availability. A live reference from Order to MenuItem means a price change today silently rewrites the receipt for an order placed last week, which is both a correctness bug and, in most jurisdictions, a real compliance problem. OrderLineItem freezes the name and price at checkout time, permanently.
  • State machine for the order lifecycle: PLACED → CONFIRMED → PREPARING → OUT_FOR_DELIVERY → DELIVERED, with each OrderState implementation only accepting the transitions that are legal from that state — a "delivered" event arriving while the order is still "placed" (e.g. a duplicated or out-of-order webhook) is rejected by the state itself rather than trusted.
  • Strategy for delivery-partner assignment, atomically claimed by a Dispatcher: the assignment rule (nearest available, load-balanced) is isolated in DeliveryAssignmentStrategy, but selecting a candidate and claiming them must happen as one atomic step in DeliveryDispatcher — otherwise two orders could both select the same "available" partner before either claim commits, the identical select-then-claim race Elevator's (Problem 11) hall-call dispatcher already solved for cars instead of couriers.
  • Observer for status push: every legal state transition notifies OrderStatusNotifier, which fans out to the customer's app — reusing Pub-Sub's (Problem 10) foundational subject/observer relationship and the Notification System's (Problem 7) channel dispatch, rather than building a third bespoke notification path in this document.

O. Design Evolution

  • V1: one order status field with ad hoc updates, live price lookup, manual delivery-partner assignment, no push notifications.
  • V2: introduce OrderLineItem snapshots the moment historical price integrity matters — which should be immediately, since it's a compliance concern, not an edge case.
  • V3: formalize the OrderState machine once status updates start arriving from external systems (POS, delivery app) that can't be fully trusted to send them in order.
  • V4: extract DeliveryAssignmentStrategy and the atomic DeliveryDispatcher once automatic assignment is requested.
  • V5: wire OrderStatusNotifier into existing Pub-Sub/Notification infrastructure once live push updates are requested.

What stays stable: OrderService's public place/update API. New states and assignment rules are additive.

P. API / Interface Design

interface OrderState {
  OrderState onConfirm();
  OrderState onPrepared();
  OrderState onPickedUp();
  OrderState onDelivered();
}

interface DeliveryAssignmentStrategy {
  DeliveryPartner selectPartner(Order order, List<DeliveryPartner> candidates);
}

class OrderService {
  Order placeOrder(Customer customer, Restaurant restaurant, Cart cart);
  void updateStatus(String orderId, StatusEvent event);
}

Ownership/validation notes: updateStatus() delegates to the order's current OrderState, which either returns the next state or rejects the event outright — OrderService itself never decides transition legality, only routes the event.

Q. Pseudocode — Critical Logic

Order.transitionTo(event):
  nextState = this.state.handle(event)   // OrderState decides legality
  if nextState is REJECTED: reject
  this.state = nextState
  orderStatusNotifier.notifyStatusChanged(this)

DeliveryDispatcher.assign(order):
  lock(availablePartnersPool)
  try:
    candidates = availablePartnersPool.nearRestaurant(order.restaurant)
    chosen = strategy.selectPartner(order, candidates)
    chosen.status = BUSY               // claim happens inside the same lock as selection
    return chosen
  finally:
    unlock(availablePartnersPool)

U. Testing Strategy

  • Happy path: an order moves through every lifecycle stage in order, with a notification fired at each transition.
  • Edge cases: a "delivered" event arriving while the order is still "placed" is rejected, not silently accepted or treated as skipping intermediate states.
  • Price-history tests: changing a MenuItem's price after an order was placed does not alter that order's already-recorded total.
  • Concurrency tests: two orders becoming ready for pickup at the same instant, with only one available delivery partner nearby, result in exactly one assignment and one order correctly left waiting for the next available partner.

W. Concurrency

Shared mutable state: the pool of currently-available delivery partners, particularly during a lunch-rush spike when many orders become ready for pickup at once.

  • Select-then-claim as one atomic step: choosing a candidate and marking them BUSY must happen inside the same lock — selecting a partner, releasing the lock, and only then claiming them reopens the exact double-assignment race Elevator's (Problem 11) hall-call dispatcher already had to solve, now with couriers instead of cars.
  • Out-of-order and duplicated status events: because status updates originate from external systems (a restaurant's POS, a delivery partner's phone) over unreliable networks, the OrderState machine — not the caller — must be the sole authority on whether an incoming event is legal from the order's current state, rejecting or safely no-op-ing anything that isn't.

X. Persistence

Orders and their line-item snapshots are durable, legally significant records — a receipt that changes after the fact or disappears on restart is unacceptable. Delivery-partner availability state is more transient and could reasonably live in a fast in-memory/cache layer, refreshed frequently, while the order and its price snapshot remain firmly repository-backed.

Z. Failure Scenarios

  • No delivery partner is available when an order becomes ready: the order should hold in a "ready, awaiting assignment" sub-state rather than the assignment call blocking or failing the whole order — a background retry re-attempts assignment as partners free up.
  • A delivery partner goes offline mid-delivery: the order needs an explicit stalled/escalation path (reassign to a new partner, alert support) rather than remaining silently in OUT_FOR_DELIVERY forever.

AA. Common Bad Designs

  • A live reference from Order to MenuItem for price instead of a frozen OrderLineItem snapshot — the defining mistake for this problem; see I.
  • Selecting a delivery partner and claiming them as two separate, unlocked steps — reopens the double-assignment race even with a well-designed Strategy.
  • A raw status enum checked with scattered if statements across the codebase instead of an OrderState hierarchy — invites illegal transitions to slip through in exactly the code path nobody remembered to update.
  • Trusting every incoming status event as legal and in-order — a flaky delivery-partner app can and will send duplicate or out-of-order events.

AB. Design Trade-Offs

DecisionOption AOption BRecommendation
Delivery assignment scopeOne partner per order (1:1)Batched delivery runs (one partner, multiple orders)Start 1:1 for correctness and clarity; batching is a real optimization but adds real complexity — defer until asked
Handling duplicate status eventsReject as an errorSilently no-op if already in the target stateNo-op for exact duplicates (idempotent), reject only for genuinely illegal transitions — distinguishing "already done" from "impossible" avoids false alarms from network retries

AC. Interviewer Evaluation

Strong signal: snapshotting price/name into the order unprompted; building the order lifecycle as a State machine rather than a raw enum; independently identifying the select-then-claim race for delivery-partner assignment; treating duplicate status events as an idempotency question, not just an error case.

Red flag: a live price reference to the catalog; a status field with scattered validation logic; unlocked select-then-claim assignment; assuming status events always arrive once, in order.

AD. Interview Simulation

Interviewer: Design a food delivery system like DoorDash.
Candidate: One thing I'd get right immediately: an order should snapshot each item's name and price at checkout time into an OrderLineItem, not hold a live reference to the restaurant's MenuItem. Otherwise a price change today silently rewrites a receipt from last week.
Interviewer: How do you model the order's progress from placed to delivered?
Candidate: As a State machine — each OrderState knows which events are legal from that specific status. That matters because status updates come from external systems like the restaurant's POS or the courier's phone, over unreliable networks, so I can't trust every incoming event is legal or even novel.
Interviewer: What happens when two orders are ready for pickup at the same moment and there's only one available courier?
Candidate: Selecting a candidate and claiming them has to be one atomic step under a lock — same fix as the elevator dispatcher's double-assignment problem. If I select first and claim later as two separate steps, both orders could pick the same courier before either claim commits.
Interviewer: The courier's app is flaky and sends the same "picked up" event three times.
Candidate: That should be a no-op, not an error — if the order's already past that state, a duplicate of an already-applied event is idempotent by definition. I'd only reject events that are genuinely illegal from the current state, like "delivered" arriving while still "placed."

A. Realistic Interview Prompt

"Design an in-process publish-subscribe / message queue system. Publishers publish messages to named topics; subscribers subscribe to topics and receive every message published to them. Support multiple independent subscribers per topic, and don't lose messages if a subscriber is temporarily slow."

B. Difficulty

Advanced + Concurrency. The publish/subscribe wiring itself is simple Observer — the difficulty is entirely in delivery semantics under concurrency and failure: backpressure when a subscriber falls behind, at-least-once delivery forcing idempotent consumers, and ordering guarantees that only hold within a partition, never globally.

C. What This Problem Tests

  • Recognizing Observer as the structural foundation, then correctly identifying everything beyond plain Observer that a real message queue actually needs
  • Push vs. pull delivery model trade-offs, and how each shifts where backpressure has to live
  • At-least-once delivery forcing idempotent consumers — the fourth occurrence of this exact lesson in this document, at its most explicit
  • The LLD/HLD boundary between an in-process event bus and a distributed broker (Kafka/Pulsar/SQS/SNS)

D. Requirements

Functional

  1. Publishers publish messages to a named Topic
  2. Subscribers subscribe/unsubscribe to a topic and receive every message published after subscribing
  3. Support multiple independent subscribers per topic, each processing at its own pace
  4. A slow or temporarily unavailable subscriber must not lose messages or block other subscribers
  5. Optionally: partition a topic so that ordering is guaranteed within a partition, and support a dead-letter queue for messages a subscriber repeatedly fails to process

Non-Functional

  • At-least-once delivery — a message may be redelivered after a failure, so consumers must be idempotent
  • Backpressure: an unbounded queue per slow subscriber risks unbounded memory growth; the system needs an explicit overflow policy
  • No global message ordering guarantee across the whole topic — only within a partition, if partitioning is used

F. Assumptions

  • Confirmed: named topics; multiple independent subscribers; a slow subscriber must not block others or silently lose messages.
  • Assumption: push model with a per-subscriber bounded queue — the broker delivers proactively, but each subscriber's own queue absorbs bursts up to a configured limit, at which point the chosen OverflowPolicy kicks in.
  • Assumption: at-least-once delivery, which means every subscriber's message handler must be idempotent — duplicate delivery after a retry is expected, not exceptional.
  • Assumption: ordering is guaranteed only within a partition (if the topic is partitioned by a key); across partitions or across a non-partitioned topic's independent subscribers, no ordering guarantee is made or needed.

I. Class Relationships

  • Observer as the foundational pattern: a Topic maintaining a list of Subscribers and notifying them on publish() is exactly the Observer pattern — the same structural idea already used for Ride-Sharing's ride-status notifications (Problem 5), Notification System's event triggers (Problem 7), and Coffee Machine's optional low-inventory alerts (Problem 8). This problem is what all three of those generalize toward: Observer stops being "a hook" and becomes the entire product.
  • Where plain Observer stops being enough: naive Observer calls every subscriber synchronously and in-line with publish(), which means one slow subscriber blocks the publisher and every other subscriber. The fix is Subscription — each subscriber gets its own bounded queue and its own consumption thread/loop, decoupling "message was published" from "this particular subscriber has processed it yet."
  • Strategy: OverflowPolicy (drop-oldest, drop-newest, block-publisher) is a mutually exclusive, swappable backpressure choice — the same shape as Problem 6's async-appender overflow decision, applied here per-subscriber instead of per-logger.
  • Why not a Bridge for delivery-model × persistence: it might seem like "push vs. pull" and "in-memory vs. persisted" are two independent dimensions worth a Bridge, but in practice the delivery model is a fixed architectural decision made once (see F), not something that varies per-topic at runtime — introducing Bridge here would mirror Problem 7's rejected category×channel Bridge for a dimension that, in this design, never actually needs independent runtime variation.

O. Design Evolution

  • V1: plain Observer — Topic.publish() calls every subscriber synchronously, in-line, no queueing.
  • V2: extract Subscription with a per-subscriber queue and a background consumption loop, once a slow subscriber is shown to block everyone else.
  • V3: add OverflowPolicy once an unbounded queue is shown to risk unbounded memory growth.
  • V4: add ack/retry and a DeadLetterQueue once at-least-once delivery and consumer idempotency become explicit requirements.
  • V5: add Partition once per-key ordering is requested.
  • V6: discuss (but do not necessarily build) the migration path to a distributed broker.

What stays stable: Broker.publish()/subscribe() signatures and the Subscriber.onMessage() contract. Backpressure, retry, and partitioning are all additive layers around Subscription, never changes to the subscriber-facing interface.

P. API / Interface Design

interface Subscriber {
  void onMessage(Message message);
}

interface OverflowPolicy {
  void onOverflow(Subscription subscription, Message incoming);
}

class Broker {
  Topic createTopic(String name);
  void publish(String topicName, Message message);
  Subscription subscribe(String topicName, Subscriber subscriber, OverflowPolicy policy);
  void unsubscribe(Subscription subscription);
}

class Subscription {
  void ack(String messageId);
  void nack(String messageId);   // triggers redelivery, up to a retry limit, then dead-letter
}

Ownership/validation notes: subscribe() returns a Subscription handle rather than requiring the caller to track topic/subscriber pairs manually — acking/nacking flows entirely through that handle, keeping the retry/dead-letter bookkeeping out of the subscriber's own code.

Q. Pseudocode — Critical Logic

Topic.publish(message):
  for subscription in this.subscriptions:
    if not subscription.queue.tryEnqueue(message):     // bounded queue full
      subscription.overflowPolicy.onOverflow(subscription, message)

Subscription.consumeLoop():                             // one per subscriber, background thread
  while running:
    message = this.queue.take()
    try:
      this.subscriber.onMessage(message)                // must be idempotent — may be a redelivery
      this.ack(message.id)
    catch:
      this.nack(message.id)

Subscription.nack(messageId):
  attempts = this.retryCount.increment(messageId)
  if attempts > MAX_RETRIES:
    this.deadLetterQueue.add(message, reason="retry exhausted")
  else:
    this.queue.tryEnqueue(message)   // redeliver — subscriber will see this message again

U. Testing Strategy

  • Happy path: publish → every current subscriber eventually receives and acks the message exactly once under normal conditions.
  • Edge cases: a subscriber that unsubscribes mid-delivery must not receive messages published after unsubscribing; a subscriber added after a message was published must not receive that earlier message (no replay unless explicitly designed for).
  • Backpressure tests: filling one subscriber's queue must trigger its OverflowPolicy without affecting any other subscriber's delivery.
  • Idempotency tests: deliberately redeliver a message (simulating a retry) and assert the subscriber's handler produces the same end state as a single delivery — this is the test that actually validates the at-least-once contract, not just that redelivery happens.
  • Ordering tests: messages with the same partition key arrive in publish order; messages with different keys make no ordering claim relative to each other.

W. Concurrency

Shared mutable state: each Topic's subscriber list; each Subscription's queue and retry-count map.

  • Push model shifts backpressure to the subscriber's own queue: since the broker actively delivers, an unbounded queue is the actual risk — bounding it and defining an explicit OverflowPolicy is not optional polish, it's the core non-functional requirement.
  • At-least-once delivery is a concurrency-adjacent correctness requirement, not just a retry detail: because a message can be redelivered after a failure (or after a crash-and-restart before an ack was recorded), subscriber handlers must be idempotent — the same lesson as Splitwise's settle-up, Ride-Sharing's ride-accept, and Notification System's dedupe, now at its most explicit because retries are the entire point of this system rather than an edge case within it.
  • Partition-level, not topic-level, ordering: guaranteeing global order across a topic would require serializing all publishes through one lock, killing throughput; guaranteeing it only within a partition (keyed messages routed to the same partition, processed in order there) is the realistic, scalable guarantee — the same trade-off real systems like Kafka make.

X. Persistence

If durability across a restart is required, messages need to be written to a log before being acknowledged as published (write-ahead, same idea as a database's commit log) — otherwise an in-memory-only queue loses everything on a crash. This document treats persistence as an explicit, named trade-off rather than assuming it for free: an in-memory version is a legitimate, simpler answer if the round doesn't ask for restart-survival.

Z. Failure Scenarios

  • Subscriber crashes mid-processing, after dequeue but before ack: the message must be considered undelivered and redelivered — this is precisely what makes at-least-once (not exactly-once) the honest guarantee without a persisted, transactional ack log.
  • Publisher publishes faster than a subscriber can ever consume, indefinitely: the bounded queue and OverflowPolicy are what prevent this from becoming an unbounded memory leak — worth stating that some overflow policy will always eventually apply under sustained overload, it's not a corner case.
  • A message repeatedly fails processing: without a retry limit and dead-letter queue, it would be redelivered forever, permanently blocking that subscriber's queue behind it — the dead-letter queue exists specifically to prevent one poison message from starving everything behind it.

AA. Common Bad Designs

  • Synchronous, in-line subscriber calls directly inside publish() — one slow subscriber blocks the publisher and every other subscriber, defeating the entire point of decoupling.
  • An unbounded queue per subscriber — "solves" backpressure by deferring the problem to an eventual out-of-memory crash.
  • Assuming exactly-once delivery is free — without a persisted, transactional ack protocol, "exactly-once" is usually actually at-least-once with un-idempotent consumers quietly double-processing.
  • Global ordering assumed across an entire topic — either silently broken under concurrency, or achieved only by serializing everything through one lock and destroying throughput.

AB. Design Trade-Offs

DecisionOption AOption BRecommendation
Delivery modelPush (broker delivers proactively)Pull (subscriber polls/fetches)Push is simpler for low-latency fan-out with few subscribers; pull scales better for many slow/bursty consumers since each controls its own rate — state which one and why rather than defaulting silently

AC. Interviewer Evaluation

Strong signal: naming Observer as the structural foundation immediately, then unprompted identifying its limits (synchronous blocking, no backpressure) and fixing them with per-subscriber queues and an explicit overflow policy; independently raising idempotent-consumer requirements once at-least-once delivery is confirmed; correctly scoping ordering to per-partition rather than claiming a global guarantee.

Red flag: calling subscriber.onMessage() synchronously inside publish() as the final design; an unbounded queue with no stated overflow policy; claiming "exactly-once" delivery without a persisted ack protocol to back it up; assuming global ordering without acknowledging the cost.

AD. Interview Simulation

Interviewer: Design a publish-subscribe system.
Candidate: At its core this is Observer — a Topic holds a list of subscribers and notifies them on publish. But plain Observer calls every subscriber synchronously, so one slow subscriber would block the publisher and everyone else. I'd give each subscriber its own bounded queue and background consumption loop instead.
Interviewer: What happens when that queue fills up?
Candidate: That's a backpressure policy decision, not something to hardcode — I'd make it a Strategy, OverflowPolicy, so drop-oldest, drop-newest, or block-the-publisher are all swappable rather than baked in.
Interviewer: Can a message be delivered twice?
Candidate: Yes, under at-least-once delivery — if a subscriber crashes after dequeuing but before acking, it gets redelivered. That means subscriber handlers need to be idempotent; the broker can't make that guarantee for them by itself without a much more expensive exactly-once protocol.
Interviewer: Does this guarantee message order?
Candidate: Only within a partition, if the topic is partitioned by key. Guaranteeing order across the whole topic would mean serializing every publish through one lock, which kills throughput for no benefit if the messages weren't causally related anyway.

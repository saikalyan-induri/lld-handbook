A. Realistic Interview Prompt

"Design a parking lot system. It should support multiple vehicle types and multiple spot types, assign a spot when a vehicle enters, generate a ticket, and compute a fee when the vehicle leaves. Assume it can have multiple floors."

Note what is not specified: the vehicle-to-spot matching rule, the pricing rule, single vs. multiple entrances. A strong candidate surfaces these in section E before writing a single class.

B. Difficulty

Intermediate, escalating to Advanced + Concurrency once the interviewer adds multiple simultaneous entrances (a very common follow-up). Single-floor/single-entrance is a clean intermediate OOD test: enough entities and changing behavior (pricing, allocation, vehicle types) to test abstraction skill, but no distributed-systems concerns.

C. What This Problem Tests

  • Abstraction — separating "vehicle" and "spot" from their concrete subtypes
  • Composition over inheritance (Lot has Floors has Spots — not "is-a")
  • Strategy pattern for allocation and pricing — only once justified by a requirement
  • Open/Closed Principle — adding a vehicle type or pricing rule without touching existing classes
  • Facade pattern for a clean external API
  • Concurrency reasoning once multiple entrances are introduced

D. Requirements

Functional

  1. Support multiple vehicle types (motorcycle, car, bus/truck at minimum)
  2. Support multiple spot types/sizes with a compatibility rule between vehicle and spot
  3. Assign an available compatible spot on entry; reject entry if none available
  4. Issue a ticket at entry (unique ID, entry time, assigned spot)
  5. On exit, validate the ticket, compute a fee based on duration, free the spot
  6. Support multiple floors
  7. Track real-time availability, ideally per spot type

Non-Functional

  • Extensibility — new vehicle types, spot types, pricing rules should not require touching existing classes
  • Correctness under concurrent entries — two vehicles must never be assigned the same spot
  • Interview-scale latency (not "millions of cars/sec" — don't over-engineer)
  • Out of scope by default: physical hardware (gates/cameras), payment gateway integration, reservations — unless the interviewer asks

F. Assumptions

  • Confirmed (from prompt): multiple vehicle types, multiple spot types, multi-floor, ticket + fee-on-exit flow.
  • Assumption: matching is size-based (MOTORCYCLE < COMPACT < LARGE) — a spot fits any vehicle at or below its size. Generalizes better than 1:1 type mapping.
  • Assumption: single entry/exit path in the base design (v1–v4); concurrency is introduced explicitly in v6, mirroring how interviewers actually escalate this problem.
  • Assumption: pricing is hourly, rounded up, size-dependent — modeled as a pluggable strategy from the start since the interviewer confirmed it "could change."
  • Assumption: no reservations, no payment gateway, no hardware modeling in the base design — explicit follow-ups (section V), not baked in prematurely.
  • Assumption: in-memory state; persistence discussed as an extension (section X).

I. Class Relationships

  • Composition: ParkingLot owns Floors; Floor owns ParkingSpots. A spot cannot outlive its floor conceptually — composition, not aggregation.
  • Inheritance: Vehicle → Motorcycle/Car/Bus. Kept shallow — only diverges on data (size), not behavior, so it stays justified rather than becoming a taxonomy for its own sake.
  • Dependency: ParkingLot → SpotAllocator and ParkingLot → FeeStrategy — both injected interfaces, not concrete classes, so the allocation/pricing algorithm can be swapped without touching ParkingLot.
  • Association: Ticket → Vehicle, Ticket → ParkingSpot — a ticket references them but doesn't own their lifecycle.
  • Why composition over inheritance for Floor/Spot? A floor is not "a kind of" spot collection with special behavior — it's a container. Modeling it as inheritance would force artificial subclassing just to change floor count, which is a runtime configuration concern, not a type concern.

Explicitly avoided: Singleton for ParkingLot. Several source implementations default to it "because there's only one lot," but that's an application-wiring decision (create one instance and pass it around), not a class-design constraint — Singleton would make the class untestable (can't spin up two lots in unit tests) for no real benefit.

O. Design Evolution

  • V1 — Single floor, one vehicle type: ParkingLot directly holds a list of spots.
  • V2 — Multiple vehicle types + spot types: introduce Vehicle/ParkingSpot abstractions and a size-matching rule.
  • V3 — Multiple floors: introduce Floor as a composition layer; ParkingLot now iterates floors instead of a flat spot list.
  • V4 — Pricing varies: extract FeeStrategy; ParkingLot stops computing fees itself.
  • V5 — Allocation policy varies (nearest-spot, load balancing): extract SpotAllocator; Floor stops deciding "the" spot alone.
  • V6 — Concurrent entrances: spot reservation becomes an atomic operation (lock or CAS on the spot/floor); ParkingLot's public API signature doesn't change — only the internals of allocation gain synchronization.

What stays stable across all versions: the ParkingLot.parkVehicle()/unparkVehicle() facade signature. That stability is the payoff of extracting SpotAllocator and FeeStrategy early — callers never notice the internal evolution.

function park(vehicle) {
  const size = vehicle.getSize();
  const spot = allocator.allocate(size);        // must be atomic — see W. Concurrency
  if (spot === null) throw new Error('NoAvailableSpotException');
  spot.occupy(vehicle);
  const ticket = Ticket.create(vehicle, spot, now());
  return ticket;
}

function unpark(ticket) {
  if (ticket.status !== ACTIVE) throw new Error('InvalidTicketException');
  ticket.close(now());
  const fee = feeStrategy.calculate(ticket);
  ticket.spot.vacate();
  return fee;
}
function park(vehicle: Vehicle): Ticket {
  const size: VehicleSize = vehicle.getSize();
  const spot: ParkingSpot | null = allocator.allocate(size);   // must be atomic — see W. Concurrency
  if (spot === null) throw new Error('NoAvailableSpotException');
  spot.occupy(vehicle);
  const ticket: Ticket = Ticket.create(vehicle, spot, now());
  return ticket;
}

function unpark(ticket: Ticket): Fee {
  if (ticket.status !== ACTIVE) throw new Error('InvalidTicketException');
  ticket.close(now());
  const fee: Fee = feeStrategy.calculate(ticket);
  ticket.spot.vacate();
  return fee;
}

U. Testing Strategy

  • Happy path: park a car, get a ticket, unpark, get a correct fee.
  • Edge cases: lot exactly full; vehicle exactly at a spot's size boundary; zero-duration parking (entry==exit time).
  • Invalid input: unpark with an unknown ticket ID; unpark with an already-closed ticket; park a vehicle type with no compatible spot anywhere.
  • Failure scenarios: allocator returns a spot that gets raced by another thread (see W); fee strategy misconfigured (negative/zero rate).
  • Concurrency tests: N threads racing to park when only 1 spot remains — exactly one must succeed, the rest must get NoAvailableSpotException, never a double-allocation.

W. Concurrency

Shared mutable state: the pool of available spots (per floor, per size). Two threads calling allocate() concurrently for the last spot of a size is the canonical race.

  • Critical section: "check spot is free" + "mark it occupied" must be a single atomic step — never two separate steps a thread could be pre-empted between.
  • Pessimistic approach: a mutex per floor (or per size-bucket) guarding the check-and-occupy. Simple, safe, some contention under heavy concurrent entry.
  • Optimistic approach: model spot state as an atomic (e.g. std::atomic<bool> or a CAS-based state field) and use compare-and-swap to claim a spot — no lock held, but requires careful retry logic if CAS fails.
  • Lock granularity trade-off: one global lock on the whole lot is simplest but serializes all entries lot-wide (bad under load); per-spot atomics give maximum parallelism but more code complexity.
  • Idempotency: if a client retries a park request after a timeout (not knowing if it succeeded), the system must not double-allocate — this argues for the caller supplying an idempotency key, or the atomic claim being the only side effect that matters.
  • Deadlock avoidance: if a design ever needs to lock two spots at once (rare here — parking doesn't naturally need it), always acquire locks in a consistent global order (e.g., by spot ID) to avoid circular wait.

X. Persistence

If the lot must survive a restart: ParkingSpot, Floor, and Ticket become persistent entities with durable IDs (not just in-memory object references). A TicketRepository/SpotRepository abstraction replaces direct in-memory maps — same interface shape, different backing store. Occupying a spot becomes a transaction (or an optimistic-locking update with a version column) rather than a plain in-memory mutation, so two processes can't both "win" the same spot across a crash/restart boundary. Ticket IDs should be generated in a way that's safe across restarts (UUID, not an in-memory counter).

Y. Scaling Boundary

LayerWhat Belongs Here
LLD (this document)Object relationships, responsibilities, APIs, in-process state, patterns for one lot

Z. Failure Scenarios

  • Duplicate exit request: ticket already CLOSED — second unparkVehicle call must be rejected, not double-charge.
  • Timeout mid-park: client doesn't get the ticket response but the spot was actually claimed — client retry must not double-allocate (idempotency key or "check if this plate already has an active ticket" guard).
  • Crash between "spot occupied" and "ticket created": reconciliation on restart should treat "occupied but no matching ticket" as an anomaly to flag, not silently trust.
  • External payment failure at exit: spot should not be released until payment is confirmed (or a grace/retry policy is defined) — otherwise a car could be double-billed or the spot double-allocated while the driver is still physically parked.

AA. Common Bad Designs

  • One giant ParkingLot god class doing allocation + pricing + payment + ticket printing. Looks reasonable early (fewer files!) but every new requirement means editing the same massive class — violates SRP and OCP simultaneously. Fix: extract SpotAllocator and FeeStrategy as soon as either shows signs of variability.
  • Singleton everywhere (ParkingLot, SpotAllocator, FeeStrategy all singletons). Looks like "there's only one of these in production" — but makes unit testing (need 2 lots side by side) and swapping strategies at runtime awkward. Fix: single instances via dependency injection at the application-wiring layer, not baked into the class itself.
  • Strategy pattern for every tiny behavior (a strategy interface for "how to format a ticket ID," for instance). Looks thorough, but adds indirection with no variability to justify it. Fix: only introduce a Strategy when there's a real, stated reason it needs to vary.
  • Type-string switch statements (if vehicle.type == "car") instead of polymorphism. Looks quick to write, but every new vehicle type means hunting down every switch statement across the codebase. Fix: polymorphic getSize()/behavior on the Vehicle hierarchy itself.

AC. Interviewer Evaluation

  • Weak candidate: jumps straight to code; one big class; hardcodes vehicle types with if/else; never asks a clarifying question.
  • Average candidate: asks 1–2 clarifying questions; produces a reasonable class split (Vehicle, Spot, Ticket, Lot) but pricing/allocation logic is still inline inside ParkingLot.
  • Strong candidate: asks clarifying questions up front; extracts FeeStrategy/SpotAllocator proactively because they identify pricing/allocation as "likely to change"; discusses trade-offs verbally without prompting.
  • Exceptional candidate: does all of the above, then anticipates the concurrency follow-up before being asked ("I'll note that allocate-and-occupy needs to be atomic once we have multiple entrances"), and can articulate exactly where the LLD boundary ends and HLD begins if pushed on scale.

AD. Interview Simulation

Interviewer: Design a parking lot system.
Candidate: Before I start — what vehicle types and spot types should I support, and can those grow over time?
Interviewer: Assume motorcycles, cars, and buses, and yes, more types could be added later.
Candidate: Then I'll model matching by a VehicleSize concept rather than exact type-to-type pairs, so new vehicle types don't require new spot logic.
Interviewer: Good. Assume it's multi-floor.
Candidate: I'll introduce a Floor that composes ParkingSpots, sitting between the top-level ParkingLot and individual spots.
Interviewer: Pricing rules change frequently — think peak hours, promotions.
Candidate: I'll isolate that behind a FeeStrategy interface so ParkingLot never needs to change when pricing rules change — that's Open/Closed in practice, not just a buzzword.
Interviewer: Now, two cars arrive at the exact same time for the last available compact spot.
Candidate: The allocate-and-occupy step has to be atomic. I'd guard it with a lock scoped to the spot pool being checked — or use an atomic compare-and-swap on the spot's state if I want to avoid blocking. I'd pick the lock first for clarity, and mention the CAS alternative if pushed on throughput.
Interviewer: What if the payment provider fails after the car has already left?
Candidate: That's a case for not releasing the spot until payment is confirmed, plus making the fee-charge operation idempotent so a retry after a timeout doesn't double-charge.
Interviewer: Last one — how would this look if we had to support a thousand lots citywide?
Candidate: At that point it crosses from LLD into HLD — I'd keep this exact object model per lot, but partition storage by lot ID and put a service layer with a database and cache in front of it. The class design here doesn't need to change; only where it runs does.

A. Realistic Interview Prompt

"Design the software for an ATM. Support card insertion, PIN authentication, balance inquiry, cash withdrawal, and deposit. Cash is dispensed as a mix of denominations."

B. Difficulty

Intermediate. The session flow (card → PIN → operation → dispense → eject) is a clean, bounded State machine; the two things that actually separate strong answers are denomination-splitting for cash dispensing and the balance-race that appears the instant more than one channel (a second ATM, or online banking) can touch the same account.

C. What This Problem Tests

  • Modeling the ATM session itself as a State machine with real illegal-transition guarantees (no withdrawal before PIN verification)
  • Chain of Responsibility for greedy denomination dispensing — a textbook fit that most candidates reach for a hand-rolled loop instead
  • Recognizing withdrawal as the same check-then-act balance race seen in every other resource-contention problem in this document, now with real money at stake
  • Correctly drawing the boundary between the ATM (a client) and the bank (the system of record for balances and authentication)

D. Requirements

Functional

  1. Accept a card, prompt for and verify a PIN against the bank
  2. Support balance inquiry, cash withdrawal, deposit, and transfer
  3. Dispense withdrawn cash as an optimal mix of available denominations
  4. Eject the card at the end of a session or on cancellation
  5. Track the ATM's own cash inventory per denomination and refuse withdrawals it cannot physically fulfill

Non-Functional

  • A withdrawal must never debit an account without successfully dispensing the cash, and must never dispense cash without a successful debit — the two must be atomic as a pair
  • Concurrent withdrawal attempts against the same account (from this ATM or another channel) must not both succeed against an insufficient balance

F. Assumptions

  • Confirmed: card + PIN auth, balance inquiry, withdrawal, deposit, denomination-aware dispensing.
  • Assumption: the bank is a separate system of record reachable via a BankServer interface — the ATM is a client that authenticates and requests debits/credits, never the authority on an account's true balance.
  • Assumption: the ATM tracks its own physical cash inventory locally (it, not the bank, knows how many $20s are left in its own tray).
  • Assumption: transfer, if in scope, is treated as a withdrawal-equivalent debit paired with a credit to another account, reusing the same atomicity requirement.

I. Class Relationships

  • State (headline) for the session: a withdrawal action attempted from IdleState (no card yet) or CardInsertedState (PIN not yet verified) is structurally unavailable, not a runtime if (!authenticated) reject scattered across every transaction method.
  • Chain of Responsibility for dispensing: a CashDispenser for $270 hands the request to a Hundred-handler (dispenses two $100s, passes $70 down), then a Fifty-handler (dispenses one $50, passes $20 down), then a Twenty-handler (dispenses one $20, passes $0 down, chain stops). Each handler only knows its own denomination and how to pass a remainder along — a new denomination is a new link, not a change to a central dispensing algorithm.
  • Strategy for transaction type: withdrawal, deposit, balance inquiry, and transfer are mutually exclusive alternatives selected once per session — exactly Strategy's shape, resolved via a small Factory off the customer's menu selection, the same Factory-over-Strategy shape used for Rate Limiter's algorithm selection and Notification System's channel resolution.
  • Why the ATM is not the source of truth for balance: the ATM's own ATM class tracks only its physical cash tray; every debit/credit is delegated to BankServer, which is the actual system of record — this boundary is what makes the account-balance race in W a real, correctly-scoped concern rather than something the ATM could ever fix unilaterally.

Explicitly avoided: a hand-rolled greedy loop for dispensing inline in ATM — it works but re-implements exactly what Chain of Responsibility already models cleanly, and can't be extended with a new denomination without editing the loop itself.

O. Design Evolution

  • V1: one ATM class, a mode string, inline greedy dispensing loop.
  • V2: extract real ATMState classes once illegal-action rejection needs to be airtight, not just conditionally checked.
  • V3: extract the DenominationHandler chain once a second denomination or a "minimize note count" requirement makes the inline loop unwieldy.
  • V4: extract Transaction as Strategy once deposit/transfer are added alongside withdrawal.
  • V5: add the atomic debit-then-dispense sequencing (see W) once multi-channel access to the same account is in scope.

What stays stable: the ATMController's session API. New denominations and transaction types are pure additions.

P. API / Interface Design

interface ATMState {
  void insertCard(Card card);
  void enterPin(String pin);
  void selectTransaction(Transaction t);
}

interface Transaction {
  TransactionResult execute(Account account, BankServer bank);
}

class ATM {
  void dispense(int amount);            // delegates to CashDispenser chain
  void setState(ATMState state);
}

class BankServer {
  AuthResult authenticate(Card card, String pin);
  DebitResult debit(Account account, int amount);   // must be atomic at the bank
  void credit(Account account, int amount);
}

Ownership/validation notes: WithdrawTransaction.execute() calls bank.debit() first and only calls atm.dispense() if the debit succeeds — never the reverse order, so a dispensing failure after a successful debit is a recoverable "credit back" case, while a dispensing-before-debit order would risk giving out cash with no guaranteed recovery if the debit then failed.

Q. Pseudocode — Critical Logic

WithdrawTransaction.execute(account, bank):
  result = bank.debit(account, amount)     // atomic at the bank: check-and-deduct as one op
  if not result.success: return INSUFFICIENT_FUNDS
  try:
    atm.dispense(amount)
  catch DispenseFailure:
    bank.credit(account, amount)           // compensating action — never leave a debit stranded
    return DISPENSE_FAILED
  return SUCCESS

DenominationHandler.handle(amount):
  count = min(amount / this.value, this.availableCount)
  dispense(count, this.value)
  remainder = amount - (count * this.value)
  if remainder > 0 and next != null: next.handle(remainder)
  else if remainder > 0: throw InsufficientCashException

U. Testing Strategy

  • Happy path: a withdrawal amount is split into the fewest notes possible given current tray inventory.
  • Edge cases: a withdrawal exceeding the ATM's total physical cash is rejected before any debit occurs; a withdrawal amount not representable by available denominations (e.g. $15 with only $20/$50/$100 in the tray) is rejected cleanly.
  • Atomicity tests: a simulated dispense failure after a successful debit triggers the compensating credit — the account never ends up debited with no cash received.
  • Concurrency tests: two simultaneous withdrawal attempts against an account with only enough balance for one must result in exactly one success and one clean rejection, never both succeeding.

W. Concurrency

Shared mutable state: the account balance at the bank (shared across every ATM and every other channel touching that account); the ATM's own local cash tray (shared only across concurrent sessions on that one machine, a much smaller-scoped concern).

  • The check-then-act balance race, once more: "read balance, confirm sufficient, then debit" as two separate steps is exactly the same bug shape as Parking Lot's spot occupation and Splitwise's ledger writes, now scoped to money. bank.debit() must be a single atomic compare-and-deduct operation at the bank (a conditional update, not read-then-write), so two concurrent withdrawal requests against a balance that can satisfy only one of them result in exactly one success.
  • The ATM's local cash tray is a much smaller-scoped lock — it only needs to serialize concurrent sessions on the same physical machine, and is irrelevant to the cross-channel account race above.
  • Debit-then-dispense ordering (see P/Q) is what keeps a partial failure recoverable — the compensating credit only has to reverse a debit, never has to "claw back" cash already physically dispensed.

X. Persistence

The ATM itself is stateless across sessions beyond its physical cash inventory — every account/transaction fact of record lives at the bank. Locally, only a session-level transaction log (for reconciliation and dispute resolution) needs to persist, behind a simple repository interface, independent of ATMState or BankServer.

Z. Failure Scenarios

  • Network failure between debit success and dispense confirmation: without a clear acknowledgment, this is the same ambiguous-outcome problem every payment system faces — the design should favor a reconciliation job that reviews debits with no matching dispense record, rather than assuming success or blindly retrying (which could double-dispense).
  • Card left in the machine / customer walks away mid-session: a timeout transitions any active state back toward IdleState and ejects the card automatically, rather than holding the session open indefinitely.
  • Tray physically empty for a denomination the chain expected: the handler's availableCount check (not just the logical count from the last known inventory) is what's authoritative — a hardware-reported count, not an assumed one.

AA. Common Bad Designs

  • One ATM god-class with a mode field and every method starting with an if (mode != AUTHENTICATED) return guard — the State-machine violation seen across this entire document.
  • A hand-rolled greedy dispensing loop inline in the withdrawal method instead of Chain of Responsibility — works, but can't add a denomination without touching the loop.
  • Dispensing cash before confirming the debit succeeded — the reverse of the safe ordering in Q, and the harder failure mode to recover from.
  • Treating the ATM's local balance cache as authoritative instead of always deferring to BankServer — reintroduces the exact race W exists to prevent.

AB. Design Trade-Offs

DecisionOption AOption BRecommendation
Dispensing algorithmGreedy largest-denomination-first (Chain of Responsibility)DP-based minimum-notes solverGreedy — real ATM denomination sets are chosen specifically to make greedy optimal, and it's dramatically simpler to implement and reason about
Debit/dispense orderingDebit first, then dispense, with compensating credit on dispense failureDispense first, then debitDebit first — a failed compensating credit is a bank-side accounting fix; a failure after cash has already left the machine is unrecoverable

AC. Interviewer Evaluation

Strong signal: proposing State for the session unprompted; reaching for Chain of Responsibility for dispensing rather than a hand-rolled loop; independently naming the debit-before-dispense ordering and the compensating-credit recovery path; recognizing the balance race as the same shape already seen in Parking Lot/Splitwise.

Red flag: a mode-flag ATM class; a hardcoded dispensing loop with no extension point; dispensing before confirming the debit; treating the ATM as the account's source of truth.

AD. Interview Simulation

Interviewer: Design an ATM.
Candidate: The session itself is a State machine — idle, card-inserted, authenticated, dispensing, out-of-service — so a withdrawal attempted before PIN verification is structurally impossible, not just conditionally rejected.
Interviewer: How do you dispense $270 as physical notes?
Candidate: Chain of Responsibility — a $100 handler takes as many $100s as it can and passes the remainder to the $50 handler, and so on down to $1. Adding a new denomination is a new link in the chain, not a change to a central dispensing method.
Interviewer: What if someone tries to withdraw from two ATMs at once with just enough balance for one withdrawal?
Candidate: That's the same check-then-act race as a parking spot or a shared ledger — the bank's debit has to be one atomic compare-and-deduct operation, not read-balance-then-write-balance as two steps, or both ATMs could see a sufficient balance and both succeed.
Interviewer: What if the debit succeeds but the cash fails to dispense?
Candidate: That's exactly why I debit before dispensing rather than the reverse — a dispense failure after a successful debit is recoverable with a compensating credit back to the account, whereas a debit failure after cash has already left the machine would not be recoverable at all.

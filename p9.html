A. Realistic Interview Prompt

"Design an in-memory file system supporting files and directories. Support creating, deleting, moving, reading, and writing files; listing directory contents; searching for files by name or extension; and computing disk usage for any directory."

B. Difficulty

Intermediate → Advanced. The tree structure itself is not hard — the difficulty is entirely in what a naive candidate bolts onto the base node type (every possible read-only operation, permission logic, locking) versus what a mature candidate keeps separate via Composite + Visitor + a disciplined locking protocol.

C. What This Problem Tests

  • Recognizing files and directories as a classic Composite — a directory holds children uniformly, whether they're files or more directories
  • ISP judgment: resisting the urge to add size(), search(), countFiles() etc. directly to the base node interface, and reaching for Visitor instead
  • Iterator design trade-offs when a directory's contents can change mid-traversal (fail-fast vs. snapshot)
  • Lock-ordering discipline for a cross-directory move() — the same multi-resource deadlock shape as Splitwise's multi-pair settle-up, applied to a tree instead of a ledger

D. Requirements

Functional

  1. Create/delete files and directories (deleting a non-empty directory requires an explicit recursive flag)
  2. Read/write file contents
  3. Move/rename a file or directory, including across different parent directories
  4. List a directory's immediate contents
  5. Search for files by name, extension, or size under a given subtree
  6. Compute total disk usage of any directory (recursive size)

Non-Functional

  • Concurrent reads must be safe and non-blocking against each other; a write must be exclusive against both other writes and reads to the same node
  • A move() must never deadlock against a concurrent move() elsewhere in the tree
  • A directory cannot be moved into its own subtree (no cycles)

F. Assumptions

  • Confirmed: in-memory tree of files and directories; CRUD, move, list, search, disk usage.
  • Assumption: single-process, multi-threaded access (not a distributed filesystem) — GFS/HDFS-style metadata services and chunk replication are explicitly out of scope (see Y).
  • Assumption: no symbolic or hard links — every node has exactly one parent, which is what makes "can't move a directory into its own descendant" a simple ancestry check rather than general cycle detection on an arbitrary graph.
  • Assumption: permissions, if present at all, are a simple owner-based check rather than full POSIX-style ACLs.

I. Class Relationships

  • Composite (headline): File and Directory both extend FileSystemNode; a Directory holds a uniform collection of FileSystemNode — client code walking the tree never needs an instanceof check or an isDirectory() boolean scattered through every call site. This is the direct cure for the most common naive design in this problem (see AA).
  • Why Visitor over methods on FileSystemNode: disk usage, search-by-extension, and count-files-under-subtree are all read-only aggregate operations, and there will always be another one an interviewer asks for next. Adding each as a new method on FileSystemNode (and its File/Directory overrides) violates ISP — every node is forced to implement every operation whether it's relevant or not, and the base interface grows without bound. A NodeVisitor with visitFile()/visitDirectory(), dispatched via a single stable accept(visitor) method, lets new read-only operations (DiskUsageVisitor, SearchVisitor) be added as entirely new classes with zero changes to FileSystemNode, File, or Directory — a direct OCP payoff.
  • Iterator: DirectoryIterator decouples "how children are traversed" from Directory's internal storage — see AB for the fail-fast-vs-snapshot policy trade-off this pattern forces into the open.
  • Why Proxy, not Decorator, for permission checks (if in scope): a permission-checking wrapper around FileSystemNode looks structurally identical to a Decorator, but the intent is different — Decorator composes additional behavior onto a base object (e.g. Problem 5's surge-pricing decorator adds a computation), while a permission check is access control: it decides whether the real call happens at all, not how to embellish its result. That's exactly what Proxy names. Calling it a Decorator would describe the shape correctly but the intent wrongly — worth stating explicitly if asked.

O. Design Evolution

  • V1: plain tree, no locking, isDirectory boolean and inline recursion for size/search.
  • V2: replace the boolean flag with real File/Directory subclasses under Composite once the inline instanceof branching starts spreading across call sites.
  • V3: extract NodeVisitor once a second read-only operation (search, after disk-usage) is requested — the point where hardcoding each as a new node method would start hurting.
  • V4: add DirectoryIterator with an explicit fail-fast-vs-snapshot decision.
  • V5: add per-node readers-writer locks and a canonical-path lock-ordering protocol for move().
  • V6: optional Proxy layer for permissions; pluggable StorageBackend for real persistence.

What stays stable: FileSystem's top-level API signatures. New aggregate operations are pure additions (new visitor classes); persistence and permissions slot in behind existing interfaces without touching File/Directory.

Ownership/validation notes: move() resolves both the source and destination parent directories, verifies the destination is not a descendant of the source (cycle check), then acquires both parents' locks in canonical-path order before mutating either — never partially detach a node without knowing the reattachment will succeed.

Q. Pseudocode — Critical Logic

FileSystem.move(source, destination):
  srcParent = resolveParent(source)
  destParent = resolveParent(destination)
  node = srcParent.getChild(source.lastSegment)

  if node is Directory and destination.isDescendantOf(source):
    throw IllegalMoveException("cannot move a directory into its own subtree")

  // lock ordering: always acquire in canonical-path order to prevent
  // an ABBA deadlock against a concurrent move() going the other direction
  (first, second) = orderByCanonicalPath(srcParent, destParent)
  lock(first); lock(second)
  try:
    srcParent.removeChild(node.name)
    node.parent = destParent
    destParent.addChild(node)
  finally:
    unlock(second); unlock(first)

void move(Path source, Path destination) throws IllegalMoveException {
  Directory srcParent = resolveParent(source);
  Directory destParent = resolveParent(destination);
  FileSystemNode node = srcParent.getChild(source.lastSegment());

  if (node instanceof Directory && destination.isDescendantOf(source)) {
    throw new IllegalMoveException("cannot move a directory into its own subtree");
  }

  // lock ordering: always acquire in canonical-path order to prevent
  // an ABBA deadlock against a concurrent move() going the other direction
  Directory[] ordered = orderByCanonicalPath(srcParent, destParent);
  Directory first = ordered[0], second = ordered[1];
  lock(first); lock(second);
  try {
    srcParent.removeChild(node.getName());
    node.setParent(destParent);
    destParent.addChild(node);
  } finally {
    unlock(second); unlock(first);
  }
}

void visitDirectory(Directory d) {
  long total = 0;
  for (FileSystemNode child : d.getChildren().values()) {
    child.accept(this);              // recurses; visitFile adds file.size directly
    total += this.lastSize;
  }
  this.lastSize = total;
}
void FileSystem::move(const Path& source, const Path& destination) {
  auto srcParent = resolveParent(source);
  auto destParent = resolveParent(destination);
  auto node = srcParent->getChild(source.lastSegment());

  if (std::dynamic_pointer_cast<Directory>(node) && destination.isDescendantOf(source)) {
    throw IllegalMoveException("cannot move a directory into its own subtree");   // throws IllegalMoveException
  }

  // lock ordering: always acquire in canonical-path order to prevent
  // an ABBA deadlock against a concurrent move() going the other direction
  auto [first, second] = orderByCanonicalPath(srcParent, destParent);
  lock(first); lock(second);
  try {
    srcParent->removeChild(node->name);
    node->parent = destParent;
    destParent->addChild(node);
  } catch (...) {
    unlock(second); unlock(first);
    throw;
  }
  unlock(second); unlock(first);
}

U. Testing Strategy

  • Happy path: create → write → read round-trips content exactly; list() reflects exactly the current children.
  • Edge cases: deleting a non-empty directory without the recursive flag is rejected; deleting an empty directory succeeds without it.
  • Cycle prevention: attempting to move a directory into its own descendant is rejected before any locks are acquired or any node is mutated.
  • Concurrency tests: two concurrent move() calls that would lock the same two directories in opposite orders must not deadlock (verifies the canonical-order fix actually works); many concurrent readers of the same file never block each other; a writer blocks and is blocked by both readers and other writers on that same node.
  • Iterator semantics: a directory mutated mid-iteration behaves according to whichever policy was chosen (fail-fast throws cleanly; snapshot silently reflects the pre-mutation state) — the test asserts the chosen policy, not "some" behavior.

W. Concurrency

Shared mutable state: every Directory's children map; every File's content.

  • Readers-writer lock per node: concurrent read()/list() calls proceed without blocking each other; a write(), addChild(), or removeChild() takes an exclusive lock.
  • Lock ordering for cross-directory move(): moving a node touches two directories (source parent, destination parent). Locking them in call order (source first, then destination) is exactly how two concurrent moves going in opposite directions deadlock — the same ABBA shape as Splitwise's multi-pair settle-up. The fix is identical in spirit: always acquire locks in one fixed global order (e.g. canonical path string comparison), regardless of which one is logically the "source" for a given call.
  • Cycle check happens before any lock is taken: validating that the destination isn't a descendant of the source is a pure read against the current tree shape; doing it first avoids holding locks during a check that might reject the whole operation anyway.

X. Persistence

The prompt is explicitly in-memory, but the design should not hardcode that assumption into File itself: a StorageBackend interface behind read()/write() (in-memory byte array today, real disk or blob-store tomorrow) keeps persistence swappable without touching the tree structure, Composite hierarchy, or any visitor — the same DIP boundary used for payment gateways and cache backends elsewhere in this document.

Z. Failure Scenarios

  • A node is deleted while a visitor is mid-traversal of that subtree: the fail-fast-vs-snapshot iterator policy (see AB) determines whether this throws cleanly or completes against a consistent pre-deletion view — either is acceptable, but it must be a deliberate choice, not undefined behavior.
  • `move()` fails partway (e.g. destination lock acquisition fails after the cycle check passed): the pseudocode in Q never detaches the node from its source until both locks are held, so a failure before that point leaves the tree untouched — no orphaned nodes.
  • Delete while a file handle is still open (POSIX-style unlink semantics): a reference-counted handle model means delete() unlinks the node from the directory tree immediately (it disappears from list()) but the underlying content isn't actually freed until the last open handle closes — the same "logically gone, physically pending" split real filesystems use.

AA. Common Bad Designs

  • A single Node class with an isDirectory boolean and scattered if/instanceof checks at every call site instead of Composite polymorphism — the single most common naive shape for this problem.
  • Every new query (size, search, count, checksum) added as a direct method on the base node interface — grows the interface without bound and violates ISP; this is exactly what Visitor exists to prevent.
  • A single global filesystem-wide lock — correct but needlessly serializes completely unrelated subtrees under any real load.
  • Locking move()'s two directories in call order instead of a fixed canonical order — passes every single-threaded test and deadlocks the first time two moves cross paths concurrently.

AB. Design Trade-Offs

AC. Interviewer Evaluation

Strong signal: reaching for Composite immediately and unprompted for the file/directory split; independently proposing Visitor once asked for a second read-only operation, with a clear ISP-based justification for why it's not just another node method; naming the lock-ordering fix for move() without being walked into the deadlock first.

Red flag: an isDirectory boolean surviving past the first design pass; adding every new query directly to the node interface; proposing a single global lock as the final answer rather than a deliberately simple starting point; not noticing the cycle risk in move() until explicitly prompted.

Candidate: Files and directories need to be treated uniformly by anything walking the tree, but a directory has children and a file doesn't — that's a textbook Composite: both extend a common FileSystemNode, and client code never needs to check which one it has.
Interviewer: Now add a way to compute total disk usage under any directory.
Candidate: I wouldn't add a size() method to every node type for this — there will always be another aggregate query after this one. I'd add a NodeVisitor interface and a DiskUsageVisitor implementation, dispatched through one stable accept() method on the nodes.
Interviewer: What about moving a file between two directories while other operations are happening concurrently?
Candidate: That needs locks on both the source and destination parent directories. If I lock them in call order, two concurrent moves crossing in opposite directions can deadlock — so I'd always acquire locks in a fixed canonical order, like comparing normalized path strings, regardless of which is logically the source.
Interviewer: What stops someone from moving a directory into its own subtree?
Candidate: An explicit ancestry check — is the destination a descendant of the source — done before any locks are taken, since it's a pure read that can reject the operation for free.

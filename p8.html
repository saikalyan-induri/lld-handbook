A. Realistic Interview Prompt

"Design a coffee vending machine. It offers several beverages, each requiring specific quantities of ingredients (water, milk, coffee, sugar). A user selects a beverage, pays, and the machine dispenses it — or rejects the request if ingredients are insufficient."

B. Difficulty

Beginner → Intermediate. Deliberately the smallest, most contained problem in this set — often used as a warm-up or as the "textbook State pattern" round, precisely because the machine's behavior really does change shape by state in a way that's hard to fake with a simple boolean flag.

C. What This Problem Tests

  • Whether a candidate reaches for the State pattern when a switch-on-status-field would clearly rot
  • Judgment about when not to add a pattern — Template Method looks tempting here and is a considered, deliberate rejection
  • Atomic ingredient reservation, the same check-then-act race shape as every resource-allocation problem in this set, at a much smaller scale
  • Strategy for payment methods without over-building a payments system

D. Requirements

Functional

  1. Offer several beverages, each with a fixed recipe (ingredient → required quantity)
  2. Let a user select a beverage and pay via cash or card
  3. Dispense the beverage if and only if all required ingredients are sufficiently stocked
  4. Reject the selection (and refund, if paid) if ingredients are insufficient
  5. Allow a technician to refill ingredients

Non-Functional

  • The machine must never dispense a beverage it can't fully complete (no half-made drinks)
  • Ingredient inventory must not go negative even if operations overlap (multi-slot machines)
  • Adding a new beverage must not require code changes beyond adding a recipe

F. Assumptions

  • Confirmed: fixed recipes; ingredient sufficiency check before dispensing; refill capability.
  • Assumption: a single shared ingredient hopper feeds potentially multiple brewing slots, making the ingredient-reservation race a real (if small-scale) concern rather than a purely academic one.
  • Assumption: payment is a simple PaymentStrategy (cash/card) that returns success/failure; actual card-processing internals are out of scope, matching Splitwise/Ride-Sharing's payment-gateway boundary.
  • Assumption: a failed mid-dispense attempt returns reserved ingredients to inventory and refunds payment — no half-charged, half-brewed outcomes.

I. Class Relationships

  • State: CoffeeMachine delegates every action to its current CoffeeMachineState object (Idle → Selecting → Dispensing → Idle, with OutOfStock and Cancelled as alternate branches) rather than an internal switch statement — the textbook GoF State example, and the cleanest fit for State in this entire document since the states genuinely change which actions are even legal, not just cosmetic labels.
  • Strategy: PaymentStrategy implementations (cash/card) are mutually exclusive alternatives, same shape as every other Strategy in this set.
  • Composition: a Beverage owns its Recipe; a Recipe has no meaning outside the beverage it describes.
  • Why Template Method was considered and rejected: every beverage's brewing steps are identical — check ingredients, reserve them, combine, dispense, commit inventory — and only the quantities differ, which is data (the Recipe), not behavior. Template Method exists to let subclasses override specific steps of an algorithm; here there is nothing for a subclass to override, so introducing a beverage-per-subclass hierarchy just to hang a shared method on would add a class hierarchy with zero actual variation in behavior. A single parameterized brew(recipe) method captures this correctly. This is the same class of judgment call as Coffee's sibling problems rejecting Bridge (Problem 7) or a second parallel Strategy (Problem 5's surge).

O. Design Evolution

  • V1: one beverage, no payment, dispense always succeeds if ingredients exist (simple boolean check).
  • V2: multiple beverages via Recipe data; still a boolean "status" field.
  • V3: replace the boolean/status field with a proper CoffeeMachineState hierarchy once illegal-action bugs start appearing (e.g. dispensing twice for one payment).
  • V4: extract PaymentStrategy; add refund-on-failure.
  • V5: atomic Ingredient.reserve()/release() for multi-slot safety.
  • V6: Observer-based low-inventory alerts; cancellation mid-selection.

What stays stable: CoffeeMachine.select()/pay()/dispense() signatures. New beverages are pure data additions; new payment methods and alerting are additive via existing interfaces.

P. API / Interface Design

interface CoffeeMachineState {
  void selectBeverage(CoffeeMachine ctx, Beverage b);
  void insertPayment(CoffeeMachine ctx, PaymentStrategy method, Money amount);
  void dispense(CoffeeMachine ctx);
  void cancel(CoffeeMachine ctx);
}

class CoffeeMachine {
  void select(Beverage b);      // Idle -> Selecting, or rejects if not Idle
  void pay(PaymentStrategy method, Money amount);  // Selecting -> Dispensing
  void dispenseNow();           // Dispensing -> Idle (or -> OutOfStock)
  void cancel();                // Selecting -> Idle, refunds if already paid
  void refill(Ingredient ing, int qty);  // technician action, any state
}

Ownership/validation notes: dispenseNow() reserves all required ingredients atomically before physically dispensing anything — if reservation fails partway (one ingredient insufficient), nothing is reserved and the machine transitions to OutOfStockState with a refund, never a partial drink.

Q. Pseudocode — Critical Logic

CoffeeMachine.dispenseNow():
  recipe = this.selectedBeverage.recipe
  reserved = []
  for (ingredient, qty) in recipe.requirements:
    if not ingredient.tryReserve(qty):        // atomic check-and-decrement
      for r in reserved: r.ingredient.release(r.qty)   // roll back partial reservation
      this.paymentMethod.refund(recipe.price)
      this.state = OutOfStockState
      return
    reserved.add((ingredient, qty))
  // all ingredients reserved successfully — safe to physically dispense
  dispenser.pour(recipe)
  this.state = IdleState

U. Testing Strategy

  • Happy path: sufficient ingredients, successful payment → beverage dispensed, inventory decremented by exactly the recipe amounts.
  • Edge cases: exactly-enough inventory (boundary), payment succeeds but one ingredient is insufficient (must refund, not dispense a partial drink).
  • Illegal transitions: calling dispenseNow() while still Idle (nothing selected/paid) must be rejected by the current state object, not silently no-op.
  • Concurrency tests: two concurrent dispense attempts on a shared, barely-sufficient ingredient — exactly one succeeds, the other cleanly falls back to OutOfStockState with a refund, inventory never goes negative.

W. Concurrency

Shared mutable state: each Ingredient's quantity, if the machine has multiple brewing slots sharing one hopper.

  • The same check-then-act race, at coffee-machine scale: two slots both check "is there enough milk?", both see yes, both proceed — and the hopper goes negative. The fix is identical in shape to Parking Lot and Ride-Sharing: make check-and-decrement one atomic operation (tryReserve), not a separate read then write.
  • Rollback on partial failure: if a recipe needs three ingredients and the third fails to reserve, the first two reservations must be released back — an all-or-nothing reservation, mirroring Splitwise's all-or-nothing expense mutation.
  • Single-slot machines need none of this: worth stating plainly that if the clarifying question in E reveals a single brewing unit, this entire section is a non-issue — don't over-engineer concurrency that the requirements don't actually call for.

X. Persistence

Minimal for this problem: ingredient inventory levels need to survive a machine restart/power cycle (a simple local persisted counter, updated on every reserve/refill), and a sales/dispense log is useful for a technician's restocking schedule but isn't a hard requirement unless the round asks for reporting.

Z. Failure Scenarios

  • Physical jam mid-dispense (after ingredients reserved, before pour completes): must release reserved ingredients and refund — never leave inventory permanently short for a drink that was never actually made.
  • Payment succeeds but dispensing then fails: refund is mandatory, not optional — same principle as Ride-Sharing's "trip happened, payment is separate" but inverted (here, payment happened, "trip" did not).
  • Power loss mid-transaction: on restart, any in-flight reservation should be treated as failed/rolled-back rather than assumed committed.

AA. Common Bad Designs

  • A single status string with scattered if checks everywhere instead of a real State pattern — works for two states, rots badly past three or four.
  • Check-then-decrement ingredient logic — fine on a single-slot machine, breaks the instant a second slot shares the hopper.
  • A beverage-subclass-per-drink hierarchy for brewing — over-applies Template Method to what's actually just data variation (see I, M).
  • Charging payment before confirming ingredient sufficiency — creates an avoidable refund path that a reserve-before-charge (or check-before-charge) ordering would prevent entirely.

AC. Interviewer Evaluation

  • Weak candidate: a status boolean, no separation between selection/payment/dispensing, dispenses without checking payment succeeded.
  • Average candidate: has recognizable State and Strategy usage but doesn't handle partial-failure refund/rollback.
  • Strong candidate: clean State machine, atomic ingredient reservation with rollback, correct payment/dispense ordering.
  • Exceptional candidate: all of the above, plus explicitly and correctly argues against Template Method for beverage variation, and scopes concurrency honestly (applying it only if multi-slot is actually in play).

AD. Interview Simulation

Interviewer: Design a coffee vending machine.
Candidate: The machine's behavior clearly depends on where it is in a flow — idle, selecting, dispensing — so I'd model that as a State pattern rather than a status flag, since the legal actions genuinely differ by state.
Interviewer: Would you make each beverage its own class, since they each brew differently?
Candidate: Actually no — every beverage follows the exact same steps: check ingredients, reserve them, combine, dispense. Only the quantities differ, and that's data, not behavior. I'd keep Recipe as a data object and use one shared brew() method rather than a beverage-subclass hierarchy with nothing to actually override.
Interviewer: What if the machine has two brewing heads sharing one milk container?
Candidate: Then reserving milk needs to be atomic — check-and-decrement in one step — or two concurrent brews could both see "enough milk" and overdraw it. Same race condition as the parking-spot problem, just a much smaller blast radius.
Interviewer: What happens if reservation succeeds for milk and coffee but fails for sugar?
Candidate: I'd roll back the milk and coffee reservations and refund the payment — an all-or-nothing reservation, so the machine never ends up in a state where it's charged the user for a drink it can't actually make.

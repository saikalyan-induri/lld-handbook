A. Realistic Interview Prompt

"Design a stock brokerage system. Users should be able to create an account, deposit and withdraw cash, place buy and sell orders for stocks, and view their portfolio and order history. Assume stock prices come from an external market data feed."

Note what is not specified: whether only market orders are supported or limit orders too, whether an unfilled order sits pending or is rejected outright, and whether execution means "trade against the live feed price" or "match against other users' orders" (a full exchange). A strong candidate surfaces these before writing a single class — the last one in particular determines whether this is an LLD problem at all, or secretly an HLD/distributed-systems one.

B. Difficulty

Advanced, escalating to Advanced + Concurrency/Consistency once the interviewer asks about two orders racing on the same account's cash or holdings (an almost-guaranteed follow-up). It sits a notch above Parking-Lot-style problems because the domain has hard financial invariants — a balance must never go negative, a sell must never exceed held shares — that have to survive concurrent access, not just single-threaded correctness.

C. What This Problem Tests

  • Modeling money and quantities correctly (no floating point for currency)
  • State-machine thinking for order lifecycle (PENDING → EXECUTED / REJECTED / CANCELLED)
  • Strategy pattern for execution logic (market vs. limit) — only once justified by a requirement
  • Observer pattern for reacting to price changes instead of polling
  • Enforcing invariants (funds/holdings) at the right layer, not scattered across callers
  • Concurrency reasoning once multiple orders can race on the same account
  • Recognizing the LLD/HLD boundary — this is a brokerage placing orders against a price feed, not a matching engine for a stock exchange

D. Requirements

Functional

  1. Create an account with a cash balance
  2. Deposit and withdraw cash from an account
  3. Place a buy or sell order for a stock, as a market or limit order
  4. Validate an order against available funds (buy) or available holdings (sell) before accepting it
  5. Execute an order against the current market price — immediately for market orders, or once the price condition is met for limit orders
  6. Maintain a portfolio of holdings per account
  7. Maintain an order/transaction history per account
  8. Allow cancelling an order that hasn't executed yet
  9. Look up the current price of a stock via a market data feed

Non-Functional

  • Extensibility — new order types (stop-loss, stop-limit) should not require touching existing order classes
  • Correctness under concurrency — cash can never be double-spent and shares can never be double-sold, even with concurrent orders on the same account
  • Interview-scale (a handful of accounts and stocks, not a full exchange's order volume)
  • Out of scope by default: matching orders against other users' orders (a real order book/exchange), multi-currency, tax reporting, real payment-rail integration — unless the interviewer asks

F. Assumptions

  • Confirmed (from prompt): account creation, deposit/withdraw, buy/sell orders, portfolio, order history, external price feed.
  • Assumption: execution happens against a pluggable market-data feed's price — this is a brokerage routing orders, not a peer-to-peer order book. Real cross-user matching is called out explicitly as an HLD boundary (see Y), mirroring how a single parking lot's design doesn't try to solve city-wide allocation.
  • Assumption: market orders execute immediately at the current feed price; limit orders remain PENDING until a feed price update crosses the limit, re-checked via a subscription callback (Observer), never by polling.
  • Assumption: funds (for buys) and holdings (for sells) are reserved at order-placement time and released on cancel/rejection — this is what prevents two concurrently pending orders from both passing a check against the same unspent balance.
  • Assumption: single currency, whole-share (integer) quantities in the base design; fractional shares are a stated extension, not built preemptively.
  • Assumption: in-memory state; persistence discussed as an extension (section X).
  • Assumption: no Singleton for Broker — same testability reasoning used throughout this handbook (see M).

Deliberately not created (yet): a peer order-matching engine/order book, a PaymentGateway for real money movement, a multi-currency FxConverter, a ComplianceEngine. The reference GitHub write-up this problem is commonly modeled after (ashishps1/awesome-low-level-design) keeps scope similarly narrow, but wires its central class as a Singleton — this handbook deliberately avoids that (see M) for the same reason it avoids Singleton everywhere else: it isn't a class-design requirement, it's an application-wiring decision, and baking it in makes the class harder to test.

I. Class Relationships

  • Composition: Broker owns Accounts; Account owns its Portfolio. An account's holdings don't make sense detached from the account — composition, not aggregation.
  • Inheritance: Order → BuyOrder/SellOrder. Kept shallow — the two subclasses diverge only on direction (which side gets reserved, which side gets settled), not on unrelated behavior, so the split stays justified rather than becoming ceremony.
  • Dependency: Broker → ExecutionStrategy and Broker → MarketDataFeed — both injected interfaces, so the execution rule and the price source can each be swapped (e.g. a fake feed in tests) without touching Broker.
  • Association: Order → Account, Order → Stock — an order references both but owns the lifecycle of neither.
  • Observer: MarketDataFeed notifies subscribed pending orders on a price change, rather than the system polling the feed on a timer — the same "push, don't poll" reasoning used for the Pub-Sub problem elsewhere in this handbook.
  • Why composition over a standalone Account service? An account's cash and holdings are two views of one financial position that must stay consistent with each other during a trade — splitting them into unrelated services would make the reserve/settle step span a network call for no benefit at this scale.

Explicitly avoided: Singleton for Broker. The reference implementation this problem is commonly based on defaults to a Singleton StockBroker "because there's only one broker in the process" — but that's an application-wiring decision (construct one instance, inject it everywhere), not a class-design constraint. Singleton would make it impossible to spin up two independent brokers side-by-side in a unit test, for no real production benefit.

O. Design Evolution

  • V1 — Single account, single stock, market orders only: Broker executes directly against the feed price with no reservation step.
  • V2 — Multiple stocks + real validation: introduce Portfolio; buy/sell must be validated against funds/holdings before accepting.
  • V3 — Limit orders introduced: extract ExecutionStrategy so Broker doesn't special-case order type with if/else.
  • V4 — Orders can stay pending: extract MarketDataFeed as an observable source; pending limit orders subscribe instead of being polled.
  • V5 — Preventing double-spend across pending orders: introduce the reserve-then-settle model on Account/Portfolio instead of a plain balance check.
  • V6 — Concurrent orders on the same account: reserve/settle become atomic operations (lock or CAS per account); Broker's public API signature doesn't change — only the internals of reservation gain synchronization.

What stays stable across all versions: the Broker.placeOrder()/cancelOrder() facade signature. That stability is the payoff of extracting ExecutionStrategy and MarketDataFeed early — callers never notice the internal evolution.

Order placeOrder(Account account, Stock stock, Side side, int qty, OrderType type, Money limitPrice)
    throws InsufficientFundsException, InsufficientHoldingsException {
  if (side == Side.BUY) {
    Money estimatedCost = (type == OrderType.MARKET ? feed.getPrice(stock.getSymbol()) : limitPrice).times(qty);
    account.reserve(estimatedCost);                       // throws InsufficientFundsException
  } else {
    account.getPortfolio().reserveShares(stock, qty);      // throws InsufficientHoldingsException
  }

  Order order = Order.create(account, stock, side, qty, type, limitPrice);
  ExecutionStrategy strategy = strategyFor(type, limitPrice);
  Money price = feed.getPrice(stock.getSymbol());
  Optional<Money> result = strategy.tryExecute(order, price);   // must be atomic w.r.t. account state — see W

  if (result.isPresent()) {
    settle(order, result.get());
  } else {
    order.setStatus(OrderStatus.PENDING);
    feed.subscribe(stock.getSymbol(), order);              // re-checked on future price ticks
  }
  return order;
}

void onPriceUpdate(Symbol symbol, Money newPrice) {          // Observer callback, not polling
  for (Order order : pendingOrdersFor(symbol)) {
    Optional<Money> result = order.getStrategy().tryExecute(order, newPrice);
    result.ifPresent(price -> settle(order, price));
  }
}

void settle(Order order, Money executionPrice) {
  if (order.getSide() == Side.BUY) {
    account.release(order.getReservedEstimate());
    account.withdraw(executionPrice.times(order.getQuantity()));
    portfolio.addHolding(order.getStock(), order.getQuantity());
  } else {
    portfolio.settle(order.getStock(), order.getQuantity(), Side.SELL);   // removes reserved shares
    account.deposit(executionPrice.times(order.getQuantity()));
  }
  order.setStatus(OrderStatus.EXECUTED);
}

void cancelOrder(OrderId orderId) throws InvalidOrderStateException {
  Order order = orderRepository.find(orderId);
  if (order.getStatus() != OrderStatus.PENDING) throw new InvalidOrderStateException();
  releaseReservation(order);                                  // cash or shares, by side
  order.setStatus(OrderStatus.CANCELLED);
}
std::shared_ptr<Order> placeOrder(std::shared_ptr<Account> account, std::shared_ptr<Stock> stock,

    account->portfolio.reserveShares(stock, qty);         // throws InsufficientHoldingsException

  }

}

function placeOrder(account, stock, side, qty, type, limitPrice) {
  if (side === Side.BUY) {
    const estimatedCost = (type === OrderType.MARKET ? feed.getPrice(stock.symbol) : limitPrice) * qty;
    account.reserve(estimatedCost);                      // throws InsufficientFundsException
  } else {
    account.portfolio.reserveShares(stock, qty);          // throws InsufficientHoldingsException
  }

  const order = Order.create(account, stock, side, qty, type, limitPrice);
  const strategy = strategyFor(type, limitPrice);
  const price = feed.getPrice(stock.symbol);
  const result = strategy.tryExecute(order, price);       // must be atomic w.r.t. account state — see W

  if (result !== null) {
    settle(order, result);
  } else {
    order.status = 'PENDING';
    feed.subscribe(stock.symbol, order);                   // re-checked on future price ticks
  }
  return order;
}

}

function settle(order, executionPrice) {
  if (order.side === Side.BUY) {
    account.release(order.reservedEstimate);
    account.withdraw(executionPrice * order.quantity);
    portfolio.addHolding(order.stock, order.quantity);
  } else {
    portfolio.settle(order.stock, order.quantity, Side.SELL);   // removes reserved shares
    account.deposit(executionPrice * order.quantity);
  }
  order.status = 'EXECUTED';
}

function cancelOrder(orderId) {
  const order = orderRepository.find(orderId);
  if (order.status !== 'PENDING') throw new Error('InvalidOrderStateException');
  releaseReservation(order);                                 // cash or shares, by side
  order.status = 'CANCELLED';
}
function placeOrder(account: Account, stock: Stock, side: Side, qty: number,
                    type: OrderType, limitPrice: Money): Order {
  if (side === Side.BUY) {
    const estimatedCost: Money = (type === OrderType.MARKET ? feed.getPrice(stock.symbol) : limitPrice) * qty;
    account.reserve(estimatedCost);                      // throws InsufficientFundsException
  } else {
    account.portfolio.reserveShares(stock, qty);          // throws InsufficientHoldingsException
  }

  const order: Order = Order.create(account, stock, side, qty, type, limitPrice);
  const strategy: ExecutionStrategy = strategyFor(type, limitPrice);
  const price: Money = feed.getPrice(stock.symbol);
  const result: Money | null = strategy.tryExecute(order, price);   // must be atomic w.r.t. account state — see W

  if (result !== null) {
    settle(order, result);
  } else {
    order.status = OrderStatus.PENDING;
    feed.subscribe(stock.symbol, order);                   // re-checked on future price ticks
  }
  return order;
}

function onPriceUpdate(symbol: Symbol, newPrice: Money): void {   // Observer callback, not polling
  for (const order of pendingOrdersFor(symbol)) {
    const result: Money | null = order.strategy.tryExecute(order, newPrice);
    if (result !== null) settle(order, result);
  }
}

function settle(order: Order, executionPrice: Money): void {
  if (order.side === Side.BUY) {
    account.release(order.reservedEstimate);
    account.withdraw(executionPrice * order.quantity);
    portfolio.addHolding(order.stock, order.quantity);
  } else {
    portfolio.settle(order.stock, order.quantity, Side.SELL);   // removes reserved shares
    account.deposit(executionPrice * order.quantity);
  }
  order.status = OrderStatus.EXECUTED;
}

function cancelOrder(orderId: OrderId): void {
  const order: Order = orderRepository.find(orderId);
  if (order.status !== OrderStatus.PENDING) throw new Error('InvalidOrderStateException');
  releaseReservation(order);                                 // cash or shares, by side
  order.status = OrderStatus.CANCELLED;
}

U. Testing Strategy

  • Happy path: deposit funds, place a market buy, portfolio reflects the new holding, cash balance decreases correctly.
  • Edge cases: buy that spends the balance down to exactly zero; sell of exactly all held shares; limit order placed exactly at the current price.
  • Invalid input: buy exceeding available funds; sell exceeding held shares; cancel of an unknown or already-executed order.
  • Failure scenarios: feed returns a stale or non-positive price (see Z); a pending order's stock is delisted mid-wait.
  • Concurrency tests: N concurrent buy orders on the same account that individually fit the balance but collectively exceed it — exactly the affordable prefix (by arrival or a defined tie-break) must succeed, the rest must get InsufficientFundsException, never an overdraft.

W. Concurrency

Shared mutable state: an account's cashBalance/reservedCash and a portfolio's holdings/reserved-quantity. Two orders racing to spend or sell against the same account is the canonical hazard here.

  • Critical section: "check available balance/holdings" + "reserve it" must be one atomic step — never two steps a thread could be pre-empted between.
  • Pessimistic approach: a mutex per account guarding reserve/release/settle. Simple, safe, and cheap in practice because accounts are naturally independent — locking Account A never blocks an order on Account B.
  • Optimistic approach: model the balance as a versioned/CAS-based field and retry the reserve on a failed compare-and-swap — avoids holding a lock, at the cost of retry logic.
  • Lock granularity trade-off: per-account locking is the natural boundary here (unlike a parking lot's shared spot pool) — different users' orders never need to contend, so granularity is close to free parallelism. A single global lock would be simpler but would serialize unrelated users' trades for no reason.
  • Idempotency: if a client retries a placeOrder call after a timeout (not knowing if it succeeded), the system must not double-reserve — this argues for an idempotency key on order placement.
  • Deadlock avoidance: a feature this base design doesn't need (transferring funds between two accounts) would require locking two accounts at once — always acquire such locks in a consistent global order (e.g., by account ID) to avoid circular wait.

X. Persistence

If state must survive a restart: Account, Portfolio, and Order become persistent entities with durable IDs, not in-memory object references. An AccountRepository/OrderRepository abstraction replaces direct in-memory maps — same interface shape, different backing store. The reserve-then-settle step becomes a database transaction (or an optimistic-locking update with a version column), so a crash between "reserve" and "settle" can't leave cash permanently held or shares double-counted. Order IDs should be generated in a way that's safe across restarts (UUID, not an in-memory counter).

Z. Failure Scenarios

  • Duplicate order-placement retry: a client retries placeOrder after a timeout — must not double-reserve funds/shares (idempotency key on the request).
  • Crash between "reserve" and "settle": reconciliation on restart should treat "reserved but never settled or released" as an anomaly to flag, not silently trust as normal pending state.
  • Stale or invalid feed price: a price feed delivering a stale, zero, or negative price must be rejected by validation before it's ever used to execute a trade — never trade on unchecked external input.
  • Withdrawal racing a pending buy's reservation: a withdraw request must check against the available balance (total minus reserved), never the raw total, or a pending order's funds could be withdrawn out from under it.

AA. Common Bad Designs

  • One giant Broker god class doing validation + execution + portfolio updates + history logging inline. Looks reasonable early (fewer files!) but every new order type or fee rule means editing the same massive class — violates SRP and OCP simultaneously. Fix: extract ExecutionStrategy and repositories as soon as either shows signs of variability.
  • Singleton StockBroker. Common in reference implementations "because there's only one broker" — but that's an application-wiring decision, not a class-design constraint, and it makes side-by-side testing awkward. Fix: a single instance via dependency injection at the wiring layer.
  • Using floating-point for money. Looks fine in a demo, quietly accumulates rounding errors across many trades. Fix: integer cents (or a fixed-point/decimal Money type) for all currency arithmetic.
  • Polling the price feed on a timer for every pending order. Looks simple to write, wastes cycles and adds latency at any real scale. Fix: subscribe pending orders to price-change notifications (Observer) so only actual changes trigger a re-check.
  • Type-string switch statements (if order.type == "limit") instead of polymorphism. Every new order type means hunting down every switch statement across the codebase. Fix: polymorphic ExecutionStrategy selected once at order creation.

AC. Interviewer Evaluation

  • Weak candidate: jumps straight to code; one big Broker class; uses floats for money; never asks whether execution is against a feed or a real order book.
  • Average candidate: asks 1–2 clarifying questions; produces a reasonable class split (Account, Order, Portfolio, Broker) but reservation and execution logic are still inline inside Broker.
  • Strong candidate: asks clarifying questions up front, including the order-book-vs-feed question; extracts ExecutionStrategy proactively because they identify execution rules as "likely to change"; models money as integers without being prompted.
  • Exceptional candidate: does all of the above, then anticipates the concurrency follow-up before being asked ("reserve needs to be atomic per account once orders can race"), and can clearly draw the line between this brokerage LLD and a full exchange's matching engine if pushed on scale.

AD. Interview Simulation

Interviewer: Design a stock brokerage system.
Candidate: Before I start — when I place an order, does it execute against a live market price feed, or does it get matched against other users' orders directly?
Interviewer: Assume it executes against a market data feed — you're not building an exchange.
Candidate: Good, that keeps this in LLD territory. I'll model a MarketDataFeed interface the broker depends on, so the price source is swappable and testable.
Interviewer: We need both market and limit orders, and pricing rules like commissions may come later.
Candidate: Then I'll isolate execution behind an ExecutionStrategy interface — market executes immediately, limit checks the price condition — and keep commission as a separate, future strategy rather than bolting it onto the same interface, since they vary independently.
Interviewer: What stops a user from placing two orders that together overdraw their balance?
Candidate: I'll reserve funds at order-placement time rather than only checking the balance — the reservation itself has to be atomic, guarded by a per-account lock, so two concurrent orders on the same account can't both pass a check against the same unspent cash.
Interviewer: The price feed goes down for thirty seconds. What happens to pending limit orders?
Candidate: They should just stay pending — I wouldn't execute against a stale or missing price. I'd add a staleness check on the feed and fail closed rather than trade on old data.
Interviewer: Last one — how would this look for millions of users trading at once?
Candidate: That crosses from LLD into HLD — I'd keep this exact account/order model, but shard accounts by user ID, put a message bus in front of price-tick fan-out instead of in-process subscriptions, and back the repositories with a real database. The object design here doesn't need to change; only where it runs does.

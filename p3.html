A. Realistic Interview Prompt

"Design a rate limiter that restricts how many requests a client can make to an API within a given time window. It should support multiple limiting algorithms and different limits for different clients or endpoints."

B. Difficulty

Intermediate for a single-process, single-algorithm version. Escalates to Advanced + Distributed Systems the moment the interviewer asks "now run this across many servers" — at which point the interesting problem stops being OOD and becomes "how do multiple processes atomically share one counter."

C. What This Problem Tests

  • Strategy pattern — this is arguably the single most natural Strategy example in all of LLD, since the algorithm (token bucket vs. sliding window vs. fixed window) is explicitly expected to vary
  • Factory pattern for producing the right configured limiter per endpoint/client tier
  • Testability discipline — passing time in rather than reading a wall clock internally
  • Concurrency — atomic check-and-decrement under a shared counter
  • Recognizing the LLD→distributed-systems boundary

D. Requirements

Functional

  1. Accept a request identified by client ID (and optionally endpoint)
  2. Decide allow/deny based on a configured limit and algorithm
  3. Support multiple algorithms (token bucket, sliding window, fixed window) interchangeably
  4. Return enough information for the caller to act: allowed/denied, remaining quota, retry-after

Non-Functional

  • Decision latency must be low — this sits on the hot path of every request
  • Thread-safe under concurrent requests from the same client
  • Extensible to new algorithms without touching the calling code
  • Bounded memory even with millions of distinct clients (stale state must be reclaimable)

F. Assumptions

  • Confirmed: must support multiple algorithms interchangeably; different clients/endpoints can have different limits.
  • Assumption: per-client-per-endpoint granularity as the default key.
  • Assumption: single-process, in-memory design first (V1–V5); distributed sharing of state is an explicit extension (V6), not baked in from the start.
  • Assumption: timestamps are passed into algorithm methods (server-generated, never trusted from the client) rather than read from a wall clock internally, for testability and to prevent client clock manipulation.
  • Assumption: idle client state is evicted after a TTL to bound memory.

I. Class Relationships

  • Dependency (interface): RateLimiter → RateLimitAlgorithm. The facade never knows which concrete algorithm it's talking to.
  • Creation: RateLimiterFactory builds algorithm instances from RateLimitConfig — this is where "which algorithm for which endpoint" is decided, kept out of both the facade and the algorithms themselves.
  • Composition: each algorithm instance owns its own per-client state map — state and algorithm travel together, since token bucket state (tokens, lastRefill) is structurally different from sliding-window state (a timestamp deque).
  • Why not one shared generic "Bucket" object across all algorithms? Because the state shape genuinely differs per algorithm (a single counter vs. a queue of timestamps vs. two rolling counters) — forcing a common state class would either bloat it with unused fields or leak abstraction, similar to the LRU/LFU issue in Problem 2.

O. Design Evolution

  • V1: one hardcoded fixed-window algorithm, one global limit.
  • V2: per-client tracking — a map keyed by client ID.
  • V3: extract RateLimitAlgorithm; add token bucket and sliding window as swappable strategies.
  • V4: per-endpoint/per-tier configuration via RateLimiterFactory + RateLimitConfig.
  • V5: thread-safety — per-client lock (or atomic state) so the hot path doesn't serialize unrelated clients.
  • V6: distributed — move per-client state into a shared store (Redis), using an atomic script (e.g. Lua) for the check-and-decrement so multiple app servers agree on one counter; define a fail-open/fail-closed policy for when that store is unreachable.

What stays stable: RateLimiter.check()'s signature. V6's biggest change is entirely inside the algorithm implementations' storage layer.

P. API / Interface Design

interface RateLimitAlgorithm {
  RateLimitResult allowRequest(String clientKey, long nowMs);
}

class RateLimiter {
  RateLimitResult check(String clientId, String endpoint, long nowMs);
}

class RateLimitResult {
  boolean allowed;
  long    remaining;
  long    retryAfterMs;   // 0 if allowed
}

Ownership/validation notes: nowMs is always supplied by the calling layer (server-side clock), never trusted from client input, and never read internally via a static call — this is what makes every algorithm implementation independently unit-testable with fabricated timestamps.

Q. Pseudocode — Token Bucket

allowRequest(key, now):
  bucket = store.getOrCreate(key, capacity)
  lock(bucket):
    elapsed = now - bucket.lastRefillTime
    bucket.tokens = min(capacity, bucket.tokens + elapsed * refillRatePerMs)
    bucket.lastRefillTime = now
    if bucket.tokens >= 1:
      bucket.tokens -= 1
      return ALLOW(remaining = floor(bucket.tokens))
    else:
      deficit = 1 - bucket.tokens
      return DENY(retryAfterMs = deficit / refillRatePerMs)

U. Testing Strategy

  • Happy path: requests under the limit are all allowed.
  • Edge cases: exactly at the limit; burst then wait exactly the refill interval (deterministic via injected clock); window-boundary burst for fixed-window (intentionally demonstrate the known weakness).
  • Invalid input: unknown client falls back to the configured default policy.
  • Concurrency tests: N threads racing for the last token — exactly capacity requests succeed, never more.
  • Failure scenarios: shared store (if distributed) times out — verify the configured fail-open/fail-closed behavior triggers correctly.

W. Concurrency

Shared mutable state: each client's bucket/window counters. The canonical race: two threads both read "tokens = 1," both decide to allow, both decrement — exceeding the limit by one.

  • Fine-grained locking: lock per client key (not one global lock) so unrelated clients never contend — critical for throughput at scale.
  • Atomic alternative: if the state is simple enough (e.g. a single counter in fixed-window), an atomic compare-and-swap loop can avoid locking entirely; token bucket's compound refill+decrement is harder to express as a single atomic op, so a lock is the more honest answer there.
  • Distributed atomicity: once state lives in Redis, "check-then-decrement" must be one atomic operation from Redis's perspective — a Lua script (executed atomically server-side) is the standard tool, rather than a separate GET then SET from the application, which would reintroduce the same race across the network.
  • Idempotency: rate-limit checks are naturally idempotent-safe (they're not a mutating business action) — a retried check just consumes an extra unit of quota, which is an acceptable, well-understood cost, not a correctness bug.

X. Persistence

Rate-limiter state is inherently ephemeral and derived — losing it on restart (resetting all clients to a full bucket) is an acceptable, safe default, not a data-loss incident. In the distributed design, Redis (with a TTL) effectively serves as the "shared state" layer, but it's not meant to be a durable system of record — it can be treated as a fast, shared cache.

LayerWhat Belongs Here

Z. Failure Scenarios

  • Shared store outage (distributed mode): must have an explicit fail-open/fail-closed policy — silence here is itself a bug.
  • Duplicate/retried client requests: naturally handled — each retry is just another checked request, no special idempotency machinery needed since rate-limiting isn't a mutating operation.
  • Clock skew across distributed nodes: mitigated by centralizing the time-sensitive math inside the shared store's atomic script rather than trusting each app server's local clock independently.
  • Stale/leaked per-client state: bounded via TTL eviction — otherwise an attacker could cheaply exhaust memory by rotating fake client IDs.

AA. Common Bad Designs

  • One class hardcoding token-bucket math with no interface — quick to write, but adding sliding-window later means editing and re-testing already-shipped, working code — the textbook OCP violation this problem exists to teach.
  • A single global lock around the entire limiter — "looks" thread-safe, but serializes every client's requests behind every other client's, destroying throughput.
  • Trusting a client-supplied timestamp — looks convenient for testing, but is a real security hole: a client could manipulate its own rate limit.
  • Building the distributed (Redis) version on day one

AC. Interviewer Evaluation

  • Weak candidate: hardcodes one algorithm inline with no interface; doesn't ask about per-client vs. global scope.
  • Average candidate: extracts a Strategy interface for algorithms, but doesn't discuss concurrency or mention testability (clock injection).
  • Strong candidate: Strategy + Factory, proactively raises the check-and-decrement race, chooses per-client locking, and injects time as a parameter without being asked.
  • Exceptional candidate: all of the above, and when scale comes up, can immediately articulate the fail-open/fail-closed trade-off and why Redis needs an atomic script rather than separate GET/SET calls.

AD. Interview Simulation

Interviewer: Design a rate limiter for an API.
Candidate: Should limiting be per-client, per-endpoint, or both — and do you need multiple algorithms supported, like token bucket versus sliding window?
Interviewer: Per-client-per-endpoint, and yes, assume the algorithm might change later.
Candidate: Then I'll define a RateLimitAlgorithm interface with one method, allowRequest(key, timestamp) — the timestamp is passed in rather than read internally, so every algorithm is testable without mocking a clock.
Interviewer: Good. Implement token bucket.
Candidate: Each client key maps to a bucket with a token count and last-refill time. On each request, I refill based on elapsed time, then check if a token is available before decrementing.
Interviewer: Two requests for the same client arrive at the same instant, both see one token left.
Candidate: That refill-check-decrement sequence needs to be atomic per client key — I'd use a lock scoped to that client's bucket, not a global lock, so unrelated clients aren't affected.
Interviewer: Now this needs to run correctly across ten application servers.
Candidate: At that point the per-client state has to move out of any single server's memory into a shared store like Redis, and the check-and-decrement needs to be one atomic operation there too — typically a Lua script executed server-side, so two app servers can't race each other over the network.
Interviewer: What if Redis goes down?
Candidate: That's a policy decision, not a bug to hide — fail-open keeps the service available but risks a traffic spike; fail-closed protects the backend but rejects legitimate users. I'd make that explicit and configurable rather than picking silently.

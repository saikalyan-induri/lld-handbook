A. Realistic Interview Prompt

"Design a movie ticket booking system like BookMyShow. Users can browse shows, select seats, hold them briefly while paying, and confirm a booking. Thousands of users may try to book seats for a popular show at the same time."

B. Difficulty

Advanced — the concurrency showcase of this document's second half. The entity model is not the hard part; the hard part is that every popular-show demo scenario is a high-contention multi-seat race, and the interview is really evaluating whether the candidate's locking design survives that contention without deadlocking, double-booking, or leaving seats stuck in limbo.

C. What This Problem Tests

  • Splitting the physical Seat from its per-show status (ShowSeat) — the same "shared static thing vs. per-instance changing state" split as Library's Book/BookItem and Hotel's Room/RoomInventory, now at genuinely high contention
  • State machine for a seat's per-show lifecycle (available → locked → booked, with expiry back to available)
  • TTL-based soft locking during payment, converted to a hard commit only on payment success
  • Multi-seat atomicity: booking several seats together must be all-or-nothing and deadlock-free
  • Idempotent payment confirmation under retries

D. Requirements

Functional

  1. Browse shows for a movie by city/theater/time
  2. View a show's seat map with real-time availability
  3. Select one or more seats and hold them temporarily while completing payment
  4. Confirm a booking on successful payment; release the hold on failure or timeout
  5. Price seats by category (Silver/Gold/Premium) and show (peak/off-peak)

Non-Functional

  • Two users must never both successfully book the same seat for the same show
  • A user who abandons checkout must not permanently lock a seat — the hold must expire
  • Booking multiple seats together must not deadlock against another user doing the same for an overlapping seat set

F. Assumptions

  • Confirmed: show browsing, seat-map viewing, temporary seat hold, payment-gated confirmation, category/show-based pricing.
  • Assumption: holds expire after a fixed TTL (e.g. 5–10 minutes) unless stated otherwise.
  • Assumption: payment confirmation arrives via a callback/webhook that may be retried by the payment provider, so it must be handled idempotently.

I. Class Relationships

  • Seat vs. ShowSeat is the central modeling decision, once again: a seat's physical attributes (number, category) are static across every show that ever plays in that screen, while its booking status only makes sense relative to one specific show — the same seat is available for the 3pm show and booked for the 7pm show. This is the identical split-shape already seen in Library's Book/BookItem and Hotel's Room/RoomInventory, but the contention here is dramatically higher because a single popular show creates a genuine thundering-herd on a small set of good seats.
  • State machine for ShowSeat: AVAILABLE → LOCKED → BOOKED, with LOCKED → AVAILABLE on hold expiry or payment failure. Encoding this as a ShowSeatState hierarchy (rather than a raw enum checked with scattered if statements) keeps every transition's legality colocated with the state itself — a BOOKED seat simply has no onLock() transition to accept.
  • SeatLock as a TTL-bound soft hold, Booking confirmation as the hard commit: selecting seats doesn't book them — it soft-locks them for a bounded window so the seat isn't shown as available to other users while this user pays, but the lock self-expires if they abandon checkout. Only a successful payment converts the soft lock into a permanent BOOKED status. This two-phase shape is deliberately similar to a database's optimistic-lock-then-commit pattern, made explicit at the domain level.
  • Strategy for pricing, Observer for the waitlist: both are the same shapes already established in Hotel (Problem 16) and Library (Problem 15) respectively — pricing varies by seat category and show timing behind PricingStrategy, and waitlist notification on a cancellation reuses the same subject/observer relationship rather than a bespoke path.

O. Design Evolution

  • V1: one booked boolean per seat, no hold concept, one flat price, synchronous payment.
  • V2: split Seat from ShowSeat the moment a screen hosts more than one show — the "same seat, different show" case that a single boolean cannot represent.
  • V3: introduce the ShowSeatState machine and SeatLock TTL once "hold while paying" becomes a real requirement rather than instant booking.
  • V4: extract PricingStrategy once category/show-based pricing is requested.
  • V5: wire WaitlistNotifier once sold-out waitlisting is requested.

What stays stable: BookingService's public hold/confirm/cancel API. New states and pricing rules are additive.

P. API / Interface Design

interface PricingStrategy {
  Money calculatePrice(Seat seat, Show show);
}

class BookingService {
  SeatLock holdSeats(User user, Show show, List<SeatId> seatIds);
  Booking confirmBooking(String lockId, PaymentResult result);  // idempotency-keyed
  void cancelBooking(String bookingId);
}

Ownership/validation notes: holdSeats() acquires locks on every requested ShowSeat in one atomic step (all-or-nothing — see W for lock ordering), and confirmBooking() is keyed by an idempotency key derived from the payment provider's transaction id, so a retried webhook call cannot double-confirm or double-charge.

Q. Pseudocode — Critical Logic

BookingService.holdSeats(user, show, seatIds):
  orderedIds = sort(seatIds)          // canonical order — see W
  locks = []
  try:
    for id in orderedIds:
      lock(showSeatFor(id))
      locks.append(showSeatFor(id))
      if showSeatFor(id).status != AVAILABLE: rollback(locks); reject
    for seat in locks: seat.status = LOCKED
    seatLock = new SeatLock(user, locks, expiresAt = now + HOLD_TTL)
    return seatLock
  finally:
    for seat in locks: unlock(seat)

BookingService.confirmBooking(lockId, paymentResult, idempotencyKey):
  if alreadyProcessed(idempotencyKey): return existingBookingFor(idempotencyKey)  // idempotent retry
  seatLock = lockFor(lockId)
  if seatLock.isExpired(): reject
  if paymentResult.success:
    for seat in seatLock.seats: seat.status = BOOKED
    booking = new Booking(seatLock, CONFIRMED)
  else:
    for seat in seatLock.seats: seat.status = AVAILABLE
    waitlistNotifier.notifyWaiting(seatLock.seats)
  recordProcessed(idempotencyKey, booking)
  return booking

  │

  │  payment webhook fires → confirmBooking(lockId, success, idempotencyKey)
  │  A4, A5 → BOOKED; Booking CONFIRMED

U. Testing Strategy

  • Happy path: holding then confirming a set of seats transitions exactly those seats to BOOKED and no others.
  • Edge cases: a hold that expires before payment completes releases all its seats back to AVAILABLE and, if a waitlist exists, triggers notification.
  • Idempotency tests: calling confirmBooking() twice with the same idempotency key produces exactly one Booking and one charge, not two.
  • Concurrency tests: two users concurrently holding overlapping seat sets (e.g. user A wants A4-A5, user B wants A5-A6) result in exactly one success for the shared seat A5, and neither request deadlocks against the other.

W. Concurrency

Shared mutable state: each ShowSeat's status for a popular show, under genuinely high simultaneous contention — this is the highest-contention scenario in the entire document.

  • The check-then-act race, at multi-resource scale: holding a single seat has the same check-then-lock-then-commit shape seen throughout this document (Parking Lot, Splitwise, ATM, Library, Hotel). What's new here is that a booking often spans multiple seats, which introduces a genuine deadlock risk: if user A locks A4 then tries to lock A5 while user B has already locked A5 and is trying to lock A4, both wait on each other forever.
  • Canonical lock ordering resolves it: sorting the requested seat ids before acquiring any locks, and always acquiring in that sorted order, guarantees every concurrent request converges on the same global lock order — this is exactly File System's (Problem 9) inter-process lock-ordering fix for the same deadlock shape, reapplied to seats instead of files.
  • TTL-based soft locks prevent indefinite holds: a SeatLock that never expired would let an abandoned checkout permanently starve a seat; the TTL guarantees eventual release even if the client disappears mid-payment.
  • Idempotent confirmation under retries: payment webhooks can and do get retried by the provider; keying confirmBooking() on an idempotency key prevents a retry from double-booking or double-charging — the same lesson Pub-Sub (Problem 10) established for message redelivery.

X. Persistence

Bookings and confirmed seat status must survive a restart without question — a booking that vanishes after payment is a trust-destroying failure. Seat holds are a middle ground: they could technically be rebuilt from a fast in-memory/distributed cache (with the TTL as the natural expiry), but the confirmed Booking record itself is always durable, repository-backed data.

Z. Failure Scenarios

  • Payment gateway times out with an unknown result: the seat must stay LOCKED (not auto-release, not auto-confirm) until an explicit success/failure callback or a manual reconciliation job resolves it — assuming either outcome is a correctness bug in one direction or the other.
  • The service crashes between locking seats and returning the SeatLock to the caller: a background sweep that releases any lock past its TTL guarantees seats don't stay stuck forever even if the in-flight request never got its response.

AA. Common Bad Designs

  • A single booked boolean per seat, shared across all shows — the defining mistake for this problem; see I.
  • Locking seats one at a time in whatever order the caller happened to request them — the deadlock trap; see W.
  • No TTL on a seat hold — an abandoned checkout permanently locks a seat no one else can ever book.
  • Treating payment confirmation as safe to process more than once — without an idempotency key, a retried webhook can double-book or double-charge.

AB. Design Trade-Offs

DecisionOption AOption BRecommendation
Lock scope for multi-seat holdsLock seats individually in sorted orderLock the entire show for the duration of any hold attemptSorted individual locks — locking the whole show serializes unrelated bookings on unrelated seats, destroying throughput for a popular show
Ambiguous payment result handlingAuto-release the seat after a short grace timeoutKeep the seat locked indefinitely pending manual reconciliationA bounded grace timeout with a reconciliation job as backstop — indefinite locking on an ambiguous result is a worse failure mode than occasionally releasing a seat that later turns out to have been paid for (refundable) than double-selling one that wasn't (not always reversible)

AC. Interviewer Evaluation

Strong signal: splitting Seat/ShowSeat unprompted; proposing a TTL-bound hold before being asked how checkout abandonment is handled; independently identifying the multi-seat deadlock risk and fixing it with canonical lock ordering; flagging idempotency for payment confirmation without being prompted.

Red flag: one booked flag per seat; per-seat locking with no defined acquisition order; no hold expiry; treating payment confirmation as safe to run twice.

AD. Interview Simulation

Interviewer: Design a movie ticket booking system for a popular show with thousands of concurrent users.
Candidate: I'd split the physical Seat from ShowSeat, since booking status only makes sense relative to one specific show — the same seat is free for one showtime and booked for another. Each ShowSeat runs a small state machine: available, locked, booked.
Interviewer: What happens between selecting a seat and actually paying for it?
Candidate: Selecting seats acquires a TTL-bound SeatLock — a soft hold, not a booking. If payment succeeds within the window, the hold converts to a permanent BOOKED status; if it fails or the TTL expires, the seats revert to available automatically.
Interviewer: What if a user tries to book two seats, and another user is simultaneously trying to book an overlapping pair in the opposite order?
Candidate: That's a real deadlock risk if each request locks seats in whatever order the user clicked them. I'd sort the requested seat ids and always acquire locks in that canonical sorted order — the same fix I'd use for the file-lock-ordering problem — so every concurrent request converges on the same global order and none of them can circularly wait on each other.
Interviewer: The payment provider retries its confirmation webhook due to a network blip. What happens?
Candidate: confirmBooking() is keyed by an idempotency key derived from the payment transaction id. A retried call with the same key returns the already-created booking instead of creating a second one or charging twice.

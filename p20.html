A. Realistic Interview Prompt

"Design a chat application like WhatsApp. Users can message each other one-on-one or in groups, see delivery and read receipts, and reconnect after being offline without losing or duplicating messages."

B. Difficulty

Advanced. This problem is the natural capstone of the Observer arc this document has built since Ride-Sharing's first small hook (Problem 5): a chat conversation is, structurally, a Pub-Sub topic with its participants as subscribers. The genuine new difficulty is per-conversation message ordering, exactly-once delivery across reconnects, and correctly separating the Mediator concern (decoupling participants from each other) from the Observer concern (notifying connected clients).

C. What This Problem Tests

  • Recognizing a conversation as a Pub-Sub topic — the same subject/observer relationship this document has used as a small hook in Ride-Sharing, Notification System, Library, Hotel, Movie Ticket Booking, and Food Delivery, and generalized fully in Pub-Sub (Problem 10) — now applied at the scale it was always heading toward
  • Mediator for group chat: participants hold a reference to the Conversation, never to each other directly, avoiding an O(n²) mesh of peer references as group size grows
  • State machine for per-message delivery status (sent → delivered → read)
  • Per-conversation message ordering assigned centrally, not by client clocks
  • Exactly-once delivery on reconnect, and a presence-status race across a user's multiple devices

D. Requirements

Functional

  1. Send a 1:1 or group message; all participants receive it in a consistent order
  2. Track delivery and read status per message (and, for groups, per recipient)
  3. Show a user's online/offline presence, correctly across multiple simultaneously-connected devices
  4. On reconnect after being offline, deliver missed messages exactly once, in order

Non-Functional

  • Two participants must never see the same conversation's messages in a different relative order
  • A reconnecting client must not receive a duplicate of a message it already has, nor miss one
  • Group size growth must not require every participant's client to hold a reference to every other participant

F. Assumptions

  • Confirmed: 1:1 and group messaging, delivery/read receipts, presence, exactly-once reconnect delivery.
  • Assumption: a user can be connected from multiple devices; presence is "online" if at least one device is connected.
  • Assumption: message ordering within a conversation is assigned by the server at receipt time, not derived from client-reported timestamps.

I. Class Relationships

  • Conversation is simultaneously a Mediator and an Observer subject — two complementary lenses, not competing patterns: as a Mediator, Conversation decouples its participants from each other — a User never holds a direct reference to any other participant, only to the conversations they're part of, which avoids an O(n²) mesh of peer references that would otherwise form as a group grows. As an Observer subject, Conversation is exactly the same subject/observer relationship this document has used repeatedly as a small hook — Ride-Sharing's driver-matched notification (Problem 5), Notification System's event triggers (Problem 7), Library's hold-queue availability (Problem 15), Hotel's booking confirmation (Problem 16), Movie Ticket's waitlist (Problem 17), Food Delivery's status push (Problem 18) — and generalized fully as the entire point of Pub-Sub (Problem 10). A chat conversation is arguably the most natural full-scale realization of that generalization: every participant is a subscriber, every sent message is a publish, and the whole document's Observer arc converges here.
  • DirectConversation needs no real mediation, but shares the base class anyway: with exactly two participants, there's no reference-explosion problem to solve, so the Mediator justification specifically doesn't kick in — but modeling it as the same Conversation abstraction (rather than a special-cased 1:1 path) keeps ChatService's API uniform regardless of conversation size, and costs nothing since a 2-subscriber topic is a trivial case of the general one.
  • MessageStatus as a per-recipient state machine: SENT → DELIVERED → READ, tracked independently per recipient in a group conversation (so "read by 3 of 5" is representable), rather than one status field on the message that can only mean one thing for every recipient at once.

O. Design Evolution

  • V1: one flat message list per pair of users, no groups, no receipts, no reconnect handling.
  • V2: introduce Conversation as the shared abstraction (Mediator + Observer subject) the moment groups are requested — this is exactly when direct user-to-user references would otherwise start multiplying.
  • V3: add per-recipient MessageStatus once delivery/read receipts are requested.
  • V4: add server-assigned sequencing once ordering-under-concurrent-sends becomes a real concern, not a demo simplification.
  • V5: add the reconnect-replay queue and PresenceTracker once offline delivery and multi-device presence are requested.

What stays stable: ChatService's public send/reconnect API. New conversation and content types are additive.

Ownership/validation notes: sendMessage() assigns the message's sequenceNo from the target Conversation's own monotonic counter — never from the client's clock — and reconnect() returns only messages strictly after lastSeenSequence, making replay naturally idempotent: calling it twice with the same cursor returns the same (or an empty) result, never a duplicate delivery.

Q. Pseudocode — Critical Logic

Conversation.send(sender, content):
  lock(this.sequenceCounter)
  try:
    seq = ++this.nextSequence      // server-assigned, monotonic per conversation
    message = new Message(sender, content, seq)
  finally:
    unlock(this.sequenceCounter)
  this.messages.append(message)
  for participant in this.participants:      // Observer fan-out
    if presenceTracker.isOnline(participant):
      deliver(participant, message)
    else:
      offlineQueueFor(participant).enqueue(message)
  return message

ChatService.reconnect(user, lastSeenSequence):
  missed = offlineQueueFor(user).allAfter(lastSeenSequence)   // idempotent: same cursor -> same result
  offlineQueueFor(user).clearUpTo(lastSeenSequence + missed.size)
  return missed

std::shared_ptr<Message> Conversation::send(std::shared_ptr<User> sender, const std::string& content) {
  std::shared_ptr<Message> message;
  lock(sequenceCounter_);
  try {
    long seq = ++nextSequence_;      // server-assigned, monotonic per conversation
    message = std::make_shared<Message>(sender, content, seq);
  } catch (...) {
    unlock(sequenceCounter_);
    throw;
  }
  unlock(sequenceCounter_);
  messages_.push_back(message);
  for (auto& participant : participants_) {      // Observer fan-out
    if (presenceTracker->isOnline(participant)) {
      deliver(participant, message);
    } else {
      offlineQueueFor(participant)->enqueue(message);
    }
  }
  return message;
}

groupChat.send(userA, "Hi all") → sequenceNo=42 assigned under the conversation's counter
  │  fan-out: userB online → delivered immediately; userC offline → enqueued
  ▼
userC reconnects with lastSeenSequence=41
  │  reconnect() returns exactly [message #42], marked delivered
  │  a duplicate reconnect() call with the same cursor returns the same result, not a re-delivery

userB opens the chat → MessageStatus for userB's receipt transitions DELIVERED → READ

U. Testing Strategy

  • Happy path: a message sent to a group is received by every online participant in the same relative order.
  • Edge cases: a participant offline at send time receives the message on reconnect, correctly marked as delivered only once they actually connect, not at send time.
  • Idempotency tests: calling reconnect() twice with the same lastSeenSequence cursor returns the same result and does not re-fire delivery receipts.
  • Concurrency tests: two participants sending to the same conversation at nearly the same instant receive server-assigned sequence numbers that are strictly ordered and consistent across every participant's view.

W. Concurrency

Shared mutable state: a conversation's sequence counter, and a user's set of connected devices.

  • Per-conversation ordering must be centrally assigned: if two participants' clients each stamped their own message with a local timestamp, clock skew between devices could reorder messages inconsistently across different participants' views. Assigning sequenceNo from the conversation's own lock-guarded counter at receipt time guarantees a single, consistent order every participant agrees on.
  • Exactly-once delivery on reconnect: replaying missed messages by a cursor (last-seen sequence) rather than a "have I sent this before" flag per message makes the operation naturally idempotent — the same lesson already established for payment-webhook retries in Movie Ticket Booking (Problem 17) and E-commerce Checkout (Problem 19), now applied to message redelivery instead of payment confirmation.
  • The presence race across multiple devices: device A disconnecting while device B is simultaneously connecting for the same user is a check-then-act race on the user's aggregate online status; modeling PresenceTracker as a set of connected device ids (rather than a single boolean flipped by whichever event arrives last) avoids the race entirely — "online" is simply "is this set non-empty," and add/remove operations on a set are commutative regardless of arrival order.

X. Persistence

Messages and their receipts are durable by nature — a chat history that disappears on restart is a trust-destroying failure, matching Movie Ticket Booking's and E-commerce's treatment of confirmed transactional records. Presence state is the opposite: inherently transient, tied to an active connection, and reasonably rebuilt from scratch (as "offline") on any restart rather than persisted.

Z. Failure Scenarios

  • A participant's client crashes mid-delivery, after receiving a message but before acknowledging it: on reconnect, the cursor-based replay in reconnect() naturally re-delivers anything not yet acknowledged — the idempotent-by-construction design from W means this "failure" requires no special-case handling.
  • The conversation's sequence counter's lock is held by a slow send while a burst of new sends arrives: the lock window is intentionally tiny (just the increment, not the full fan-out), keeping contention bounded even under a message burst.

AA. Common Bad Designs

  • Giving every User direct references to every other participant they've chatted with instead of routing through Conversation as a Mediator — the defining mistake for group chat; see I.
  • Ordering messages by client-reported timestamp instead of a server-assigned sequence — breaks the instant two devices have any clock skew.
  • Tracking "delivered" as a single flag per message instead of a per-recipient receipt map — can't represent partial delivery/read state in a group.
  • Modeling presence as one boolean flipped by whichever connect/disconnect event arrives last instead of a device set — reintroduces exactly the race a set-based model avoids for free.

AC. Interviewer Evaluation

Strong signal: naming Conversation as both a Mediator and an Observer subject and explaining why those are complementary, not competing, framings; assigning message order from a server-side counter unprompted; designing reconnect as cursor-based (hence idempotent) rather than flag-based; modeling presence as a device set rather than a single racy boolean.

Red flag: direct peer references between users in a group; client-timestamp-based ordering; a single delivered/not-delivered boolean per message; a presence boolean that races across devices.

AD. Interview Simulation

Interviewer: Design a chat application supporting both 1:1 and group messaging.
Candidate: I'd model a Conversation as the shared abstraction for both — every participant holds a reference to the conversation, never to each other directly. That's a Mediator role: it prevents an O(n²) mesh of direct references as a group grows. It's simultaneously an Observer subject — every participant is a subscriber, and sending a message is a publish. That's the same subject/observer shape this design has used as a small hook in several other systems, generalized fully here.
Interviewer: How do you keep message order consistent for everyone in a group?
Candidate: I wouldn't trust client timestamps — clock skew between devices could reorder messages differently for different viewers. I'd assign a sequence number from the conversation's own server-side counter at the moment the message is received, so there's one authoritative order everyone agrees on.
Interviewer: A user reconnects after being offline for an hour. How do you avoid duplicating or losing messages?
Candidate: Reconnect takes the client's last-seen sequence number as a cursor and replays everything strictly after it. That's naturally idempotent — replaying from the same cursor twice returns the same result, so a retried reconnect can't double-deliver.
Interviewer: What about a user logged in on two devices, and one disconnects?
Candidate: I'd model presence as a set of connected device ids per user rather than one boolean — "online" just means the set is non-empty. Add and remove on a set commute regardless of arrival order, which sidesteps the race a single last-writer-wins boolean would have.

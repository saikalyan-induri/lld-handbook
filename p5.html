A. Realistic Interview Prompt

"Design a ride-sharing service like Uber or Lyft. Riders request a trip from a pickup location to a destination; the system matches them with a nearby available driver, the ride proceeds through pickup and drop-off, and a fare is calculated and charged at the end."

B. Difficulty

Advanced. This is one of the few problems in this set that genuinely straddles LLD and HLD: it combines a real-time matching problem, a multi-state ride lifecycle, geospatial data structures, dynamic pricing, and heavy concurrency (many riders and drivers mutating shared state at once). Interviewers explicitly watch for whether a candidate recognizes the LLD/HLD boundary rather than trying to design a distributed geo-sharded system inside a 45-minute class-design round.

C. What This Problem Tests

  • Two independent Strategies (matching algorithm, fare algorithm) that must not be conflated into one
  • State-machine thinking for a ride's lifecycle with real illegal-transition risk
  • Geospatial reasoning — at least conceptually (Haversine distance, geohash/quadtree bucketing) even without a production-grade index
  • Observer for notifications, decoupled from core orchestration
  • Concurrency: atomically reserving a driver so two riders can't both be matched to the same driver
  • Explicitly recognizing what belongs in LLD versus what is an HLD/infrastructure concern

D. Requirements

Functional

  1. Rider requests a ride: pickup location, dropoff location
  2. System matches the rider to a nearby available driver
  3. Driver accepts or rejects the match; on accept, drives to pickup
  4. Ride proceeds: driver arrives → picks up rider → trip in progress → drop-off
  5. Fare is computed (distance + time + surge) and charged
  6. Either party may cancel before the ride starts
  7. Rider and driver rate each other after completion

Non-Functional

  • Matching must scale past a naive O(n) scan of every driver in the city — geospatial indexing matters conceptually
  • Ride-state transitions must be enforced; a ride can't be "completed" without having been "in progress"
  • A driver must never be matched to two riders at once, even under concurrent requests
  • Fare computation must be extensible (surge, promotions) without rewriting the core request→match→complete flow

F. Assumptions

  • Confirmed: request → match → accept → pickup → in-progress → complete → fare-charge flow; pre-ride cancellation; single pickup/dropoff pair per ride.
  • Assumption: matching defaults to nearest-available-driver by straight-line (Haversine) distance; ETA-aware or rating-aware matching is a stated extension, not the baseline.
  • Assumption: a simplified in-memory geospatial bucket index (grid cell / geohash prefix → list of driver IDs) stands in for a production spatial index — the concept is being tested, not a production quadtree implementation.
  • Assumption: PaymentGateway is an external dependency behind an interface; this design computes the fare and calls it, but does not implement card processing.
  • Assumption: a single vehicle/ride type exists in the base design; multiple types are a stated later extension.
  • Assumption: a driver may reject a match; on rejection the system retries with the next-nearest available driver rather than failing the request outright.

I. Class Relationships

  • Association, not composition: Ride references one Rider and one Driver, but neither exists because of the ride, nor is destroyed with it — this mirrors why Splitwise's Group↔User is aggregation, not composition.
  • Composition: a Driver owns its current Vehicle registration and its live Location — these have no meaning detached from that driver profile.
  • Dependency: RideService → MatchingStrategy, FareStrategy, GeoIndex (all interfaces/collaborators, not concrete lookups).
  • Decorator, not a second Strategy, for surge: SurgeFareDecorator wraps any base FareStrategy and multiplies its result during high demand. Surge is a modifier that composes with distance+time fare, flat-rate fare, or a promo fare — it is not a mutually exclusive alternative the way Equal/Exact/Percent splits were in Splitwise. Making it a parallel Strategy would force every surge-aware variant to duplicate the base fare math it's supposed to modify.
  • State, for the ride lifecycle: Ride.transitionTo() is a guarded state machine (REQUESTED → MATCHED → ACCEPTED → ARRIVED → IN_PROGRESS → COMPLETED, with CANCELLED reachable from several early states) rather than a free-form status field any code can overwrite.

FacadeCallers shouldn't juggle geo-lookup + matching + reservation + fare themselvesRideServiceSkip only for the smallest single-rider/single-driver toy version

Explicitly avoided: hardcoding RideService (or a DriverRegistry/TripManager) as a Singleton. Several reference solutions default to Singleton "because there's only one system," but that bakes in global mutable state, makes the class impossible to instantiate twice in a test, and buys nothing that ordinary dependency injection of a single instance at the composition root doesn't already give you — the same critique made of ParkingLot in Problem 1.

O. Design Evolution

  • V1: single rider, single driver, no matching (manual assignment), flat fare.
  • V2: multiple drivers; naive O(n) scan across all drivers by distance.
  • V3: extract MatchingStrategy; add GeoIndex so lookups aren't a full scan.
  • V4: extract FareStrategy; add the guarded Ride state machine.
  • V5: add SurgeFareDecorator, Observer-based notifications, driver-rejection retry loop, pre-ride cancellation.
  • V6: concurrency-safe driver reservation (atomic status compare-and-swap), continuous driver location updates, multi-vehicle-type support.

What stays stable: RideService.requestRide()/acceptRide()/completeRide() signatures. Matching heuristics, fare modifiers, and the index implementation are all additive.

Q. Pseudocode — Critical Logic

requestRide(rider, pickup, dropoff):
  ride = Ride.create(rider, pickup, dropoff, status=REQUESTED)
  candidates = geoIndex.findNearby(pickup, radius=DEFAULT_RADIUS)
  while candidates not empty:
    driver = matchingStrategy.match(ride, candidates)
    if driver is None: break
    if driver.tryReserve():           // atomic CAS: AVAILABLE -> RESERVED
      ride.transitionTo(MATCHED, driver)
      notificationService.onRideStatusChanged(ride)
      return ride
    candidates.remove(driver)         // someone else grabbed it first, retry
  ride.transitionTo(NO_DRIVER_FOUND)
  return ride

completeRide(rideId):
  ride = rides.get(rideId)
  ride.transitionTo(COMPLETED)        // throws if not currently IN_PROGRESS
  baseFare = fareStrategy.calculate(ride)     // may itself be a decorator chain
  ride.fare = baseFare
  paymentGateway.charge(ride.rider, baseFare)
  driver.release()                    // RESERVED/ON_TRIP -> AVAILABLE
  notificationService.onRideStatusChanged(ride)
  return ride

  const ride = Ride.create(rider, pickup, dropoff, REQUESTED);
  let candidates = geoIndex.findNearby(pickup, DEFAULT_RADIUS);

    if (driver === null) break;

      ride.transitionTo(MATCHED, driver);
      notificationService.onRideStatusChanged(ride);
      return ride;
    }
    candidates = candidates.filter(d => d !== driver);   // someone else grabbed it first, retry
  }
  ride.transitionTo(NO_DRIVER_FOUND);
  return ride;
}

U. Testing Strategy

  • Happy path: request → match → accept → complete, with the correct fare and a driver returned to AVAILABLE afterward.
  • Edge cases: no drivers within radius; driver rejects and a second candidate is matched instead; ride cancelled between MATCHED and ACCEPTED.
  • Invalid transitions: calling completeRide on a ride still in REQUESTED must be rejected by the state machine, not silently accepted.
  • Concurrency tests: N riders simultaneously requesting near the same single available driver — exactly one tryReserve() succeeds; the rest fall through to the next candidate.
  • Fare tests: decorator stacking (surge × promo) applied in a defined, tested order.

W. Concurrency

Shared mutable state: each Driver.status field, and the GeoIndex's bucket contents as drivers move.

  • The double-booking race: two riders' requestRide calls can both read the same driver as "AVAILABLE" before either writes a reservation — a classic check-then-act race. The fix is the same one used for Parking Lot's spot occupation: make "check and reserve" a single atomic compare-and-swap (status: AVAILABLE → RESERVED), not a read followed by a separate write.
  • High-frequency location updates: drivers report position every few seconds; GeoIndex.update() must be cheap and lock-scoped to just the affected bucket(s), not a global structure lock, or writes from thousands of moving drivers would serialize against each other.
  • State machine guards double as concurrency guards: Ride.transitionTo() checking "is the current status a legal predecessor?" also prevents two racing threads from both successfully completing the same ride twice.
  • Retry-not-block: when a CAS reservation fails, the losing request should fall through to the next candidate immediately rather than blocking on a lock — matching is latency-sensitive, and a failed reservation is an expected, common outcome, not an error.

X. Persistence

Two concerns worth separating: (1) ride records — an append-only log of completed/cancelled rides for history, receipts, and disputes, naturally durable and rarely updated after completion; (2) live driver location/status — extremely high write volume, low durability requirement per individual update (only the latest position matters), and a natural fit for an in-memory store (e.g. a fast key-value store) rather than a transactional database. Treating these as one persistence layer with one consistency model is a common mismatch — mentioning the split shows you've thought about write patterns, not just schemas.

Z. Failure Scenarios

  • Driver accepts but then goes silent: needs an accept-to-arrival timeout, not an indefinite wait.
  • Payment fails at trip completion: the ride should still be marked COMPLETED (the trip physically happened); the payment failure is a separate, retryable concern, not a reason to roll back trip state.
  • Crash between reservation and match confirmation: a reservation without a corresponding notification leaves a driver stuck RESERVED — needs a timeout that releases it back to AVAILABLE.
  • GeoIndex and driver's actual location drift apart (stale update): matching against stale data occasionally returns a driver who's actually too far — acceptable if bounded by a max staleness window, a real trade-off to name explicitly.

AA. Common Bad Designs

  • God-object RideService doing geo-lookup, ranking, fare math, and notification delivery all inline — the same trap seen in every other problem in this set, just with more moving parts here.
  • Check-then-set driver reservation (read status, then separately write it) — looks correct in a single-threaded demo, breaks the instant two requests race, exactly like Parking Lot's naive spot allocation.
  • Driver extends User inheritance with no clear boundary on what's shared vs. role-specific — workable, but worth being deliberate about (composition of a role-specific profile onto a shared identity is at least as defensible and avoids forcing every future role into the same base class).
  • Treating surge as a second, parallel FareStrategy instead of a decorator — leads to duplicated base-fare logic across every surge-aware variant.
  • Baking real-time GPS streaming/WebSockets into the class design itself — an HLD/infra concern masquerading as an LLD answer; a strong candidate names it as out of scope rather than sketching a message broker on the whiteboard.

AC. Interviewer Evaluation

  • Weak candidate: one RideService class scanning all drivers linearly, mutating a raw status string with no guard against illegal transitions.
  • Average candidate: has separate Matching/Fare logic, but doesn't address the driver double-booking race or mention any geo-indexing concept.
  • Strong candidate: clean Strategy separation for matching and fare, a guarded state machine, and unprompted recognition of the atomic-reservation race.

AD. Interview Simulation

Interviewer: Design something like Uber.
Candidate: To scope this — do you want real geospatial indexing, like a geohash or quadtree, or can I assume a helper that returns nearby drivers and focus on the ride lifecycle and matching/fare logic?
Interviewer: Assume nearby-driver lookup exists; focus on the flow and the matching/fare design.
Candidate: Then I'll separate two independent strategies — a MatchingStrategy that picks among nearby candidates, and a FareStrategy that prices the trip. They vary independently, so I don't want to conflate them into one "ride algorithm" class.
Interviewer: Now add surge pricing.
Candidate: I'd wrap the base FareStrategy with a SurgeFareDecorator rather than writing a second, parallel strategy — surge is a multiplier on top of any base fare, not an alternative way of computing one, so a decorator avoids duplicating the base math.
Interviewer: Two riders request a ride at the same moment, and there's only one available driver nearby. What happens?
Candidate: That's a race condition on the driver's status. I'd make reservation a single atomic compare-and-swap — AVAILABLE → RESERVED — so exactly one request wins; the other falls through and retries the next-nearest candidate. A check-then-set approach would let both requests briefly believe they'd won.
Interviewer: How do you prevent a ride from being marked complete before it's even started?
Candidate: The Ride holds a guarded state machine — each transition checks that the current status is a legal predecessor before applying the change, so completeRide on a still-REQUESTED ride is rejected outright rather than silently accepted.
Interviewer: Last one — how would this scale to millions of drivers across a whole city?
Candidate: At that point the in-process grid index becomes a distributed, sharded geospatial service, driver location updates flow through something like a message queue instead of direct calls, and the atomic reservation needs a single source of truth for driver status across matching workers — but that's an infrastructure/HLD concern, not a change to the class design itself.

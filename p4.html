A. Realistic Interview Prompt

"Design an expense-sharing application like Splitwise. Users can form groups, add shared expenses with different splitting methods, see who owes whom, and settle up."

B. Difficulty

Intermediate for the core model (users, groups, expenses, splits, balances). Becomes Advanced once debt simplification (minimizing the number of settling transactions) and concurrent balance updates enter the conversation — the former is a genuine graph algorithm, the latter tests real correctness invariants on shared financial state.

C. What This Problem Tests

  • Strategy pattern for split computation — a close cousin of the pricing/allocation strategies in Problems 1 and 3
  • Separating "data" (who owes what) from "algorithm" (how it was computed)
  • Modeling an invariant explicitly (sum of all balances must always equal zero) and defending it under concurrency
  • Graph thinking for debt simplification (recognizing an NP-hard optimal case vs. a practical greedy approximation)
  • Idempotency for a financial mutation (settling up)

D. Requirements

Functional

  1. Create users and groups (a group is a set of users)
  2. Add an expense: total amount, payer, participants, and a split method (equal / exact / percentage)
  3. Compute and track balances (who owes whom, and how much)
  4. Settle up — record a payment that reduces an existing balance
  5. View balances, both pairwise and net per user

Non-Functional

  • Correctness invariant: the sum of all balances across all users must always equal zero
  • Concurrent expense additions/settlements must not corrupt balances
  • Extensibility to new split types without touching existing balance logic

F. Assumptions

  • Confirmed: equal / exact / percentage splits; groups; balance tracking; settle-up.
  • Assumption: pairwise net balances are tracked (not just a single net-worth number per user), since "who owes whom" is the core value proposition.
  • Assumption: the payer is not required to be a split participant (supports "I'll treat you").
  • Assumption: rounding remainders are assigned to the payer by convention, and split amounts are validated to sum exactly to the total before an expense is accepted.
  • Assumption: debt simplification is a follow-up capability (V6), not baked into the base design.
  • Assumption: settle-up is modeled as a distinct Payment entity, not an Expense subclass (see M for why).

I. Class Relationships

  • Aggregation: Group has Users, but users exist independently — deleting a group must never delete its members. This is aggregation, not composition, unlike Parking Lot's Floor/Spot relationship.
  • Composition: Expense owns its Splits — a split has no meaning outside the expense that produced it.
  • Dependency: ExpenseService → SplitStrategy (interface), resolved via a factory keyed by split type.
  • Why is Payment a sibling of Expense, not a subclass? A payment has no participants list, no split computation, and no strategy — forcing it to inherit from Expense just to reuse "affects the balance sheet" would drag along fields and methods that don't apply, an LSP smell. Both instead go through ExpenseService, which applies their effect to BalanceSheet through a narrow, shared path.

O. Design Evolution

  • V1: two users, one expense, equal split only, balance update inline.
  • V2: introduce Group with multiple members, still equal split.
  • V3: extract SplitStrategy; add Exact and Percentage splits.
  • V4: extract BalanceSheet as an explicit pairwise ledger instead of ad hoc updates scattered in the service.
  • V5: add Payment/settle-up, symmetric with Expense's effect on the ledger.
  • V6: concurrency-safe balance updates (per-pair locking with consistent ordering) + optional DebtSimplifier for minimum-transaction settlement suggestions.

What stays stable: ExpenseService.addExpense()/settleUp() signatures. The ledger's internal storage and the debt-simplification feature are additive, not disruptive.

P. API / Interface Design

interface SplitStrategy {
  List<Split> compute(Money total, List<User> participants, Map<String,Object> params);
}

class ExpenseService {
  Expense addExpense(Money total, User paidBy, List<User> participants,
                      SplitType type, Map<String,Object> params, Optional<Group> group);
  Payment settleUp(User from, User to, Money amount, String idempotencyKey);
  Money   getBalance(User a, User b);
  Map<User, Money> getNetBalances(Group group);
}

Ownership/validation notes: addExpense validates that computed splits sum exactly to total before persisting anything — rejecting the whole operation rather than silently drifting the sum-to-zero invariant. settleUp takes an idempotency key so a client retry after a timeout can't double-adjust the balance.

Q. Pseudocode — Critical Logic

addExpense(total, payer, participants, type, params):
  strategy = strategyFactory.get(type)
  splits = strategy.compute(total, participants, params)
  assert sum(s.amount for s in splits) == total   // reject if strategy is buggy
  expense = Expense.create(total, payer, splits)
  for split in splits:
    if split.user != payer:
      balanceSheet.adjust(split.user, payer, +split.amount)  // split.user owes payer
  return expense

settleUp(from, to, amount, idemKey):
  if paymentLog.seen(idemKey): return paymentLog.get(idemKey)   // idempotent replay
  balanceSheet.adjust(from, to, -amount)
  payment = Payment.create(from, to, amount)
  paymentLog.record(idemKey, payment)
  return payment

U. Testing Strategy

  • Happy path: equal split across 3 users sums correctly; percentage split summing to exactly 100%.
  • Edge cases: non-evenly-divisible amount (rounding); payer not among participants; single-participant "expense" (degenerate case).
  • Invalid input: percentages that don't sum to 100%; exact amounts that don't sum to the total — both rejected before any balance mutation.
  • Invariant check: after any sequence of expenses/payments, sum of all balances across all users equals zero.
  • Concurrency tests: concurrent expenses touching overlapping user pairs — no lost updates, invariant still holds afterward.

W. Concurrency

Shared mutable state: each entry in BalanceSheet. The core invariant — total balances across all users sum to zero — must survive concurrent writes.

  • The multi-pair problem: a single expense with N participants touches N different balance-sheet entries at once. If two overlapping expenses lock those pairs in different orders, they can deadlock.
  • Mitigation: always acquire locks for the affected pairs in one consistent global order (e.g., sorted by user ID) — the standard fix for multi-resource locking, not unique to this problem.
  • Optimistic alternative: in a persisted design, use a version column (optimistic concurrency) on each balance row instead of pessimistic locks — retries on conflict rather than blocking, often preferable since expense creation is typically low-contention per specific pair.
  • Idempotency: settleUp in particular must be idempotent — a financial "did it happen twice?" bug is much worse than most other systems' retry bugs.

X. Persistence

Two valid designs, worth presenting both: (1) event-sourced — the append-only Expense/Payment log is the source of truth, and BalanceSheet is a rebuildable projection; (2) materialized-ledger — BalanceSheet rows are updated transactionally alongside each Expense/Payment write, inside the same database transaction. Materialized is faster to read; event-sourced is more auditable and self-healing if a bug ever corrupts a balance. Mentioning both, and picking one with a stated reason, reads much stronger than assuming only one exists.

LayerWhat Belongs Here

Z. Failure Scenarios

  • Partial failure mid-expense: some balance adjustments applied, others not — must be all-or-nothing (a single transaction, or a compensating rollback).
  • Duplicate settle-up: must be idempotent via a client-supplied key.
  • Crash between "expense recorded" and "balance updated": prevented by keeping both in one transaction, or reconciled via an event-sourced rebuild.

AA. Common Bad Designs

  • God-object ExpenseService computing splits inline, mutating balances inline, formatting display strings inline — same trap as other problems, riskier here since it's financial data.
  • Payment extends Expense for code reuse — creates an LSP smell (Payment doesn't have splits or a strategy) purely to avoid writing a shared narrow interface.
  • No BalanceSheet at all, replaying full history on every balance query — correct but O(n) per read; acceptable for a toy version, a red flag if presented as final without discussing the materialized alternative.
  • Global lock around the entire ledger for every expense — correct but serializes unrelated users' expenses system-wide.

AC. Interviewer Evaluation

  • Weak candidate: hardcodes equal split only; mutates a raw balance array with no clear ledger abstraction.
  • Average candidate: has a Split hierarchy and a BalanceSheet, but doesn't mention the sum-to-zero invariant or concurrency.
  • Strong candidate: clean Strategy separation; explicitly states and tests the sum-to-zero invariant; raises idempotency for settle-up unprompted.
  • Exceptional candidate: all of the above, plus correctly frames debt simplification as an NP-hard optimal problem with a practical greedy approximation, and reasons about lock ordering across multi-participant expenses without being pushed.

AD. Interview Simulation

Interviewer: Design something like Splitwise.
Candidate: What split types need support — equal, exact, percentage — and do balances need to be tracked pairwise, or just net-per-user?
Interviewer: All three split types, and yes, pairwise — I want to know exactly what I owe each person.
Candidate: Then I'll separate the split data from the split algorithm — a SplitStrategy interface computes a list of Split objects from the total and participants, and an Expense just stores the result.
Interviewer: How do you guarantee the numbers stay consistent?
Candidate: I'd enforce, as an invariant, that the sum of all balances across every user always equals zero — and validate that every strategy's output sums exactly to the total before accepting the expense at all.
Interviewer: Now support settling up.
Candidate: I'd model that as a separate Payment entity, not a subclass of Expense — it has no splits or strategy, so inheriting would just carry along fields that don't apply.
Interviewer: A client retries a settle-up after a network timeout.
Candidate: settleUp needs to be idempotent — I'd have the client pass an idempotency key so a retried call returns the original result instead of adjusting the balance twice.
Interviewer: Last one — a group of 10 people has a tangled web of debts. Minimize the number of payments needed to settle everyone up.
Candidate: That's a graph min-cash-flow problem, and the truly optimal version is NP-hard. I'd use a practical greedy approach instead — repeatedly match the largest creditor with the largest debtor using two max-heaps — and I'd be upfront that it's a good approximation, not a guaranteed minimum.

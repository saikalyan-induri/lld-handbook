A. Realistic Interview Prompt

"Design the control system for a bank of elevators in a building. Support external hall calls (up/down buttons on each floor) and internal car calls (floor buttons inside each cabin), and decide which elevator services which request."

B. Difficulty

Intermediate → Advanced. The state machine for a single elevator is straightforward; the real difficulty is dispatch — deciding which of several elevators answers a hall call — and doing that assignment safely when multiple hall-call events can arrive concurrently.

C. What This Problem Tests

  • Modeling a single elevator as a State machine with real, enforceable transition rules (an elevator with doors open cannot start moving)
  • Separating "how one elevator behaves" from "which elevator answers this call" — the second is a Strategy, not a hardcoded rule buried in the elevator class
  • Recognizing the classic SCAN/"elevator algorithm" from OS disk scheduling as the direct ancestor of a realistic dispatch strategy
  • Atomic hall-call assignment under concurrent requests — the same check-then-act shape as Parking Lot's spot occupation, now applied to "which car claims this call"

D. Requirements

Functional

  1. Support N elevators serving M floors in one building
  2. Accept external hall calls (floor, direction) and internal car calls (destination floor from inside a cabin)
  3. Assign each hall call to exactly one elevator
  4. Move an elevator toward its pending requests, opening doors at each stop it must serve
  5. Report each elevator's current floor, direction, and door state
  6. Take an elevator out of service (maintenance/fault) and redistribute its pending requests

Non-Functional

  • No hall call may ever be silently dropped or assigned to two elevators simultaneously
  • An elevator already moving in a direction should not needlessly reverse before finishing the requests it can serve along the way (the core SCAN insight)
  • Door state transitions must be safe — a door cannot be commanded to open while the cabin is moving

F. Assumptions

  • Confirmed: N elevators, M floors, hall calls (floor + direction) and car calls (destination floor), single building.
  • Assumption: single process controlling all elevators (an in-building controller), not a multi-building fleet-management service — that class of problem is named explicitly but pushed to HLD (see Y).
  • Assumption: no keycard/restricted-floor access control unless asked — if asked, it layers on as a Proxy/guard check ahead of accepting a car call, the same shape as File System's optional permission Proxy.
  • Assumption: a reasonable default capacity limit exists per cabin, but weight-sensing hardware itself is out of scope — the design just needs a hook (isFull()) for the dispatcher to check.

I. Class Relationships

  • State (headline): each Elevator holds a current ElevatorState and delegates behavior to it. A door can only be commanded open from DoorsOpenState-reachable transitions (i.e. after MovingState reports arrival) — illegal transitions like "open doors while moving" are structurally unrepresentable rather than guarded by scattered if checks.
  • Why Strategy for dispatch, not a hardcoded method: "which elevator answers this hall call" is exactly the kind of algorithm an interviewer expects to swap mid-round — nearest-car is the simple default, but zoning (dedicate elevators to floor bands during known traffic patterns) or destination-dispatch (passengers enter their destination floor at a hall kiosk, not just a direction) are common follow-ups. Isolating this behind DispatchStrategy.selectElevator() means the swap touches zero Elevator code.
  • Dispatcher as the atomicity boundary: the strategy only selects a candidate; the Dispatcher is what actually claims the call on that elevator under a lock, closing the same check-then-act gap this document has flagged in every resource-allocation problem so far (see W).
  • Why not model the Dispatcher itself as a Singleton: exactly one Dispatcher exists per building in practice, which might tempt a Singleton — but the controller already owns exactly one Dispatcher instance by composition, with no global static access needed anywhere else in the codebase. Reaching for Singleton here would repeat the naive shortcut this document has already flagged and rejected in Parking Lot and Ride-Sharing (see the Cross-Problem Synthesis Singleton contrast).

O. Design Evolution

  • V1: single elevator, a boolean doorsOpen flag and inline movement logic, no dispatch at all.
  • V2: extract real ElevatorState classes once "doors should not open while moving" becomes an explicit safety requirement.
  • V3: add a second elevator, forcing a Dispatcher and a first DispatchStrategy (nearest-car).
  • V4: add a second strategy (zoning) once peak-traffic behavior is requested — validates the Strategy boundary drawn in V3.
  • V5: add out-of-service handling and pending-request redistribution.
  • V6: optional Observer layer for floor/cabin displays; optional access-control Proxy for restricted floors.

What stays stable: ElevatorController's public API. New dispatch algorithms are pure additions; fleet size changes don't touch Elevator or state classes at all.

Ownership/validation notes: requestElevator() constructs a HallCall and hands it to the Dispatcher, which selects a candidate via the active strategy and then atomically claims that call on the candidate's stop queue — if the claim fails (e.g. the candidate went out of service in the interim), it retries selection rather than dropping the call.

Q. Pseudocode — Critical Logic

Dispatcher.dispatch(hallCall):
  loop:
    candidate = strategy.selectElevator(hallCall, activeElevators)
    if candidate is null: queue call for retry; return
    lock(candidate)
    try:
      if candidate.isInService() and not candidate.isFull():
        candidate.addStop(hallCall.floor)
        return   // claimed
    finally:
      unlock(candidate)
    // candidate became unavailable between selection and claim — retry with remaining elevators

NearestCarStrategy.selectElevator(call, elevators):
  best = null; bestDistance = infinity
  for e in elevators:
    if not e.isInService(): continue
    if e.direction == call.direction or e.direction == IDLE:
      d = abs(e.currentFloor - call.floor)
      if d < bestDistance: best = e; bestDistance = d
  return best
void dispatch(HallCall hallCall) {
  while (true) {
    Elevator candidate = strategy.selectElevator(hallCall, activeElevators);
    if (candidate == null) { queueForRetry(hallCall); return; }
    lock(candidate);
    try {
      if (candidate.isInService() && !candidate.isFull()) {
        candidate.addStop(hallCall.getFloor());
        return;   // claimed
      }
    } finally {
      unlock(candidate);
    }
    // candidate became unavailable between selection and claim — retry with remaining elevators
  }
}

Elevator selectElevator(HallCall call, List<Elevator> elevators) {
  Elevator best = null;
  double bestDistance = Double.POSITIVE_INFINITY;
  for (Elevator e : elevators) {
    if (!e.isInService()) continue;
    if (e.getDirection() == call.getDirection() || e.getDirection() == Direction.IDLE) {
      double d = Math.abs(e.getCurrentFloor() - call.getFloor());
      if (d < bestDistance) { best = e; bestDistance = d; }
    }
  }
  return best;
}

U. Testing Strategy

  • Happy path: a hall call is answered by exactly one elevator; car calls after boarding are served in SCAN order, not arrival order.
  • Edge cases: a full cabin skips further hall calls in its direction until it drops below capacity; an out-of-service elevator is never selected and its pending stops are redistributed.
  • Safety invariant: canOpenDoor() is false for every state except a stopped arrival — attempting to open doors mid-MovingState is rejected at the state level, not by a caller-side check.
  • Concurrency tests: many simultaneous hall calls across floors never result in the same call claimed by two elevators, nor silently dropped, under high contention.

W. Concurrency

Shared mutable state: each elevator's stop queues and in-service flag; the Dispatcher's view of which elevators are available.

  • The check-then-act race, once more: selecting a candidate (read) and claiming the call on it (write) are two separate steps; if not locked around the claim, two concurrent hall calls could both select the same idle elevator before either claims it, or a call could be assigned to an elevator that goes out-of-service in between. The Dispatcher closes this the same way Parking Lot closes spot-occupation: lock the candidate, re-verify eligibility, then commit — not select-then-blindly-assign.
  • Per-elevator locking, not a global dispatch lock: claiming a call only needs to lock the one candidate elevator, so unrelated elevators keep processing their own stops without contention.

X. Persistence

Elevator and fleet state is operational, not something that needs durable storage across restarts in most rounds — a restart can reasonably reinitialize all cabins to floor 1, idle. If asked, only aggregate metrics (trip counts, average wait time) would be persisted, behind a simple repository interface, without touching Elevator or Dispatcher.

Z. Failure Scenarios

  • Elevator stalls between floors: transitions to OutOfServiceState from any prior state; the Dispatcher immediately redistributes its unclaimed stops to other in-service elevators via the same strategy path used for fresh calls.
  • Door obstruction mid-close: a sensor-triggered re-open is just another legal transition from the closing sub-state back to DoorsOpenState — handled entirely within the state machine, no Dispatcher involvement.
  • Power loss mid-transit: out of scope for pure LLD (this is a hardware/failsafe-brake concern), but the design should not assume it can't happen — OutOfServiceState being reachable from MovingState is exactly what makes recovery representable at all.

AA. Common Bad Designs

  • A single Elevator class that also decides which of its siblings should answer a call — couples cabin mechanics to fleet-wide decisions and makes every new dispatch algorithm a change to every elevator instance.
  • FIFO stop queue instead of direction-ordered (SCAN) queues — technically correct but reverses direction far more often than necessary, the elevator equivalent of naive disk scheduling.
  • Selecting a candidate and assigning the call as one non-atomic step — passes single-threaded tests, double-assigns or drops calls under real concurrency.
  • Singleton Dispatcher "because there's only one" — see I; ordinary composition already provides exactly one instance without the global-access downsides.

AC. Interviewer Evaluation

Strong signal: proposing State for the elevator's own behavior unprompted; separating dispatch algorithm from dispatch mechanism (Strategy vs. Dispatcher) without being led there; naming the SCAN/disk-scheduling analogy; catching the select-then-claim race before being walked into it.

Red flag: one Elevator god-class handling both cabin mechanics and fleet-wide selection; a FIFO stop queue presented as the final answer; treating "which elevator answers this" as a static rule instead of a swappable Strategy.

AD. Interview Simulation

Interviewer: Design a bank of elevators.
Candidate: Each elevator's own behavior is a State machine — idle, moving, doors-open, out-of-service — because the illegal transitions matter for safety, like never opening doors while moving.
Interviewer: Now there are five elevators. Who decides which one answers a given floor's call?
Candidate: That's a separate concern from the elevator itself — a Dispatcher using a swappable DispatchStrategy. A simple default picks the nearest elevator already heading the right direction or idle; if you need zoning for peak hours later, that's a new strategy, not a rewrite of the elevator classes.
Interviewer: What happens if two hall calls come in at the same instant and both would naturally go to the same idle elevator?
Candidate: Selecting the candidate and actually claiming the call have to be separate steps, and the claim has to be locked and re-verified — otherwise you get the same race as two people grabbing the last parking spot. Whichever claim commits first wins; the other retries selection against the now-updated fleet state.

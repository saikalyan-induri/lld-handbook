A. Realistic Interview Prompt

"Design a two-player chess game. Support standard piece movement, detecting check and checkmate, and undoing a move. You do not need a graphical interface."

B. Difficulty

Intermediate → Advanced. Per-piece movement rules are mechanical; the real difficulty is check/checkmate detection (which requires simulating a move before committing to it) and building undo cleanly without an ad hoc "remember the last few fields I changed" hack.

C. What This Problem Tests

  • Judgment on inheritance vs. Strategy for piece movement — and recognizing that plain polymorphism is the correct simple answer here, not an under-engineered one
  • Modeling a move as a first-class Command object, enabling undo/redo and move-history without special-casing
  • Check detection as "is the king's square attacked by any opposing piece," reusing each piece's own move-generation logic rather than writing a separate parallel algorithm
  • Recognizing which real chess rules (castling, en passant, promotion) are meaningful scope-boundary discussions rather than something to silently skip or silently over-build

D. Requirements

Functional

  1. Standard 8×8 board, standard piece set and starting position for two players (White, Black)
  2. Enforce each piece type's legal movement, including captures
  3. Detect check, checkmate, and stalemate
  4. Reject any move that would leave the moving player's own king in check
  5. Support undo of the most recent move

Non-Functional

  • Adding a new piece-movement rule (a variant game) must not require changes to the turn/check-detection engine
  • Undo must restore all incidental state a move may have changed (captured piece, castling rights), not just the piece's square

F. Assumptions

  • Confirmed: standard 8×8 board, standard pieces, check/checkmate/stalemate detection, single-move undo.
  • Assumption: castling, en passant, and promotion are in scope but flagged explicitly as the highest-complexity part of the design (see V) rather than silently simplified away.
  • Assumption: no AI opponent — an engine that evaluates positions (minimax, alpha-beta, neural evaluation) is an entirely different, much larger problem than legality-checking, and is named but out of scope unless the interviewer pivots there.
  • Assumption: local two-player by default; network play, if raised, adds a server-authoritative validation boundary but doesn't change the core piece/board/move model.

I. Class Relationships

  • Why plain polymorphism, not Strategy, for piece movement (a deliberate rejection): Strategy exists to let the same object swap algorithms independently of its identity. A Rook's movement rule is not independent of being a Rook — a piece's type and its movement rule are the same fact, and always change together (a Rook never needs to "become" bishop-movement without becoming a Bishop). Plain subclassing (Piece → Rook/Bishop/…) is the honest, simpler answer, and reaching for Strategy here would be pattern-matching for its own sake rather than solving a real independent-variation problem — the same kind of judgment call as Splitwise's Payment-as-sibling-not-subclass, just landing on the opposite pattern.
  • Command (headline) for moves: a Move knows how to execute() and undo() itself, including restoring a captured piece and any castling-rights side effects. This is what makes undo a one-line pop-and-undo off a MoveHistory stack instead of manually diffing board state.
  • Check detection reuses getValidMoves(), it doesn't duplicate it: "is my king in check" is exactly "does any opposing piece's valid-move set include my king's square" — Board.isSquareAttacked() is built directly on the same per-piece movement logic already written for regular moves, not a second parallel implementation.
  • Why Command over Memento for undo: a full-board Memento snapshot per move is simpler to reason about (no risk of forgetting an incidental field) but far more memory per move; a Command that stores only the delta (moved piece, captured piece, one flag) is the more space-efficient standard choice for a game with potentially hundreds of moves in a history — see AB for the explicit trade-off.

O. Design Evolution

  • V1: board + pieces with basic movement, no check detection, no undo.
  • V2: add isSquareAttacked() and self-check rejection once "you can't move into check" becomes a real requirement.
  • V3: extract Move as a Command once undo is requested, replacing any ad hoc "remember what I changed" approach.
  • V4: add checkmate/stalemate detection (no legal move exists that escapes check) once the game needs to actually end.
  • V5: add castling/en passant/promotion as explicit special-move handling once requested — flagged as the highest-complexity increment, not a drop-in.

What stays stable: Piece.getValidMoves()'s signature and ChessGame.makeMove()'s public contract. Special moves and network play both layer on without touching the base movement model.

Ownership/validation notes: makeMove() first asks the piece at from for its candidate moves, confirms to is among them, then simulates the move on the board, checks isInCheck(movingColor) against the simulated result, and only commits (pushes to MoveHistory) if the simulated position is legal — otherwise it reverts the simulation and rejects the move.

MoveResult makeMove(Position from, Position to) {
  Piece piece = board.getPieceAt(from);
  if (piece == null || piece.getColor() != currentTurn) return MoveResult.REJECT;
  if (!piece.getValidMoves(board).contains(to)) return MoveResult.REJECT;

  Move move = new Move(from, to, piece, board.getPieceAt(to));
  move.execute(board);                      // simulate
  if (isInCheck(currentTurn)) {
    move.undo(board);                       // illegal — leaves own king in check
    return MoveResult.REJECT;
  }
  history.push(move);                        // commit
  currentTurn = opponent(currentTurn);
  if (isCheckmate(currentTurn)) declareWinner(piece.getColor());
  return MoveResult.OK;
}

boolean isSquareAttacked(Position square, Color byColor) {
  for (Piece piece : board.getPieces()) {
    if (piece.getColor() == byColor && piece.getValidMoves(board).contains(square)) return true;
  }
  return false;
}
MoveResult ChessGame::makeMove(Position from, Position to) {
  auto piece = board.getPieceAt(from);
  if (piece == nullptr || piece->color != currentTurn) return MoveResult::REJECT;
  auto validMoves = piece->getValidMoves(board);
  if (std::find(validMoves.begin(), validMoves.end(), to) == validMoves.end()) return MoveResult::REJECT;

  Move move(from, to, piece, board.getPieceAt(to));
  move.execute(board);                      // simulate
  if (isInCheck(currentTurn)) {
    move.undo(board);                       // illegal — leaves own king in check
    return MoveResult::REJECT;
  }
  history.push(move);                        // commit
  currentTurn = opponent(currentTurn);
  if (isCheckmate(currentTurn)) declareWinner(piece->color);
  return MoveResult::OK;
}

bool Board::isSquareAttacked(Position square, Color byColor) {
  for (auto& piece : pieces) {
    if (piece->color != byColor) continue;
    auto moves = piece->getValidMoves(*this);
    if (std::find(moves.begin(), moves.end(), square) != moves.end()) return true;
  }
  return false;
}

R. End-to-End Use Case

makeMove(e2, e4)  — White pawn
  │  e4 in Pawn.getValidMoves(board)? yes → simulate → isInCheck(WHITE)? no → commit
  ▼
makeMove(e7, e5)  — Black pawn (symmetric)
  ▼
... play continues ...
  ▼
makeMove(d8, h4)  — Black queen delivers check
  │  after commit: isInCheck(WHITE) == true
  ▼
White's next makeMove() candidates are filtered: any move that doesn't resolve
the check is rejected the same way as any other self-check-inducing move
  ▼
If no legal move exists for WHITE while in check → isCheckmate(WHITE) == true → game ends

U. Testing Strategy

  • Happy path: each piece type's movement matches its rule exactly, including capture-vs-block distinctions (a pawn captures diagonally but moves straight).
  • Edge cases: a move that would leave the mover's own king in check is rejected even though the piece's raw geometry allows it; checkmate is detected only when truly no legal escape exists (not merely "the king is attacked").
  • Undo correctness: undoing a capturing move restores the captured piece to its original square and color, not just the mover's position.
  • Special-move tests (if in scope): castling is rejected if the king has previously moved, if the rook has previously moved, or if any square in the king's path is attacked.

W. Concurrency

A single game is inherently turn-based and single-writer — only one move is ever being validated/applied at a time, so there is no shared-resource race analogous to Parking Lot's or Elevator's. The one real concern, and only if network play is in scope, is server-side move authority: the server (running the same ChessGame) must be the sole place a move is validated and committed, rejecting a client's move if it doesn't match the server's current turn/board state — a staleness check, not a lock.

X. Persistence

Move history doubles naturally as a persistence log — replaying the MoveHistory stack from the initial position reconstructs the full game, which is exactly how real chess notation (PGN) works. Persisting a game is therefore "serialize the move list," not "serialize the board," which is both more compact and naturally resumable.

Z. Failure Scenarios

  • A client submits a move for a turn that already passed (stale network message): rejected by the turn-order check before any board simulation happens.
  • Undo requested with no moves in history: a no-op rejection, not an exception from popping an empty stack.
  • A simulated move is found illegal (leaves own king in check): the simulation is fully reverted via the same Move.undo() path used for ordinary undo — there is exactly one reversal code path, not a separate "rollback a rejected move" special case.

AA. Common Bad Designs

  • One Piece class with a type enum and a switch statement inside getValidMoves() instead of real subclasses — the most common naive shape for this problem.
  • Checking for check with a separate, hand-rolled attack algorithm instead of reusing getValidMoves() — duplicated logic that inevitably drifts out of sync with actual piece movement rules.
  • Undo implemented as "remember the last few (from, to) squares" without capturing the captured piece or castling-rights side effects — passes simple tests, corrupts the board on any capture-undo.
  • Applying Strategy to piece movement "for consistency" with other problems in this document — see I; the pattern must fit the actual variation, not be applied reflexively for stylistic consistency.

AC. Interviewer Evaluation

Strong signal: explicitly explaining why piece movement is plain polymorphism and not Strategy; reusing getValidMoves() for check detection instead of writing a second algorithm; simulate-then-validate-then-commit as the shape of makeMove(); naming castling/en passant/promotion as a real complexity jump rather than glossing over them.

Red flag: a type-enum-and-switch Piece class; a separate hand-rolled check-detection algorithm; undo that only restores the moved piece's position; reflexively reaching for Strategy on piece movement without justification.

AD. Interview Simulation

Interviewer: Design a chess game.
Candidate: Each piece type has its own movement rule, so I'd make Piece abstract with a concrete subclass per type — Rook, Bishop, and so on — each implementing its own getValidMoves(). I'd deliberately avoid Strategy here since a piece's type and its movement rule are the same fact and always change together.
Interviewer: How do you detect check?
Candidate: "In check" just means the king's square is attacked — I'd reuse the exact same getValidMoves() every piece already implements: scan the opponent's pieces, and if any of their valid moves include my king's square, I'm in check. No separate algorithm.
Interviewer: How would you support undo?
Candidate: Model each move as a Command with execute() and undo(), storing the captured piece and any side effects, and push it onto a history stack. Undo is just pop-and-undo — and I actually reuse that same reversal path when a simulated move turns out to leave my own king in check.
Interviewer: What about castling and en passant?
Candidate: I'd flag those explicitly as the highest-complexity part of the design — castling needs "has this king or rook ever moved" tracking plus an attacked-square check along the king's path, and en passant needs one extra piece of transient state for the target square. I wouldn't want to quietly simplify those away without naming the cost.
